# 第36講　ハイブリッド暗号

第III部・暗号技術。**到達目標**は、共通鍵暗号と公開鍵技術を組み合わせる理由を説明し、RSA鍵配送とECDHE鍵共有の違い、TLSの認証、Forward Secrecy（前方秘匿性）を、科目Aの選択肢と科目Bの事例で判断できることである。

**参考書の確認箇所**：『徹底攻略 情報処理安全確保支援士教科書 令和7年度版』4-1-1「共通鍵暗号方式」（p.257～262）、4-1-2「公開鍵暗号方式」（p.263～266）、6-1-1「TLS」（p.378～380）。本文の暗号方式の基本とTLSの目的は参考書に基づく。TLS 1.3の具体的なメッセージ順序、HKDF、X25519などは講師の技術仕様補足であり、参考書の旧来のTLS説明と区別する。図、ログ、設問例は講師作成。

**学習優先度**：A（必須）75％＝鍵配送・鍵共有・認証・前方秘匿性・TLS・攻撃判断。B（理解補助）20％＝公開鍵の数学的イメージと鍵導出。C（任意）5％＝HKDFの内部式や楕円曲線演算の詳細。

## 1．なぜ二つの暗号技術を組み合わせるのか【A】

顧客がWebサイトでクレジットカード情報を送る場面を考えよう。通信を暗号化するにはAESのような**共通鍵暗号**が適している。AESは比較的高速で、大量のHTTPデータを継続して暗号化できる。しかしAESでは暗号化と復号に同じ秘密鍵が必要になる。ブラウザとWebサーバが初めて通信する場合、両者はまだ同じ秘密鍵を持っていない。鍵をそのままネットワークに流せば、盗聴者もその鍵を知り、暗号文を復号できてしまう。つまり「データを暗号化できる」ことと「その暗号鍵を安全に共有できる」ことは別の課題である。

公開鍵暗号なら、受信者が公開する鍵を用いて秘密情報を暗号化し、受信者だけが保持する秘密鍵で復号する方法を取れる。一方、RSAなどの公開鍵暗号は計算負荷が大きく、暗号化できる平文の長さにも制限がある。大きなファイルをRSAで直接暗号化するのは実用的ではない。そこで、公開鍵技術で**小さな鍵を確立**し、実データはAESなどの共通鍵暗号で保護する。これがハイブリッド暗号の基本発想である。

|技術|得意なこと|それだけでは足りないこと|
|---|---|---|
|AESなどの共通鍵暗号|大量データを効率的に暗号化する|初対面の相手との鍵共有|
|RSAによる鍵配送|受信者の公開鍵で秘密情報を暗号化して届ける|大量データの直接暗号化、前方秘匿性|
|ECDHEによる鍵共有|双方が秘密値を送らずに共有秘密を確立する|通信相手が本物かどうかの認証|
|証明書と電子署名|公開鍵の持ち主やハンドシェイクの正当性を検証する|HTTPデータの高速な暗号化|

ここで重要な区別がある。「公開鍵暗号で共通鍵を送る」は**RSA鍵配送型**の説明としては正しいが、**ECDHEを使う現代のTLS**では同じ説明は正確ではない。ECDHEでは共通の秘密を暗号化して送るのではなく、双方が計算によって共有秘密を作る。

## 2．RSA鍵配送型のハイブリッド暗号【A】

送信者Aが受信者Bへ機密ファイルを送る例で、登場する鍵を分けて考える。BはRSA公開鍵とRSA秘密鍵のペアを生成し、公開鍵を公開する。秘密鍵はBだけが厳重に保管する。Aはファイル暗号化用に新しいランダムなAES鍵Kを生成する。**BのRSA公開鍵、BのRSA秘密鍵、AES鍵Kは別物**である。

**図1：RSA鍵配送型の流れ**

```text
送信者A                                          受信者B
  |                                                |
  |<--------- BのRSA公開鍵（事前に取得） -----------|
  |                                                |
  | AES鍵Kを乱数で生成                              |
  | ファイルをAES鍵Kで暗号化                        |
  | KをBのRSA公開鍵で暗号化                         |
  |                                                |
  |-- RSAで暗号化したK + AESで暗号化したファイル -->|
  |                                                | RSA秘密鍵でKを復号
  |                                                | Kでファイルを復号
```

①BはRSA鍵ペアを準備する。②AはAES鍵Kを生成し、ファイルをKで暗号化する。③Aは**BのRSA公開鍵**でKだけを暗号化する。④Aは「RSAで暗号化されたK」と「AESで暗号化されたファイル」を送る。⑤Bは**BのRSA秘密鍵**でKを復元する。⑥Bは復元したKでファイルを復号する。RSAが処理するのは小さな鍵であり、ファイル本体ではない。これが性能面での利点である。

なお、公開鍵を取得しただけでは、その鍵が本当にBのものか分からない。攻撃者がBの公開鍵を自分の公開鍵に差し替えれば、Aは攻撃者に読める形でKを送ってしまう。公開鍵と本人の対応関係を確認する仕組みが必要になる。TLSでは証明書による認証がこの問題に関係する。

ファイルをAES-GCMで暗号化する場合、暗号文のほかにnonceと認証タグを扱う。認証タグは改ざん検出に使う。第34講の復習として、**同じAES-GCM鍵の下でnonceを再利用しない**ことも忘れない。単に「AESで暗号化した」だけでは、どの動作モードを使い、完全性をどう保護したかまでは分からない。

## 3．RSA鍵配送と過去通信の危険【A】

攻撃者が今日の暗号化通信を記録し、数年後にBの長期RSA秘密鍵を盗んだとする。記録の中にRSAで暗号化されたKがあれば、攻撃者は盗んだ秘密鍵でKを復号し、さらにKで当時のデータを復号できる可能性がある。**盗聴した当時に復号できなくても、後日の秘密鍵漏えいで過去の通信が危険になる**という点が重要である。

**図2：過去通信の記録と後日漏えい**

```text
時点1：攻撃者が [RSA暗号化されたK] と [AES暗号化された通信] を保存
                             |
時点2：サーバの長期RSA秘密鍵が漏えい
                             |
時点3：保存していたKを復号 → Kで保存済み通信を復号するおそれ
```

このような長期秘密鍵の後日漏えいから過去通信を守る性質を**Forward Secrecy（前方秘匿性）**という。RSA鍵配送型は通常この性質を備えない。一方、ECDHEでは通信ごとに生成した一時秘密値を適切に破棄することによって、長期認証秘密鍵だけが後から漏えいしても過去の共有秘密を計算し直せないようにする。ただし、当時の一時秘密値や通信鍵自体が漏えいすれば、対応する通信は危険になり得る。「前方秘匿性があれば鍵漏えいの被害がゼロになる」という意味ではない。

## 4．ECDHEでは何を交換し、なぜ同じ秘密を作れるのか【A・B】

ECDHEは *Elliptic Curve Diffie-Hellman Ephemeral* の略で、楕円曲線を用いる一時的なDiffie-Hellman鍵共有である。ここでいう「一時的」は、鍵共有用の秘密値をセッションに応じて新しく生成することを意味する。数学の詳細はCだが、誰が何を秘密にし、何を送るかはAの必須知識である。

ブラウザは秘密値 `a` を、サーバは秘密値 `b` を、それぞれ独立して生成する。公開された基準点を `G` とすると、ブラウザは公開情報 `A = aG`、サーバは公開情報 `B = bG` を計算する。ここでの掛け算は楕円曲線上の点の演算であり、通常の整数の掛け算ではない。公開情報から元の秘密値を逆算することは、適切な方式・パラメータでは計算上困難である。

**図3：ECDHEの交換と共有秘密の計算**

```text
ブラウザ                                     サーバ
秘密値 a を生成                              秘密値 b を生成
公開情報 A = aG を計算                        公開情報 B = bG を計算
    |                                           |
    |--------------- 公開情報 A --------------->|
    |<-------------- 公開情報 B ----------------|
    |                                           |
    | 自分の a と相手の B を使用                 | 自分の b と相手の A を使用
    | aB = a(bG) = abG                          | bA = b(aG) = abG
    |                                           |
    +-------- 両者が同じ共有秘密 abG を得る -----+

通信路に流れる：A、B（公開情報）
通信路に流れない：a、b、共有秘密 abG
```

ブラウザは受け取ったBに自分の秘密値aを作用させて `aB = abG` を計算する。サーバは受け取ったAに自分の秘密値bを作用させて `bA = abG` を計算する。両者の結果が一致するのは、楕円曲線上のスカラー倍の性質による。盗聴者はAとBを見られるが、aもbも知らないため、通常は同じ結果を得られない。**秘密値を送らず、公開情報だけで共有秘密を確立できる**のが鍵共有の核心である。

ただし、ECDHEで得た共有秘密をそのままAES鍵として使用するとは限らない。TLS 1.3では、**HKDF（HMAC-based Key Derivation Function）**という鍵導出の仕組みを使い、共有秘密とハンドシェイクの情報などから用途別の鍵を導出する。クライアントからサーバへの暗号化鍵と、サーバからクライアントへの暗号化鍵も区別する。HMACはハッシュ関数を利用したメッセージ認証コードの仕組みである。HKDF内部の式は今回の必須範囲ではない。

## 5．なぜECDHEだけでは中間者攻撃を防げないのか【A】

ECDHEの数学が安全でも、**相手の公開情報が本当に正規サーバから来たか**は別問題である。攻撃者Mがブラウザと正規サーバの間でメッセージを差し替えられる場合、Mはブラウザには「サーバ」を装って自分の公開情報を送り、サーバには「ブラウザ」を装って別の公開情報を送れる。すると、ブラウザとM、Mとサーバの間に**別々の共有秘密**が成立する。

**図4：認証のない鍵共有で起こる中間者攻撃**

```text
ブラウザ                攻撃者M                  正規サーバ
   |                       |                         |
   |--- ECDHE公開情報 ---->|--- 別の公開情報 ------->|
   |<-- Mの公開情報 -------|<-- サーバの公開情報 -----|
   |                       |                         |
   |<== 共有秘密 K1 ======>|<====== 共有秘密 K2 ====>|
   |                       |                         |
   |--- K1で暗号化 ------->|                         |
   |                       | 復号・閲覧・改変可能    |
   |                       |--- K2で再暗号化 ------->|
```

MはECDHEを破っているのではない。**M自身が二つの鍵共有の正当な計算当事者になっている**ので、それぞれの通信を復号できるのである。だから「ECDHEを使用している」というログだけでは、相手認証が安全とは判断できない。

TLSではサーバが**公開鍵証明書**を提示する。証明書は、サーバ名などの識別情報と公開鍵を結び付け、認証局（CA）が署名する仕組みである。ブラウザは信頼の連鎖、接続先ホスト名、有効期間などを検証する。TLS 1.3ではさらにサーバがハンドシェイクに関係する情報へ電子署名を行い、ブラウザが証明書中の公開鍵で検証する。これによって正規サーバの秘密鍵を持たないMは、単純に公開情報を差し替えただけでは正当な署名を作れない。

逆に、アプリケーションが証明書検証を無効化していると、Mの偽証明書を受け入れ、Mとの鍵共有を正規サーバとの通信だと誤認するおそれがある。**対策はECDHEの採用だけでなく、証明書・ホスト名・署名の適切な検証を維持すること**である。第35講での復習対象「証明書検証無効が中間者攻撃につながる因果関係」は、この具体例で確認しておこう。

## 6．TLS 1.3の通信を順番に追う【A】

HTTPSは、HTTPをTLSで保護する仕組みである。TLS 1.3の通常のサーバ認証付きフルハンドシェイクを簡略化して追う。再接続時のPSKや0-RTTなど、別の経路もあるが、ここでは扱わない。

**図5：TLS 1.3の主要メッセージ（概念図）**

```text
ブラウザ                                              Webサーバ
  |                                                       |
  |-- ClientHello ---------------------------------------->|
  |   対応方式、ECDHE公開情報など                          |
  |<------------------------------------------ ServerHello-|
  |                             選択方式、ECDHE公開情報   |
  |                                                       |
  |  双方がECDHE共有秘密を計算し、HKDFで鍵を導出            |
  |                                                       |
  |<-- {EncryptedExtensions} ------------------------------|
  |<-- {Certificate} -------------------------------------|
  |<-- {CertificateVerify} -------------------------------|
  |<-- {Finished} ----------------------------------------|
  |    証明書・署名・Finishedを検証                         |
  |-- {Finished} ----------------------------------------->|
  |                                                       |
  |<==== アプリケーション用の共通鍵でHTTPを保護 ==========>|

{ }：ハンドシェイク用の鍵で保護されるメッセージ
```

**①ClientHello**：ブラウザは対応する方式と鍵共有用の公開情報などを提示する。**②ServerHello**：サーバは方式を選択し、自分の鍵共有公開情報を返す。双方はそれぞれの秘密値を用いて同じECDHE共有秘密を計算し、HKDFでハンドシェイク用の鍵を導出する。**③EncryptedExtensions**：サーバは暗号化された拡張情報を送る。**④Certificate**：サーバは証明書を提示する。**⑤CertificateVerify**：サーバはハンドシェイクの内容に関連した署名を送り、証明書の秘密鍵を持つことを証明する。**⑥Finished**：双方がハンドシェイクの整合性を確認する。認証・検証に成功したら、導出したアプリケーション用の鍵でHTTP要求・応答を保護する。

ここで二つの注意点がある。第一に、**TLS 1.3ではServerHelloの後、ハンドシェイク途中から暗号化が始まる**。第二に、**TLS 1.3ではRSA鍵配送を使わない**。ただしRSAの署名アルゴリズムをサーバ認証に使うことはある。「RSA鍵配送なし」と「RSAを一切使わない」は同義ではない。

## 7．設定・ログを読む【A】

以下は実製品のログではなく、学習用に簡略化した**擬似ログ**である。実際のTLS 1.3では鍵共有グループと暗号スイートは別に交渉される。

```text
[接続A]
Protocol    = TLSv1.3
KeyShare    = X25519
CipherSuite = TLS_AES_256_GCM_SHA384
CertVerify  = enabled

[接続B]
Protocol    = TLSv1.2
CipherSuite = TLS_RSA_WITH_AES_128_CBC_SHA
CertVerify  = enabled

[接続C]
Protocol    = TLSv1.3
KeyShare    = X25519
CipherSuite = TLS_AES_128_GCM_SHA256
CertVerify  = disabled
```

接続AはTLS 1.3で、X25519によるECDHE鍵共有とAES-256-GCMによるデータ保護を利用する例である。`SHA384`はハッシュ関数に関係する表示であり、HTTP本文をSHA-384で「暗号化する」という意味ではない。接続BはTLS 1.2のRSA鍵配送型で、後日長期RSA秘密鍵が漏えいした場合に過去通信が解読されるおそれがある。接続CはECDHEを使っていても証明書検証が無効であり、攻撃者の偽証明書を受け入れる中間者攻撃の危険がある。したがって、**鍵共有方式・データ暗号方式・証明書検証の三つを別々に確認する**。

TLS 1.3の`TLS_AES_256_GCM_SHA384`だけからECDHEの曲線を断定してはいけない。TLS 1.3では鍵共有方式は暗号スイート名と別に示される。試験では、ログのどの欄が何を表しているかを正確に読み分けよう。

## 8．科目Aの判断と科目Bの答案【A】

**科目Aの判断**：①大量データは共通鍵暗号、②RSA鍵配送とECDHE鍵共有を混同しない、③ECDHEだけでサーバ認証が完成するわけではない、④Forward Secrecyは長期秘密鍵の後日漏えいに対する過去通信の保護、⑤TLS 1.3はRSA鍵配送を使わない、の五点を判断できるようにする。

**科目B例題1**：「TLS 1.2のRSA鍵配送を使用しており、攻撃者が暗号化通信を保存していた。後日サーバのRSA秘密鍵が漏えいした。影響と対策を述べよ。」

**答案例**：「攻撃者は保存した鍵配送メッセージを漏えいしたRSA秘密鍵で復号し、当時の通信鍵を復元して過去通信を解読するおそれがある。ECDHEを用いる鍵共有へ変更し、長期秘密鍵の後日漏えいから過去通信を保護する。」

単に「RSAは危険」と答えても、何がどのように漏れるかが分からない。**保存された鍵配送メッセージ → 秘密鍵による復号 → 通信鍵の復元 → 過去通信の解読**という因果関係が答案の中心である。

**科目B例題2**：「WebアプリケーションはTLS 1.3とECDHEを使うが、サーバ証明書の検証を無効にしている。問題点と対策を述べよ。」

**答案例**：「攻撃者が偽のサーバ証明書を提示しても受け入れられ、攻撃者とのECDHE鍵共有を正規サーバとの通信と誤認するため、通信を盗聴・改ざんされるおそれがある。信頼の連鎖、接続先ホスト名、有効期間などの証明書検証とハンドシェイクの署名検証を適切に実施する。」

ここでも「証明書を検証する」とだけ書くより、**検証しない → 偽サーバを受け入れる → 攻撃者と鍵共有する → 通信内容を読まれる**という理由をつなげることが重要である。

## 9．混同しやすい事項と復習【A・B】

|混同する概念|区別するポイント|
|---|---|
|RSA公開鍵とAES鍵|RSA公開鍵は鍵配送に使い、AES鍵はファイル本体の暗号化に使う|
|鍵配送と鍵共有|鍵配送は暗号化した秘密情報を送る。ECDHE鍵共有は公開情報を交換し、各自で共有秘密を計算する|
|鍵共有と相手認証|同じ秘密を計算できても、その相手が正規サーバとは限らない|
|長期秘密鍵と一時秘密値|長期秘密鍵は認証等で継続利用。一時秘密値はECDHEの各鍵共有で使用|
|前方秘匿性と絶対安全|長期秘密鍵の後日漏えいへの保護であり、当時の通信鍵の漏えいまで防ぐわけではない|
|TLS 1.3のRSA署名とRSA鍵配送|署名でRSAを使うことはあっても、RSA鍵配送は使用しない|

今回の最重要事項は三つある。**第一に、共通鍵暗号はデータの保護、公開鍵技術は鍵の確立に役割分担する。第二に、ECDHEは盗聴者に秘密値を送らず共有秘密を作れるが、相手認証は別に必要である。第三に、RSA鍵配送とECDHEでは、長期秘密鍵が後から漏えいした場合の過去通信への影響が異なる。**

**C：任意発展**として、X25519の演算実装、HKDF-Extract/HKDF-Expandの詳細、TLS 1.3のPSK再開や0-RTT、鍵更新を学ぶ余地がある。ただし、今回の15点の理解度チェックではこれらの内部式を前提にしない。
