第7講｜脆弱性・セキュリティ評価制度

第6講では、SOC・CSIRTなどの組織内の役割と、IPA・JPCERT/CCなど外部組織との連携を学びました。

今回は、ソフトウェアに脆弱性が発見されたときの対処と、セキュリティ製品や企業の管理体制を評価する制度を学びます。

脆弱性の深刻度と、自社にとっての危険性は必ずしも同じではないことが重要です。

1. 到達目標と参考書

1-1. 到達目標

  1. 脆弱性情報の公開から、自社システムの調査・対策までの流れ。
  2. CVE、CVSS、JVN、JVN iPediaの役割の違い。
  3. CVSSの深刻度だけで対策の優先順位を決めてはいけない理由。
  4. ISMS認証と、製品に対するセキュリティ評価の違い。
  5. ISO/IEC 15408（CC）、ST、EAL、JISEC、JCMVPの関係。
  6. 科目Bで、脆弱性の影響調査と対策の根拠を記述する方法。

1-2. 参考書の対応箇所

2. 具体例：A社で重大な脆弱性が発表された

架空の企業A社はインターネット上でECサイトを運営しています。

インターネット上の利用者 → Webサーバ（公開サイト） → アプリケーションサーバ（注文・認証） → データベースサーバ（顧客・注文情報）

アプリケーションサーバのソフトウェアに次の脆弱性が公表されました。

項目 内容
識別番号 CVE-20XX-XXXXX（架空）
対象 製品X バージョン3.0〜3.4
内容 特定の条件下で認証を回避できる
想定される影響 権限のない利用者による管理機能へのアクセス
CVSS基本値 9.8（架空の評価例）
対策 修正版3.5への更新

CVSSが9.8だからといって、影響調査を省略してよいわけではありません。対象バージョンか、脆弱な機能を使用しているか、外部から到達できるかを確認します。更新による業務影響も検証し、必要なら暫定対策を先行させます。

3. 脆弱性とは何か

脆弱性とは、システムやソフトウェアなどに存在するセキュリティ上の弱点です。

概念 A社での例
脅威 攻撃者が認証回避を悪用して侵入しようとすること
脆弱性 認証処理の不備
情報資産 顧客情報、注文情報、ECサイト
リスク 不正アクセスによる情報漏えいやサービス妨害

3-1. 脆弱性が存在すれば、必ず攻撃されるのか

いいえ。脆弱性が存在することと攻撃が成立することは別です。脆弱性自体の深刻度、自社環境での悪用可能性、悪用された際の影響を区別して判断します。

3-2. 脆弱性と設定不備の関係

ソフトウェアの欠陥だけでなく、管理画面の無制限公開や初期パスワード放置などの設定・運用の弱点も攻撃を容易にします。ただし、CVEが付与される製品の脆弱性と個々の設定不備は同じ分類とは限りません。

4. CVE：脆弱性を識別する番号

CVEは Common Vulnerabilities and Exposures の略で、公開された脆弱性を共通の識別番号で管理する仕組みです。形式例は CVE-2025-12345 です（特定の実在する脆弱性を指す例ではありません）。

4-1. なぜ識別番号が必要なのか

製品開発者、セキュリティ企業、研究者が同じ脆弱性を異なる名称で呼んでいても、共通番号があれば同一の問題について情報交換できます。

4-2. CVE番号から分かること・分からないこと

CVE番号そのものは危険度を示しません。 番号が大きいことや年が新しいことは深刻度の根拠にはなりません。

5. CVSS：脆弱性の深刻度を評価する仕組み

CVSSは Common Vulnerability Scoring System の略で、脆弱性の技術的な深刻度を共通の尺度で評価します。

5-1. CVSS基本値

CVSS v3.1では、攻撃元区分、攻撃条件の複雑さ、必要な特権、ユーザ関与、機密性・完全性・可用性への影響などを考慮します。CVSS v4.0では評価項目や体系が変更されています。

5-2. CVSS v3.1の深刻度区分

基本値 深刻度
0.0 なし（None）
0.1〜3.9 低（Low）
4.0〜6.9 中（Medium）
7.0〜8.9 高（High）
9.0〜10.0 緊急（Critical）

5-3. 深刻度と自社リスクの違い

CVSS 9.8でも対象機能が無効で外部到達不能なシステムと、CVSS 7.5でもインターネット公開され実際に悪用されている顧客情報システムとでは、後者を先に対策すべき場合があります。基本値だけで優先順位を決めてはいけません。

5-4. 基本評価・脅威評価・環境評価

CVSS v4.0では基本評価（Base）、脅威評価（Threat）、環境評価（Environmental）を区別します。v3系では時間的評価基準などの用語が使われます。脆弱性自体の性質、攻撃状況、自社への影響を別々に考えます。

6. JVNとJVN iPedia

JVNはIPAとJPCERT/CCが共同運営する脆弱性対策情報ポータルです。

6-1. JVNの役割

識別子 概要
JVN# 国内の脆弱性情報の調整・公表案件など
JVNVU# 海外の調整機関などとの連携案件
JVNTA# 注意喚起情報

6-2. JVN iPediaの役割

JVN iPediaは国内外の脆弱性対策情報を蓄積し検索できるデータベースです。

6-3. CVE・CVSS・JVNの関係

CVE：どの脆弱性か。CVSS：どの程度深刻か。JVN・JVN iPedia：どのような情報・対策があるか。 これは役割の整理であり公開順序を意味しません。

7. 脆弱性管理の実務的な流れ

7-1. 第1段階：情報を収集する

製品開発者、IPA、JVNなどから情報を入手します。前提として、自社が何の製品をどのバージョンで使用しているか、ソフトウェア資産の管理が必要です。

7-2. 第2段階：影響を調査する

対象製品・バージョン、機能の利用状況、攻撃者の到達可能性、影響する資産、侵害の兆候を調べます。外部非公開でも内部侵入後の悪用はあり得ます。

7-3. 第3段階：対応の優先順位を決める

深刻度、攻撃実態、公開範囲、資産の重要性、業務影響を総合して判断します。

7-4. 第4段階：対策を実施する

原則は修正版への更新です。すぐ更新できない場合は、機能無効化、アクセス制限、公開停止、監視強化などの暫定対策を検討します。監視だけで攻撃を防止できるとは限りません。

7-5. 第5段階：対策の有効性を確認する

更新後のバージョン、対象サーバの適用漏れ、業務動作、暫定対策の解除可否、侵害兆候を確認します。脆弱性の修正と侵害済みシステムの復旧は別です。

7-6. 例：パッチ管理の記録

項目 記録例
対象 ECアプリケーションサーバ01
製品 製品X 3.2
対象脆弱性 CVE-20XX-XXXXX（架空）
リスク 外部から認証回避の可能性
暫定対策 管理機能へのアクセス制限
恒久対策 製品X 3.5へ更新
確認 バージョン確認、動作試験、関連ログ確認
状態 対策済み

8. セキュリティ評価制度は何を評価するのか

組織の管理体制を評価する制度と、製品のセキュリティ機能を評価する制度は異なります。販売者が「安全」と主張するだけでなく、一定の規格・基準に基づく評価が判断材料となります。

9. ISMS適合性評価制度

ISMSは Information Security Management System の略で、組織の情報セキュリティリスクを管理し、継続的に改善する仕組みです。中心的な規格はISO/IEC 27001（JIS Q 27001）です。

9-1. ISMSはセキュリティ製品なのか

いいえ。資産把握、リスク評価、管理策の決定・実施、確認・改善という組織の活動を対象とします。

9-2. ISMS認証を取得すれば事故は起きないのか

いいえ。認証は規格への適合性を確認するもので、事故が絶対に起きないことを保証しません。

9-3. 認証機関と認定機関の違い

機関 役割
認証機関 組織のISMSを審査し適合性を認証
認定機関 認証機関の審査能力などを評価
要員認証機関 審査員などの資格に関わる認証

9-4. ISMSの適用範囲

認証が全社の全業務を対象とするとは限りません。取引先の認証を確認するときは対象業務が適用範囲に含まれるかを確認します。

10. CSMS適合性評価制度

CSMSは Cyber Security Management System の略で、産業用オートメーション・制御システムを対象とするセキュリティ管理の仕組みです。

10-1. ISMSとCSMSは何が違うのか

ISMSは幅広い情報セキュリティ管理、CSMSは制御システムに特化します。工場設備ではパッチ適用による停止が生産に影響するため、安全性や可用性にも配慮します。

11. ISO/IEC 15408（Common Criteria）

CCはIT製品のセキュリティ評価に関する国際規格です。

11-1. なぜ製品評価の共通基準が必要なのか

メーカー独自の安全性の主張だけでは比較が難しいため、共通の基準で評価対象の機能や評価範囲を確認します。評価済みでもあらゆる利用環境で安全とは限りません。

11-2. ST（Security Target）

STは、評価対象のセキュリティ要件や機能などを記述した文書です。STに記載された範囲を超える安全性まで保証するものではありません。

11-3. EAL（Evaluation Assurance Level）

従来のCCの評価体系ではEAL1〜7が使われます。高い数値は保証のための評価要求が厳格であることを示しますが、EAL7がEAL4より常に安全とは限りません。 規格の新しい版では保証パッケージの扱いも変わるため適用版を確認します。

11-4. STとEALの違い

用語 何を表すか
ST どのセキュリティ機能・要件を評価するか
EAL どの程度の保証を得るための評価要求を課すか

12. JISECとJCMVP

12-1. JISEC

ITセキュリティ評価及び認証制度。CCに基づきIT製品のセキュリティ機能を評価・認証します。評価機関による評価と認証機関による認証を区別します。

12-2. JCMVP

暗号モジュール試験及び認証制度。暗号機能や暗号鍵などの保護に関する評価・認証を扱います。

12-3. JISECとJCMVPの違い

制度 主な対象 評価の観点
JISEC IT製品のセキュリティ機能 CCに基づく製品評価
JCMVP 暗号モジュール 暗号機能・鍵の保護

13. PCI DSS：業界別のセキュリティ基準

PCI DSSはクレジットカード会員データの保護を目的とした基準です。

13-1. なぜ業界別の基準が必要なのか

カード情報の漏えいによる不正利用を防ぐため、アクセス制御、ネットワーク保護、脆弱性管理、監視などが求められます。

13-2. ISMSとの違い

ISMSは組織の情報セキュリティ管理体制、PCI DSSはカード会員データを安全に扱うための業界別基準です。一方への適合だけで他方への適合は証明されません。

13-3. 規格の版について

PCI DSSは改訂されます。実務では現行版と適用時期を確認します。

14. 評価制度を横断的に整理する

制度・規格 主な対象 試験で押さえるポイント
ISMS／ISO/IEC 27001 組織の情報セキュリティ管理体制 継続的なリスク管理
CSMS 産業用制御システム 制御システムに特化
ISO/IEC 15408（CC） IT製品 STと保証要件
JISEC IT製品の評価・認証 CCに基づく制度
JCMVP 暗号モジュール 暗号機能・鍵の保護
PCI DSS カード会員データ クレジットカード情報の保護

14-1. 「認証取得済み」だけで判断してはいけない

認証の適用範囲が利用予定サービスを含むか、自社の要件を満たすか、データ管理・ログ・障害対応・責任分担が適切かを確認します。

15. 脆弱性管理と評価制度はどうつながるのか

組織としてリスクを管理し、脆弱性情報を収集・評価して修正・緩和します。製品の調達時には評価結果を自社の要件と照合し、新しい脆弱性や業務変更に応じて継続的に見直します。これらは並行して行われる活動です。

16. 科目Aの典型論点

16-1. 脆弱性識別と評価の違い

CVEは識別、CVSSは深刻度評価。CVE番号自体は深刻度を示しません。

16-2. CVSS基本値と対応優先順位の違い

基本値に加え、公開範囲、攻撃状況、資産重要度などを考慮します。

16-3. ISMSとCCの違い

ISMSは組織の管理体制、CCはIT製品の評価基準です。

16-4. STとEALの違い

STは評価要件を記述する文書、EALは保証の程度に関わる指標です。

16-5. JISECとJCMVPの違い

JISECはIT製品、JCMVPは暗号モジュールを主な対象とします。

16-6. 認証の意味

認証はあらゆる攻撃への安全性を保証しません。評価対象、適用範囲、条件を確認します。

17. 科目Bの答案作成ポイント

17-1. 設問例①：脆弱性の影響調査

設問：重大な脆弱性が公表された際に最初に調査すべき事項は何か。

答案例：「自社で使用している製品のバージョンが脆弱性の対象かを確認し、脆弱な機能の使用状況と攻撃者からの到達可能性を調査する。」

17-2. 設問例②：パッチを直ちに適用できない場合

設問：業務上の理由で修正版をすぐ適用できない場合の暫定対策は何か。

答案例：「脆弱な機能へのアクセス元を制限し、必要に応じて当該機能を無効化することで、修正版適用までの悪用リスクを低減する。」

17-3. 設問例③：CVSSが高い脆弱性への対応

設問：CVSS基本値が高いものを常に優先すべきでない理由は何か。

答案例：「CVSS基本値だけでは、自社環境での攻撃可能性や、悪用された場合の業務への影響を十分に反映できないため。」

17-4. 設問例④：認証製品の調達

設問：CC認証製品の調達でSTなどを確認すべき理由は何か。

答案例：「STに記載された評価対象のセキュリティ機能や評価条件が、自社の利用目的と必要なセキュリティ要件に適合するかを確認する。」

17-5. 答案の作り方

原因・条件 → 想定される被害 → 確認事項・対策という順で説明します。

「管理機能に認証回避の脆弱性があり、インターネットから到達できるため、不正な管理操作を行われるおそれがある。そこで、修正版の適用まで管理機能へのアクセスを制限する。」

18. 重要事項の整理

  1. 脆弱性情報が公表されたら、対象製品・バージョン・攻撃成立条件を調べる。
  2. CVEは識別、CVSSは深刻度評価、JVNは脆弱性対策情報の提供に関わる。
  3. CVSS基本値だけで優先順位を決めず、自社環境と業務影響を考慮する。
  4. ISMSは組織の情報セキュリティ管理体制を対象とする。
  5. CCはIT製品の評価基準であり、STは評価対象の要件、EALは保証の程度に関わる。
  6. 科目Bでは何を確認し、何を防ぐためにどの措置を実施するかを書く。

C：発展学習として切り分けた内容

CVSSの計算式、CC保証コンポーネントの詳細、各制度の申請手順、PCI DSS個別要求事項の網羅、脆弱性情報処理APIの実装は今回の必須範囲から除外します。
