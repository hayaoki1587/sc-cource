第18講｜ポート番号とソケット

情報処理安全確保支援士（SC）合格講座｜第1〜23講・詳細再執筆シリーズ

第16講ではTCP、第17講ではUDPを学びました。今回は、それらの通信をどのアプリケーションに届けるのかを決める「ポート番号」と、アプリケーションがネットワーク通信を利用するための「ソケット」を扱います。

例えば、同じサーバでHTTPS、SSH、DNSが同時に稼働していても、通信を正しいサービスに振り分けられるのはなぜでしょうか。また、ファイアウォールでTCP 443番を許可したのに、Webサイトへ接続できない場合、何を確認すればよいのでしょうか。

この講義では、ポート番号の暗記だけでなく、IPアドレス・ポート番号・プロトコル・ソケット・通信状態の関係を理解し、科目Bのログ分析やアクセス制御の問題に対応できるようにします。

既存学習記録：第18講／14点（15点満点）／理解済み。 既修了講義の再執筆であり、過去の得点・修了履歴は変更しません。

  4. 主要なサービスのポート番号とプロトコルを判断できる。
  5. ソケットとTCPコネクションの関係を説明できる。

  7. ファイアウォールやNAPTのログから通信を識別できる。
  8. ポートスキャンや不適切な公開設定の脅威と対策を説明できる。

2. IPアドレスだけでは通信先を特定できない

2-1. 一台のサーバで複数のサービスが動く

サーバIP：203.0.113.10

HTTPSサーバ ─ TCP 443
SSHサーバ   ─ TCP 22
DNSサーバ   ─ UDP 53

宛先IPアドレスがすべて 203.0.113.10 でも、どのアプリケーションへ渡すかは分かりません。そこで、TCPやUDPのヘッダに含まれる宛先ポート番号を使います。

                サーバ：203.0.113.10
                         │
           ┌─────────────┼─────────────┐
           ▼             ▼             ▼
      HTTPSサーバ     SSHサーバ      DNSサーバ
       TCP 443        TCP 22        UDP 53

2-2. IPアドレスとポート番号の役割

情報 主な役割
宛先IPアドレス 通信先のホストやネットワークインターフェースなどを識別する
IPのプロトコル番号 TCP、UDPなど、上位のプロトコルを識別する
宛先ポート番号 受信先のサービス・通信端点を識別する
送信元ポート番号 応答先や通信の識別に使用する

ポート番号はIPアドレスの代わりにはなりません。TCP 443 だけでは世界中のどのWebサーバか分からず、203.0.113.10:443 のように組み合わせます。

2-3. OSはポート番号だけで振り分けるのか

厳密には、OSはトランスポート層のプロトコル、宛先IPアドレス、宛先ポート番号、ソケットの状態なども考慮して受信先を判断します。DNSではTCP 53とUDP 53の両方が使われますが、これらは別の通信です。ポート番号は、TCPとUDPをまたいで一つの共通番号空間を使っているわけではありません。

3. ポート番号の範囲と種類

3-1. ポート番号は16ビット

TCPとUDPのポート番号は、それぞれ16ビットで表現され、値の範囲は 0〜65535 です。ただし0番は通常のサービス待受けに使う番号として扱うものではなく、特別な用途があります。

3-2. 三つの区分

区分 範囲 主な意味
Well-Known Ports 0–1023 標準的・広く知られたサービス
Registered Ports 1024–49151 登録されたアプリケーションなど
Dynamic / Private Ports 49152–65535 動的割当てや私的利用

3-3. ウェルノウンポート

SSHはTCP 22、HTTPはTCP 80、HTTPSはTCP 443が代表的です。しかしサービスが必ず標準ポート番号で稼働するとは限りません。SSHをTCP 2222番で待ち受けさせることもできます。

3-4. 登録済みポート

登録済みポートはアプリケーションなどに割り当てられる範囲です。番号の登録は、その通信が安全であることや、その番号以外で利用できないことを保証しません。

3-5. 動的・プライベートポート

クライアントが接続するとき、送信元ポートは通常OSによって動的に選択されます。

192.0.2.100:53124 → 203.0.113.10:443

ここで53124がクライアントの送信元ポートです。OSが実際に使用する動的ポート範囲は、必ずしも49152〜65535に固定されません。 IANAの区分とOSの一時ポート選択範囲は別です。

3-6. なぜ送信元ポート番号が必要なのか

192.0.2.100:53124 → 203.0.113.10:443
192.0.2.100:53125 → 203.0.113.10:443

宛先が同じでも送信元ポートが異なれば、別のTCPコネクションとして識別できます。

4. 主要なポート番号を覚える

A：必須。 ポート番号は標準的な利用例であり、番号だけでアプリケーションの実体を断定できるわけではありません。

4-1. TCPの代表的なポート番号

ポート サービス 用途
TCP 20 FTP-data FTPのデータ転送で使われる場合がある
TCP 21 FTP FTPの制御接続
TCP 22 SSH 暗号化されたリモートログイン
TCP 23 Telnet 平文のリモートログイン
TCP 25 SMTP 主にメールサーバ間の転送
TCP 53 DNS DNSのTCP通信
TCP 80 HTTP Web通信
TCP 110 POP3 メール受信
TCP 143 IMAP メール受信・管理
TCP 443 HTTPS TLSを用いたWeb通信
TCP 587 Submission メール送信の受付
TCP 993 IMAPS TLSを用いたIMAP
TCP 995 POP3S TLSを用いたPOP3

4-2. UDPの代表的なポート番号

ポート サービス 用途
UDP 53 DNS 名前解決の問い合わせなど
UDP 67 DHCPサーバ IPv4のアドレス設定情報を提供
UDP 68 DHCPクライアント IPv4のアドレス設定情報を受信
UDP 69 TFTP 簡易ファイル転送
UDP 123 NTP 時刻同期
UDP 161 SNMP ネットワーク機器の管理情報取得など
UDP 162 SNMP Trap 管理イベントなどの通知
UDP 520 RIP ルーティング情報の交換
UDP 546 DHCPv6クライアント IPv6の設定情報を受信
UDP 547 DHCPv6サーバ IPv6の設定情報を提供

4-3. DNSはUDP 53だけではない

DNSはUDP 53だけでなくTCP 53も利用します。通常の問い合わせにUDPが使われる場合がある一方、大きな応答などではTCPを使うことがあります。DoTやDoHなど暗号化したDNSもあるため、「UDP 53以外はDNSではない」は誤りです。

4-4. HTTPSはTCP 443だけではない

従来のHTTPSではTCP 443が代表的ですが、HTTP/3はQUICを使い、通常UDP 443で通信します。

TCP 443：HTTPS（HTTP/1.1、HTTP/2など）
UDP 443：HTTP/3（QUIC）など

UDP 443を観測したからといって直ちに不正通信とは判断できません。

4-5. FTPのポート番号に関する注意

FTPは制御用とデータ転送用の通信を分けます。制御接続は通常TCP 21ですが、データ転送で常にTCP 20を使うわけではありません。パッシブモードではサーバが指定した別のポートへクライアントが接続する場合があります。FW制御で問題になりやすい理由です。

4-6. 暗号化の有無はポート番号だけでは決まらない

TCP 443という番号だけでは、TLSが適切に設定されている保証はありません。標準ポート以外でTLS通信を行うこともできます。安全性は実際のプロトコル、暗号化設定、証明書検証、認証などで判断します。

5. ソケットとは何か

5-1. アプリケーションがネットワーク通信を利用する窓口

ソケット（Socket）は、アプリケーションがOSのネットワーク機能を利用して通信するための端点です。

Webサーバのプログラム
        │
        ▼
     ソケット
        │
        ▼
       TCP
        │
        ▼
        IP
        │
        ▼
   ネットワーク

アプリケーションが毎回TCPヘッダやIPヘッダを自作する必要はなく、通常はOSのソケットAPIを利用します。

5-2. ポート番号とソケットは同じものではない

用語 意味
ポート番号 TCP・UDPの通信端点を識別する数値
ソケット アプリケーションが通信に利用するOS上の端点
TCPコネクション 二つの通信端点の間に確立されるTCP通信
ソケットAPI アプリケーションがソケットを操作するための仕組み

5-3. ソケットをIPアドレスとポート番号の組と説明してよいか

入門的には「IPアドレスとポート番号の組」と説明されますが、厳密には不十分です。TCPとUDPでは通信端点が別であり、TCPの待受けソケットと接続済みソケットも役割が違います。IPとポートは識別情報、ソケットはアプリケーションが通信するためのOS上の仕組みです。

6. TCPサーバはどのように接続を受け付けるのか

6-1. 待受けソケット

① socket()  ソケットを作成
② bind()    ローカルIPアドレス・ポート番号を設定
③ listen()  TCP接続要求の待受けを開始
④ accept()  接続を受け付ける

これは代表的なソケットAPIの概念的な流れで、OSや実装によって異なります。

6-2. bindの役割

bind() はソケットをローカルIPアドレスとポート番号に結び付けます。203.0.113.10:443 だけで待ち受ける構成も、0.0.0.0:443 のように複数のIPv4ローカルアドレスで待ち受ける構成もあります。

6-3. listenの役割

listen() はTCP接続要求の待受けを開始します。クライアントのSYNに対して通常TCPスタックがSYN+ACKを返しますが、FWやサーバ負荷などで結果は異なります。

6-4. acceptの役割

accept() は確立された接続をアプリケーションが受け取るために使います。待受けソケットと個々のクライアント用の接続済みソケットを区別します。

          待受けソケット：TCP 443
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
    接続A          接続B         接続C
 クライアントA  クライアントB  クライアントC

6-5. acceptするたびに443番が増えるのか

いいえ。接続済みソケットが増えてもサーバのローカルポートは通常443のままです。送信元・宛先IPとポート番号の組合せなどで区別します。

7. TCPコネクションと4タプル

7-1. 4タプルとは

TCPコネクションは一般に、送信元IP、送信元ポート、宛先IP、宛先ポートの四つの値で識別されます。

192.0.2.101:53001 → 203.0.113.10:443

(192.0.2.101, 53001, 203.0.113.10, 443)

7-2. 複数のクライアントが同時接続できる理由

接続 送信元 宛先
A 192.0.2.101:53001 203.0.113.10:443
B 192.0.2.102:53002 203.0.113.10:443
C 192.0.2.103:53003 203.0.113.10:443

サーバ側はすべてTCP 443でも、送信元IP・ポートが異なるので別の接続です。一つのポートでは一つのクライアントとしか通信できない、は誤りです。

7-3. 同じクライアントから複数接続する場合

192.0.2.101:53001 → 203.0.113.10:443
192.0.2.101:53002 → 203.0.113.10:443
192.0.2.101:53003 → 203.0.113.10:443

同じクライアントIPからでも送信元ポートを変えれば区別できます。

7-4. 5タプルとは

ファイアウォールやフローログでは、4タプルにプロトコル（TCP/UDP）を加えた5タプルを使います。

送信元IP／送信元ポート／宛先IP／宛先ポート／プロトコル

IPとポートが同じでもTCP 53とUDP 53は別の通信です。4タプルと5タプルの違いはプロトコル情報を明示的に含めるかどうかです。

8. TCPとUDPで同じポート番号を使える理由

8-1. TCP 53とUDP 53

DNSサーバ：203.0.113.53
TCP 53 → DNSのTCP通信
UDP 53 → DNSのUDP通信

TCPとUDPは別々のプロトコルとしてポートを管理するため競合しません。

8-2. ポート番号が同じなら同じサービスか

必ずしもそうではありません。TCP 443とUDP 443はWeb関連で利用されますが通信方式は違います。また、管理者が標準と異なるサービスを動かすこともできます。ポート番号とプロトコルの両方を確認します。

8-3. ポート番号だけで攻撃を判定しない

UDP 443が大量に観測されても、それだけでは不審とは断定できません。HTTP/3の可能性があります。通信先、通信量、アプリケーション、利用者操作なども確認します。

9. 待受けポートと通信中のポート

9-1. LISTENとESTABLISHED

Local Address          Foreign Address        State
0.0.0.0:443            0.0.0.0:0              LISTEN
203.0.113.10:443       192.0.2.101:53001     ESTABLISHED
203.0.113.10:443       192.0.2.102:53002     ESTABLISHED

TCP 443で待ち受け、二つのクライアントとの接続が確立しています。

9-2. LISTENは何を意味するか

LISTEN はTCP接続要求の待受けです。しかし外部から接続できる保証はありません。FWの遮断、ループバックだけでの待受け、ルーティング障害、接続先IPの誤りなどが考えられます。

9-3. 127.0.0.1での待受け

127.0.0.1:8080  LISTEN

通常は同じホスト内からの接続を受け付ける設定です。外部端末がLAN側IPへ接続しても、この待受けには直接接続できません。一方 0.0.0.0:8080 LISTEN は通常すべてのIPv4ローカルアドレスを対象とします。ただし外部到達性はFWなどにも左右されます。

9-4. UDPにはLISTENがないのか

UDPはTCPのような接続確立状態を持たず、OSの状態表示でTCPと同じ LISTEN や ESTABLISHED が表示されないことがあります。それでもUDPアプリケーションはポートで受信待ちできます。

10. NAPTとポート番号

10-1. NAPTが必要になる理由

NAPTはIPアドレスとTCP/UDPポート番号を変換する仕組みです。二台の社内PCが同じ送信元ポート50000で同じWebサーバへ接続する例を考えます。

社内PC-A 192.168.1.10:50000 ─┐
                              ├─ NAPTルータ 198.51.100.1
社内PC-B 192.168.1.11:50000 ─┘

10-2. NAPT変換テーブルの例

内部の送信元 変換後の送信元 外部の宛先
192.168.1.10:50000 198.51.100.1:60001 203.0.113.10:443
192.168.1.11:50000 198.51.100.1:60002 203.0.113.10:443 
198.51.100.1:60001 → 203.0.113.10:443
198.51.100.1:60002 → 203.0.113.10:443

同じグローバルIPでも送信元ポートが異なります。

10-3. 戻り通信の処理

203.0.113.10:443 → 198.51.100.1:60001 → PC-A
203.0.113.10:443 → 198.51.100.1:60002 → PC-B

NAPTルータが変換テーブルで内部端末に戻します。

10-4. 送信元ポートは必ず変換されるか

必ずしもそうではありません。元のポートを維持できればそのまま使う実装もあります。複数の内部通信を識別するためにポート番号の変換・管理を使うことが重要です。

10-5. NAPTログで重要なこと

外部から 198.51.100.1:60002 の不審通信が報告された場合、グローバルIPだけでは内部端末を特定できません。該当時刻の変換前後のIP・ポート対応を確認します。

11. ファイアウォールとポート番号

11-1. ファイアウォールの通信制御

FWは送信元・宛先IP、プロトコル、送信元・宛先ポート、通信方向、状態などを利用します。

送信元：社内ネットワーク
宛先：Webサーバ
プロトコル：TCP
宛先ポート：443
動作：ALLOW

11-2. TCP 443を許可すればUDP 443も許可されるか

いいえ。ALLOW TCP 443 と DENY UDP 443 は両立します。HTTP/3はUDP 443を使うため、Web通信の制御時に重要です。

11-3. 宛先ポートと送信元ポートを混同しない

要求：192.0.2.100:53124 → 203.0.113.10:443
応答：203.0.113.10:443 → 192.0.2.100:53124

戻り通信の宛先ポートは443ではなく、クライアントの動的ポート53124です。

11-4. ステートフルファイアウォール

PC → Server：TCP SYN、宛先443
Server → PC：TCP SYN+ACK、宛先53124
PC → Server：TCP ACK

ステートフルFWは内部から開始した接続を追跡して戻り通信を許可できます。ステートレスACLでは戻り方向の条件を別途設定する必要がある場合があります。

11-5. ポートを開けることの意味

「ポートを開ける」には、(1) サーバのアプリケーションがそのポートで待ち受ける、(2) FWがそのポートへの通信を許可する、という別の意味があります。FWが許可してもサービスが停止していれば接続できず、サービスが待ち受けてもFWが遮断すれば外部から接続できません。

12. ポートスキャンの仕組み

12-1. ポートスキャンとは

対象ホストの利用可能なポートやサービスを調査する行為です。正当な管理・診断にも攻撃前の探索にも使われ、ポートスキャンだけで不正アクセス成功とはいえません。

12-2. TCP SYNスキャンの考え方

調査端末 → 対象サーバ：SYN（宛先22）
調査端末 ← 対象サーバ：SYN+ACK

調査端末 → 対象サーバ：SYN（宛先9999）
調査端末 ← 対象サーバ：RST（返る場合）

12-3. SYNスキャンの結果を読む

観測結果 考えられる状態
SYNに対してSYN+ACK TCPポートが接続を受け付けている可能性
SYNに対してRST ポートが閉じている可能性
応答なし FWによる破棄、通信障害、応答制限などの可能性

応答がない＝閉じていると断定しません。

12-4. UDPスキャンの難しさ

UDPにSYN/RSTはありません。UDP未使用ポートへ送るとICMP Port Unreachableが返ることがありますが、応答なしなら開いていて応答しない、FWが破棄、ICMP制限、応答消失など複数の可能性があります。

12-5. ポートスキャンと脆弱性

ポートが開いているだけでは必ずしも脆弱性ではありません。公開WebサーバのTCP 443は必要な場合があります。問題は不要サービスの公開、弱い認証、ソフトウェア脆弱性、不適切なアクセス制御などです。

13. ポート番号に関係するセキュリティ対策

13-1. 不要なサービスを停止する

不要なサービスが待ち受けると攻撃対象が増えます。Telnet（TCP 23）は通常通信内容を暗号化しないため、不要なら停止し、必要なリモート管理にはSSHなどを利用します。

13-2. 管理ポートのアクセス制限

ALLOW Source:192.0.2.0/24 Destination:203.0.113.10
      Protocol:TCP Destination Port:22
DENY  Source:その他 Destination:203.0.113.10
      Protocol:TCP Destination Port:22

管理端末やVPN接続元に絞ることが考えられます。ただしIP制限だけで十分な認証にはならず、公開鍵認証などを組み合わせます。

13-3. ポート番号を変更すれば安全になるか

SSHを22から2222に変更しても、スキャンで発見され得ます。ポート番号変更は認証強化や脆弱性対策の代わりにはなりません。

13-4. 最小権限の通信制御

必要な送信元、宛先、プロトコル、ポートだけを許可します。DNS問い合わせが必要だからといって、すべての外部宛てポートを無条件に許可する必要はありません。

13-5. IPv4とIPv6の両方を確認する

IPv4でSSHを制限していてもIPv6側で同じ制御がなければIPv6経由で到達される可能性があります。両方の公開状態を確認します。

14. 通信ログとソケット状態の読み取り

14-1. 正常なHTTPS接続

2026-10-12 10:00:01
Source IP   : 192.0.2.100
Source Port : 53124
Destination IP   : 203.0.113.10
Destination Port : 443
Protocol : TCP
Action   : ALLOW

分かるのはこの通信がFWで許可されたことです。ALLOWだけでTCP接続確立やHTTPS成功までは分かりません。SYN+ACK、ACK、サーバログなどを確認します。

14-2. サーバが待ち受けていない場合

Client → Server  TCP SYN   Destination Port:443
Server → Client  TCP RST

サーバが待ち受けていない可能性がありますが、FWなどがRSTを返すこともあり、送信元を確認します。

14-3. ファイアウォールで遮断された場合

2026-10-12 10:05:00
Source      : 192.0.2.100:53124
Destination : 203.0.113.10:443
Protocol    : TCP
Action      : DENY

送信元・宛先IP、TCP/UDPの取り違え、宛先ポート、方向、ルールへの一致を確認します。

14-4. TCPとUDPの取り違え

Rule 10：ALLOW TCP 53
Rule 20：DENY  UDP 53

DNSクライアントのUDP 53問い合わせはRule 10では許可されません。TCPとUDPは別だからです。

14-5. ソケット状態の例

Proto  Local Address       Foreign Address       State
tcp    0.0.0.0:22          0.0.0.0:0             LISTEN
tcp    203.0.113.10:443    192.0.2.100:53124    ESTABLISHED
tcp    203.0.113.10:443    192.0.2.101:53125    ESTABLISHED
udp    0.0.0.0:53          0.0.0.0:0

TCP 22は待受け、TCP 443は二つの接続確立、UDP 53は受信ソケットが存在します。表示は模式例で、OSやコマンドで異なります。

14-6. ポートスキャンを疑うログ

10:10:01  198.51.100.20 → 203.0.113.10:21  TCP SYN
10:10:01  198.51.100.20 → 203.0.113.10:22  TCP SYN
10:10:01  198.51.100.20 → 203.0.113.10:23  TCP SYN
10:10:01  198.51.100.20 → 203.0.113.10:25  TCP SYN
10:10:01  198.51.100.20 → 203.0.113.10:80  TCP SYN
10:10:01  198.51.100.20 → 203.0.113.10:443 TCP SYN

同じ送信元から多数ポートへの短時間のSYNはスキャンの可能性があります。ただし正当な診断・監視の可能性もあるため、送信元、時刻、診断作業の有無、頻度を照合します。

16. 科目Bの答案作成ポイント

16-1. 設問例①：同じポートへの複数接続

設問：複数のクライアントが同じWebサーバのTCP 443番ポートへ同時に接続できる理由を説明せよ。

答案例：「TCPコネクションは送信元・宛先のIPアドレスとポート番号の組合せで識別され、クライアントごとに異なる接続として管理できるため。」

解説：「サーバが高性能だから」ではなく、通信の識別情報を示します。

16-2. 設問例②：TCPとUDPの取り違え

設問：FWでTCP 53を許可したが、DNSクライアントのUDP 53問い合わせが失敗した。原因を説明せよ。

答案例：「TCPとUDPは別のプロトコルとして制御されるため、TCP 53を許可してもUDP 53の通信は許可されないため。」

16-3. 設問例③：NAPTログの必要性

設問：複数の内部端末がNAPTで一つのグローバルIPから通信している。不正アクセス報告時にポート番号と時刻を含む変換ログが必要な理由を説明せよ。

答案例：「複数の内部端末が同じグローバルIPアドレスを共有するため、通信時刻と変換後のポート番号を内部IPアドレス・ポート番号に対応付け、送信元端末を特定する必要があるため。」

16-4. 設問例④：サービスは起動しているのに接続できない

設問：WebサーバでTCP 443の待受けが確認できるが外部から接続できない。調査点を二つ挙げよ。

答案例：「ファイアウォールで外部からのTCP 443が許可されているか、Webサーバが外部から到達可能なIPアドレスで待ち受けているかを確認する。」

解説：待受けとネットワーク到達性は別です。

16-5. 設問例⑤：ポートスキャンの判定

設問：同じ送信元からサーバの多数のTCPポートへ短時間にSYNが送られた。行為と追加確認事項を説明せよ。

答案例：「利用可能なサービスを探索するポートスキャンの可能性があるため、送信元、通信頻度、許可された脆弱性診断の実施有無などを確認する。」

16-6. 設問例⑥：SSHのポート番号変更

設問：SSHを22から2222へ変更するだけでは十分な対策でない理由を説明せよ。

答案例：「ポートスキャンによって変更後の待受けポートを発見される可能性があり、認証の強化や接続元の制限、脆弱性対策の代わりにはならないため。」

16-7. 設問例⑦：戻り通信のポート番号

設問：クライアント 192.0.2.100:53124 がサーバ 203.0.113.10:443 にTCP接続した。応答の送信元ポートと宛先ポートを答えよ。

答案例：「送信元ポートは443、宛先ポートは53124。」

解説：要求と応答では送信元・宛先が入れ替わります。

16-8. 科目Bの答案を作る手順

  1. 通信元と通信先を確認する。 どの端末からどのサーバへ送っているか。
  2. プロトコルを確認する。 TCPかUDPか。
  3. 送信元・宛先ポートを確認する。 要求と応答で入れ替わるか。
  4. 通信状態を確認する。 待受け、確立、拒否、タイムアウトなど。
  5. 制御点を確認する。 サーバ、FW、NAPT、ルーティングのどこか。
  6. 原因と対策を対応させる。 UDP 53拒否なら必要なUDP通信の許可を検討する。

17. 重要事項の整理

第一に、IPアドレスとポート番号は役割が異なります。 IPアドレスは通信先ホストなど、ポート番号はサービス・通信端点を識別します。

第二に、TCPとUDPは別々のポート番号空間を持ちます。 TCP 53とUDP 53は別の通信です。

第三に、ポート番号は16ビットです。 Well-Known、Registered、Dynamic/Privateの区分と主要サービスの標準ポートを覚えます。

第四に、ソケットはアプリケーションが通信を行うための端点です。 TCPでは待受けソケットと接続済みソケットを区別します。

第五に、一つのサーバポートで複数のTCPコネクションを扱えます。 送信元・宛先IPとポートの組合せで接続を識別します。

第六に、NAPTではポート番号が重要です。 一つのグローバルIPを共有する内部端末の通信をポート変換・管理で区別します。

第七に、FWではポートだけでなくプロトコル、方向、通信状態を確認します。 TCP 443を許可してもUDP 443は許可されません。

第八に、ポートスキャンはサービス探索に使われます。 正当な診断にも使われるため、ログだけで侵入成功とは断定しません。

C：発展学習として切り分ける内容

  • SO_REUSEADDR、SO_REUSEPORT などのソケットオプションの細部
  • OSカーネル内部のソケット管理構造
  • 複数プロセスによる待受けの高度な設計
  • ソケットプログラミングの詳細なコード実装
  • 特殊なNAT越え・ポート割当てアルゴリズム

最優先は、通信の5タプルを読み取り、ポート番号・ソケット・FW・NAPTの関係から、通信障害や不審なアクセスの原因を説明できることです。
