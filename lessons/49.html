第49講｜デジタル証明書

A：必須中心／講義本文のみ（確認問題・採点結果を除く）

第49講｜デジタル証明書

0. 到達目標・出典・優先度

到達目標：X.509公開鍵証明書の各項目を読み、CSR・発行・配布・更新の流れを追い、サーバ証明書とクライアント証明書の違い、署名・名前・用途・有効期間・失効の検証、秘密鍵漏えい時の対処を科目A/Bで判断できる。

参考書の確認箇所：『徹底攻略 情報処理安全確保支援士教科書 令和7年度版』第4章4-2「認証」、印刷p.275〜278（「PKIの仕組み」「デジタル証明書」「デジタル証明書の作成と検証の流れ」「CRL・VA・OCSP」）。p.276〜277の図では、公開鍵・主体・発行者・有効期限・シリアル番号・CA署名と検証を説明する。ここから先のSAN、EKU、CSRの詳細、TLSログ例、mTLSの判断は講師独自の補足。参考書の記述を長文転載せず再説明する。

学習配分：A必須75%、B理解補助20%、C発展5%。前講のPKIは「信頼の制度と仕組み」、本講は「証明書というデータをどう読み、どう使うか」が中心。

1. なぜ証明書が必要か【A】

Webブラウザが https://shop.example.test に接続するとき、サーバが「私の公開鍵はこれです」と渡すだけでは、その鍵が本物の店舗のものか判断できない。攻撃者が途中で自分の公開鍵を渡すこともできるからである。

そこで、公開鍵と対象の名前などを一つのデータにまとめ、認証局（CA）が電子署名したデジタル証明書（公開鍵証明書）を使う。署名を検証すれば「信頼するCAがこの内容を発行したこと」「発行後に署名対象が改ざんされていないこと」を確かめられる。ただしCAの署名だけで接続先名や現在の有効性まで保証されるわけではない。別途、名前・期間・用途・信頼連鎖・失効などの検証が必要である。

証明書に入る公開鍵は公開してよい。対応する秘密鍵は証明書に含まれず、所有者側が守る。サーバが証明書を提示しただけでは秘密鍵を持つ証拠として十分ではないため、TLSのハンドシェイクでは通常、秘密鍵を用いた署名などで所有を示す。

2. X.509証明書の読み方【A】

X.509は公開鍵証明書の代表的な規格。実際の証明書には以下の情報がある。ここでは説明用の架空の証明書を使う。

Version: 3
Serial Number: 04:2A:91
Signature Algorithm: sha256WithRSAEncryption
Issuer: CN=Example Intermediate CA, O=Example CA
Validity:
  Not Before: 2026-11-01 00:00:00 UTC
  Not After : 2027-01-30 23:59:59 UTC
Subject: CN=shop.example.test, O=Example Shop
Subject Public Key Info: RSA Public Key (2048 bit)
X509v3 Subject Alternative Name:
  DNS:shop.example.test
X509v3 Basic Constraints: CA:FALSE
X509v3 Key Usage: Digital Signature
X509v3 Extended Key Usage: TLS Web Server Authentication
Signature Value: (CAが作成した署名データ)

Subject（主体）：誰の証明書か。Issuer（発行者）：誰が発行したか。Serial Number（シリアル番号）：発行者が証明書を識別する番号。失効情報との照合などに使う。Validity（有効期間）：Not BeforeからNot Afterまで。Subject Public Key Info：証明される公開鍵とアルゴリズム。Signature Algorithm / Signature Value：CAが用いた署名方式と署名値。

SAN（Subject Alternative Name、サブジェクト代替名）は、Webサーバのホスト名を確認する重要な拡張領域。現在の一般的なTLSのDNS名照合では、SubjectのCNだけを頼りにせず、SANに対象名があるか確認する。例えば shop.example.test 用の証明書で pay.example.test に接続すると、署名が正しくても名前不一致となる。

Basic Constraints: CA:FALSEは、その証明書をCAとして下位証明書の発行に使うものではないことを示す。Key Usageは鍵の利用目的の制限、Extended Key Usage（EKU）はTLSサーバ認証・クライアント認証など用途を表す。証明書は署名が正しいだけでどの用途にも使えるわけではない。

注意：例のRSA 2048 bitや有効期間は説明用の設定値であり、すべての証明書の必須値ではない。

3. 申請から配布まで：CSRと秘密鍵の所在【A】

登場人物は、サイト管理者X、認証局CA、利用者のブラウザB。

  1. 鍵ペア作成：Xがサーバ用公開鍵と秘密鍵を作る。秘密鍵はXが安全に保管する。外部CAに秘密鍵を送る必要は通常ない。
  2. CSR作成：Xは公開鍵、申請する名前などを含むCSR（Certificate Signing Request、証明書署名要求）を作成し、通常は対応する秘密鍵でCSRに署名する。CSRは「証明書を発行してほしい」という申請であり、CA発行済み証明書ではない。
  3. 申請内容の確認：CA側でドメイン管理権限など、発行する証明書の種類に応じた確認を行う。CSRに名前が書かれているだけで所有者だと信用するわけではない。
  4. 証明書発行：CAが公開鍵・主体・有効期間・用途などを含む証明書を作り、CA側の秘密鍵で署名する。
  5. サーバ設定：Xはサーバ証明書と対応する秘密鍵をサーバへ設定し、必要な中間CA証明書も配布する。
  6. 接続と検証：Bは証明書とチェーンを受け取り、署名・名前・期間・用途・失効等を検証する。さらにTLSでサーバが証明書に対応する秘密鍵を持つことを確認する。

混同しやすい鍵：CSRの署名に使うのは通常申請者の秘密鍵。発行済み証明書に署名するのはCAの秘密鍵。証明書のCA署名を検証するのはCAの公開鍵。TLS接続でサーバが鍵を所有することを示すのはサーバの秘密鍵。これらは役割が違う。

4. 証明書検証は「一つのチェック」ではない【A】

ブラウザBが shop.example.test にアクセスする場合、概念上、次を分けて考える。

検証確認すること失敗例
署名・チェーン中間CAを経由し信頼済みルートへつながるか中間CA証明書不足、未信頼CA
名前SANのDNS名が接続先と一致するか別ホスト名の証明書
期間現在時刻が有効期間内か期限切れ、端末時刻誤り
用途・制約TLSサーバ認証用か、CA制約は正しいかクライアント用途のみ
失効失効済みと判明していないか秘密鍵漏えいで失効
秘密鍵の所持相手が対応する秘密鍵を使えるか証明書だけ盗んで秘密鍵がない

たとえば「中間CAまで署名が正しい」のにSANが別名なら、接続先の本人性は確認できない。逆に「SANは正しい」のに未知のCAが発行していれば、名前を自称しているだけかもしれない。検証のどこか一つが通っただけで安全とはしない。

失効は前講のCRL（失効証明書の一覧）とOCSP（証明書状態の照会）で学んだ。期限内でも漏えい等で失効し得る。ただし、実際の失効確認の方式や通信失敗時の扱いはクライアントの実装・ポリシーによって異なる。

5. サーバ証明書とクライアント証明書【A】

サーバ証明書はブラウザ等が接続先サーバの正当性を確認するために使う。HTTPSで一般的に用いられる。

クライアント証明書はサーバが接続元クライアントの公開鍵・身元などを確認するために使う。例えば会社の管理端末にクライアント証明書を配り、業務システムへの接続を許可する。

mTLS（mutual TLS、相互TLS認証）ではサーバだけでなくクライアントも証明書を提示し、サーバがクライアント証明書を検証する。クライアント側はサーバ証明書を検証し、サーバ側はクライアント証明書を検証する。サーバはさらにクライアントが対応する秘密鍵を持つことを確認する。

ただし証明書の有効性と業務上の権限は別。有効なクライアント証明書を持っていても、その利用者が管理者権限を持つとは限らない。証明書の主体とアカウントの対応付け、権限確認、失効・端末紛失時の停止手順が必要になる。

6. 秘密鍵漏えい・誤発行・更新ミス【A】

秘密鍵漏えい：攻撃者がサーバ秘密鍵を得ると、条件次第でサーバになりすます危険がある。秘密鍵を保護領域や適切なアクセス制御下で管理し、漏えい時は証明書を失効し新しい鍵ペアと証明書へ交換する。証明書だけ再発行して漏えい済みの秘密鍵を再利用するのは不適切。

誤発行：ドメイン管理権限の確認が不十分だと、攻撃者に正しい名前を含む証明書が発行され得る。発行審査の適正化、証明書透明性（CT）ログ等の監視が補助策になる。ただしCTは証明書の不正使用を自動で防止するものではない。

更新ミス：更新した証明書とサーバ秘密鍵が対応しない、SANが不足する、中間CA証明書を設定し忘れる、有効期限を超える、などが起こる。更新前に対象名・鍵の対応・チェーンを確認し、更新後に実際の接続先から検証する。検証無効化は根本対策にならない。

7. ログとコマンドを読む【A/B】

以下は架空のログ。観測した事実と推測を分ける。

11:00 host=shop.example.test verify=FAIL reason=HOSTNAME_MISMATCH
11:04 host=shop.example.test verify=FAIL reason=UNTRUSTED_ROOT
11:08 host=shop.example.test verify=FAIL reason=EXPIRED
11:12 host=shop.example.test verify=FAIL reason=KEY_MISMATCH

11:00はSANと接続先名を調査。11:04は発行者・中間証明書・信頼ストアを調査。11:08は有効期間と端末時刻を調査。11:12は証明書に含まれる公開鍵と、サーバが使用する秘密鍵の対応を調査する。このログだけでは攻撃か運用ミスかは断定できない。

管理者が証明書の中身を見るときの例（OpenSSL、実行例であり操作を要求しない）：

openssl x509 -in server.crt -noout -text

このコマンドは証明書の表示であり、秘密鍵を復号・公開する操作ではない。出力の Issuer、Subject、Validity、Subject Alternative Name、Key Usage、Extended Key Usage を読み、想定の接続先と用途に合うか確認する。コマンドだけではチェーン全体の信頼性や失効状態まで自動で完全検証したことにはならない。

8. 科目Aと科目Bの答案作成【A】

科目A：公開鍵証明書と秘密鍵の所在、CSRと証明書、SubjectとIssuer、SANとCN、CA署名とTLSでの鍵所持確認、サーバ証明書とクライアント証明書、期限と失効の違い。

科目B例題：「新しいサーバ証明書を適用した直後から、pay.example.test へのHTTPS接続だけ名前不一致エラーとなった。証明書のSANには shop.example.test しか記載されていない。原因と対策を説明せよ。」

事実：証明書のSANは shop.example.test のみ。接続先は pay.example.test。原因：署名が正しくても、証明書に接続先の名前が含まれず、サーバの本人性を確認できない。影響：クライアントは安全な接続として受け入れられない。対策：pay.example.test をSANに含む適切な証明書を発行・設定し、接続先で検証する。

答案例：「証明書のSANに接続先 pay.example.test がなく、ホスト名検証に失敗するため。接続先名をSANに含む証明書を発行してサーバに設定する。」

別ケース：「サーバ証明書は有効だが、mTLSでクライアント認証が失敗」なら、クライアント証明書の有無、用途、信頼先、失効、対応する秘密鍵の所持、アカウントへの対応付けを調べる。サーバ証明書の更新だけでは解決しない。

9. 重要事項と発展の切り分け

A必須：証明書は公開鍵と主体等をCAが署名したもの。秘密鍵は含まれない。SAN・有効期間・用途・チェーン・失効を区別して検証する。CSRと発行済み証明書は違う。秘密鍵漏えい時は鍵を交換し証明書を失効する。

B理解補助：mTLSでのクライアント証明書と認可の違い、OpenSSLの表示項目、更新運用のチェック。

C発展・任意：ASN.1/DER内部符号化、証明書ポリシーOID、CTログ監視の細部。科目A/Bの基礎問題を解くために内部バイト列の暗記は不要。
