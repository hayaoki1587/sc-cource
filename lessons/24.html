第1節｜到達目標と学習優先度

本講の到達目標は、HTTPリクエスト・レスポンスの構造を読めること、GET・POSTとステータスコードを区別できること、CookieとセッションIDの関係を説明できること、HTTPSで守れる範囲と守れない範囲を判断できること、HTTPヘッダーやログから原因・対策を科目Bの答案として書けることである。

参考書：『徹底攻略 情報処理安全確保支援士教科書 令和7年度版』第3章3-3「アプリケーションプロトコル」3-3-1「Webのプロトコル」pp.205〜211（先の講義で提示された対応箇所。今回、ページを再照合した記録はない）。HTTPヘッダーのセキュリティについては第6章6-2-1「Webセキュリティ」pp.402〜405も先の講義で対応箇所として提示された。TLSの仕組みや現代のCookie属性に関する細部は講師補足として扱う。

第2節｜HTTPは何をするプロトコルなのか【A】

HTTP（Hypertext Transfer Protocol）は、WebブラウザなどのクライアントとWebサーバの間で、情報の要求と応答を行うアプリケーション層プロトコルである。例えばブラウザが https://shop.example.jp/products を開くと、サーバに「商品の一覧ページを取得したい」と要求し、サーバはHTMLなどを返す。

ブラウザ
① HTTPリクエスト →
← ② HTTPレスポンス
Webサーバ

HTTPはデータのやり取りのルールであり、暗号化そのものを提供するわけではない。通常のHTTPは暗号化されず、HTTPSではHTTPメッセージをTLSで保護する。

TCP・IP・DNSとの関係

DNSはサーバ名から接続先IPアドレスを調べる。IPはパケットを転送し、TCPは順序どおりにデータを届ける。HTTPは何を要求し何を返すかを決め、TLSは暗号化と認証などを担う。HTTP/1.1やHTTP/2のHTTPS通信では一般にHTTP→TLS→TCP→IPという関係になる。ただしHTTP/3はUDP上のQUICを利用するため、HTTPSが必ずTCPを使うわけではない。

第3節｜HTTPリクエストの構造【A】

HTTP/1.1のリクエストは、先頭のリクエストライン、続くヘッダー、空行、必要に応じてメッセージボディから構成される。

GET /products HTTP/1.1
Host: shop.example.jp
User-Agent: ExampleBrowser/1.0
Accept: text/html
Cookie: sessionid=abc123
要素意味
GETHTTPメソッド：何をしたいか
/products要求対象のパス
HTTP/1.1HTTPのバージョン
Host要求先ホスト名
User-Agentクライアントの情報
Accept受け入れ可能な形式
Cookieブラウザが送信するCookie

GETとPOSTの違い

GETは主に情報取得に使う。次の例では検索語がURLのクエリ文字列に含まれる。

GET /search?q=security HTTP/1.1
Host: example.jp

POSTは主にサーバにデータを送信して登録や処理を依頼するときに使う。ボディにデータを含めることができる。

POST /login HTTP/1.1
Host: example.jp
Content-Type: application/x-www-form-urlencoded
Content-Length: 28

username=alice&password=demo

POSTだから安全、ではない。 HTTPのままならPOSTのボディも通信経路上で盗聴され得る。GETは本来状態を変更しない安全なメソッドとして設計されるため、削除や送金をGETだけで実行できるようにするのは危険である。

その他のメソッド

メソッド典型的な用途
HEADレスポンスヘッダーのみ取得
PUT対象リソースの作成・置換
DELETE対象リソースの削除
CONNECTプロキシを通じたトンネル確立

メソッド名だけで操作権限が決まるわけではなく、サーバ側で認証・認可が必要である。

第4節｜HTTPレスポンスの構造【A】

サーバの応答はステータスライン、ヘッダー、空行、必要に応じたボディで構成される。

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Cache-Control: no-store
Set-Cookie: sessionid=abc123; Secure; HttpOnly; SameSite=Lax

<html>...</html>

200 OK は要求の成功を示す。Content-Type はデータ形式、Cache-Control はキャッシュ、Set-Cookie はブラウザへのCookie保存指示に使う。

分類意味例
1xx処理途中の情報100 Continue
2xx成功200 OK、201 Created
3xxリダイレクト等301、302、304
4xx要求に関する問題400、401、403、404
5xxサーバ側の問題500、503

401は有効な認証情報が必要、または認証が成立していない状態。403はサーバが要求を理解したがアクセスを拒否する状態。安全上の理由で意図的に404を返す実装もあるため、コードだけで内部状態を断定しない。

第5節｜HTTPのステートレス性とセッション管理【A】

HTTPは個々の要求を独立して扱うステートレスなプロトコルである。しかしネット通販ではログイン→カート投入→注文確認→購入という別々の要求を同じ利用者の操作として扱う必要がある。そこでCookieとセッション管理を使う。

Cookieはブラウザに保存され、条件に応じて後続の要求に付けて送信されるデータ。セッションIDは、サーバ側で管理するログイン状態とリクエストを結び付ける識別子である。

  1. ブラウザがID・パスワードを送信する。
  2. サーバが認証し、推測困難なセッションIDを発行する。
  3. サーバがSet-CookieでセッションIDをブラウザへ送る。
  4. ブラウザは以後の要求にCookieを付ける。
  5. サーバはIDをセッション情報と照合し、ログイン状態を確認する。
Set-Cookie: sessionid=RANDOM_VALUE; Secure; HttpOnly; SameSite=Lax; Path=/
GET /mypage HTTP/1.1
Host: shop.example.jp
Cookie: sessionid=RANDOM_VALUE

重要なのは、セッションIDを知る第三者が本人になりすませる可能性があること。パスワードを知らなくても、有効なIDだけでログイン済み操作を悪用できる実装はある。

第6節｜Cookieのセキュリティ属性【A】

属性役割
SecureHTTPS通信の場合にCookieを送信する
HttpOnlyJavaScriptのdocument.cookieなどからの参照を禁止する
SameSiteクロスサイトの要求におけるCookie送信を制限する
Domain送信対象ドメインの範囲を指定
Path送信対象URLパスの範囲を指定
Max-Age / Expires有効期間を指定

HttpOnlyはXSSで実行されたJavaScriptからCookie値を直接読み取ることを防ぎやすくするが、XSS自体は防げず、悪意あるスクリプトが利用者の権限で操作する危険は残る。SameSiteはCSRF軽減に役立つが、すべての状況で十分とは限らず、CSRFトークンやOrigin検証も検討する。

第7節｜セッションハイジャック【A】

攻撃者が有効なセッションIDを入手し、正規利用者になりすます攻撃。次のような要求を送ると、サーバがIDだけで識別している場合は利用者の要求として処理され得る。

GET /account HTTP/1.1
Host: shop.example.jp
Cookie: sessionid=STOLEN_SESSION_ID

主な対策は、HTTPSによる通信保護、Secure属性、推測困難なID、セッションの有効期限と失効管理など。盗聴を防ぐ対策とIDの不正利用を抑制する対策を区別する。

第8節｜セッション固定攻撃とCSRF【A】

セッション固定攻撃

  1. 攻撃者がセッションID「XYZ」を入手または用意する。
  2. 利用者にそのIDを使わせる。
  3. 利用者がログインする。
  4. サーバがログイン前後で同じIDを使い続ける。
  5. 攻撃者がXYZで認証済みセッションを利用する。

対策：認証成功時にセッションIDを再生成し、旧IDを無効化する。

CSRFとの違い

CSRFは、攻撃者が利用者のブラウザを利用して本人の意図しないリクエストを送信させる攻撃。セッションIDを直接知る必要はない。

攻撃悪用するもの対策
ハイジャック盗まれた有効なIDID保護・失効管理
固定攻撃ログイン前から攻撃者が知るID認証時のID再生成
CSRFブラウザが自動送信する認証情報CSRFトークン、Origin検証、SameSite

第9節｜HTTPSとTLSの仕組み【A】

HTTPSはHTTPをTLS（Transport Layer Security）で保護する。TLSの主な役割は、機密性（盗聴されにくくする）、完全性（改ざん検出）、認証（証明書などで接続先サーバを確認する）の三つ。

  1. DNSで接続先IPアドレスを調べる。
  2. HTTP/1.1やHTTP/2ではTCP接続を確立する。
  3. TLSハンドシェイクを開始し暗号方式や鍵交換情報をやり取りする。
  4. サーバ証明書を検証する。
  5. 双方が暗号鍵を導出する。
  6. 暗号化・完全性保護されたHTTPメッセージを交換する。

典型的なTLS 1.3ではECDHEなどの鍵交換から共有秘密を確立し、対称鍵を導出する。サーバ証明書の公開鍵でHTTP本文全体を暗号化しているわけではない。

証明書の検証

信頼できる認証局への証明書チェーン、有効期間、アクセス先ホスト名との一致、署名の正しさ、適用される失効確認ポリシーを確認する。shop.example.jpへのアクセスに無関係な名前の証明書が返る場合は問題となる。警告を無視すると中間者攻撃の危険が高まる。

第10節｜HTTPSでも防げない攻撃【A】

脅威HTTPSで防げるか
通信経路でのHTTP本文の盗聴適切なTLS接続なら防げる
通信経路でのHTTP本文の改ざん適切なTLS接続なら検出できる
SQLインジェクション防げない
XSS防げない
正規サーバから配信される悪意あるJavaScript防げない
サーバ内部からの情報漏えい防げない

HTTPSは主に通信経路を保護する。Webアプリケーションが利用者入力を適切に出力エスケープせずHTMLに埋め込む問題は別であり、HTTPSを使用してもXSSが成立し得る。

第11節｜HTTPヘッダーを利用した防御【A】

ヘッダー役割
Strict-Transport-SecurityHSTS：対応ブラウザにHTTPS接続を強制
Content-Security-PolicyCSP：スクリプトなどの読み込み・実行元を制限
X-Content-Type-Options: nosniffMIMEタイプ推測を制限
X-Frame-Optionsフレーム内表示を制御
Cache-Control: no-storeキャッシュへの保存を抑制

HSTS

Strict-Transport-Security: max-age=31536000; includeSubDomains

指定期間はHTTPSで接続するよう対応ブラウザに指示する。初回アクセスではまだHSTSを受信していない場合があり、プリロード登録で初回から強制できる。

CSP

Content-Security-Policy: default-src 'self'; script-src 'self'

この例は原則として同一オリジンのリソースを使い、スクリプトも同一オリジンに限定する。CSPはXSS被害を軽減するが、適切な出力エスケープなどに代わるものではない。

第12節｜TLS終端とリバースプロキシ【A・B】

実務ではブラウザとリバースプロキシ間をHTTPSにし、プロキシからアプリケーションサーバ間をHTTPで通信する構成がある。

ブラウザ
   │ HTTPS
   ▼
リバースプロキシ
   │ HTTP（暗号化なし）
   ▼
アプリケーションサーバ

外部通信がHTTPSでも、内部区間が暗号化されているとは限らない。内部ネットワークだから必ず安全とは限らず、要件に応じてバックエンドもTLSで保護する。

第13節｜HTTPログと設定の読み方【A】

10:15:01 192.0.2.10 GET  /login   200
10:15:09 192.0.2.10 POST /login   302
10:15:10 192.0.2.10 GET  /mypage  200
10:17:42 198.51.100.8 GET /mypage 200

最後の行では別IPからマイページへのアクセスが成功しているが、これだけでセッションハイジャックと断定できない。回線変更や別利用者の正常なアクセスもあり得る。セッションIDに対応する内部識別子、認証ユーザー、User-Agent、アクセス時刻、セッション発行・失効記録を照合する。セッションIDそのものをログへ平文記録することは避ける。

Cookie設定の評価

Set-Cookie: sessionid=abc123; Path=/

Secure・HttpOnly・SameSiteが明示されていない。非HTTPSでの送信、JavaScriptからの参照、クロスサイト送信の制御を検討する。SameSite省略時の実際の動作はブラウザによって異なる。

Set-Cookie: __Host-sessionid=RANDOM_VALUE; Path=/; Secure; HttpOnly; SameSite=Lax

__Host-接頭辞にはSecure、Path=/、Domain省略などの条件がある。

第15節｜科目Bの答案作成【A】

「セキュリティを強化する」だけでは不十分。問題文の具体的な事実から、原因→脅威→対策を結び付ける。

例：ログイン後も同じセッションIDを使用

原因：認証前後でセッションIDが変更されない。脅威：攻撃者が事前に把握したIDで認証後のセッションを利用できる。対策：認証成功時にIDを再生成し旧IDを無効化する。

例：CookieにSecure属性がない

原因：非HTTPS通信でセッションCookieが送信され得る。脅威：通信経路上でIDを盗聴される。対策：HTTPSを使用し、CookieにSecure属性を設定する。

例：HTTPSでもXSSが成立

理由：HTTPSは通信経路を保護するが、Webアプリケーションの不適切な出力処理を修正しない。対策：出力文脈に応じたエスケープなどを行う。

第16節｜重要事項と発展学習の切り分け

  • HTTPは要求と応答を交換するアプリケーション層プロトコル。
  • HTTPはステートレスであり、Cookieとセッションでログイン状態などを管理する。
  • セッションIDの漏えいはなりすましにつながる。
  • Secure・HttpOnly・SameSiteは異なる脅威に対処する。
  • HTTPSはTLSによって機密性・完全性・サーバ認証を提供する。
  • HTTPSだけではXSSやSQLインジェクションを防げない。
  • HTTPヘッダー・ログから根拠と対策を導く力が科目Bで重要。

C：任意の発展学習：HTTP/2のHPACK、HTTP/3のQPACK、QUICの輻輳制御、TLS 1.3の鍵スケジュール詳細。今回は試験の基本判断を優先し、深掘りしない。
