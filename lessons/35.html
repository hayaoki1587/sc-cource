1. 到達目標と参考書

第34講ではAESなどの共通鍵暗号を学びました。共通鍵暗号は大量のデータを高速に暗号化できますが、通信相手と秘密の鍵をどうやって安全に共有するかという課題があります。公開鍵暗号はこの問題を解決するための重要な技術です。HTTPSのサーバ認証や電子署名にも関係します。

到達目標は、①公開鍵と秘密鍵の役割を区別する、②暗号化と電子署名で使う鍵を説明する、③RSA・DH・ECDHE・ECDSAの用途を区別する、④公開鍵すり替えと証明書の必要性を理解する、⑤科目Bで鍵共有・認証・暗号化の関係を説明することです。

2. 公開鍵暗号の基本的な仕組み【A】

共通鍵暗号では送信者と受信者が同じ鍵を使いました。公開鍵暗号では数学的に対応する2つの鍵を使います。

  • 公開鍵（Public Key）：他人に配布してよい鍵
  • 秘密鍵（Private Key）：所有者だけが秘密に保管する鍵

この2つを合わせて鍵ペア（キーペア）と呼びます。例えばBさんが公開鍵と秘密鍵を生成し、公開鍵はAさんに渡しますが、秘密鍵は渡しません。

公開鍵を知っていても対応する秘密鍵を現実的な時間で求めることが困難になるよう設計されています。ただし、公開鍵を配布できることと、その公開鍵が本当にBさんのものであることは別問題です。

3. 暗号化：誰の公開鍵を使うのか【A】

AさんがBさんだけに読める秘密のメッセージを送りたい場合、使うのはBさんの公開鍵です。

  1. Bさんが公開鍵と秘密鍵を生成する。
  2. Bさんが公開鍵をAさんに渡す。
  3. AさんがBさんの公開鍵でメッセージを暗号化する。
  4. Aさんが暗号文をBさんに送る。
  5. Bさんが自分の秘密鍵で復号する。

第三者がBさんの公開鍵を入手しても、通常、それだけでは暗号文を復号できません。暗号化に使う公開鍵は送信者Aではなく、受信者Bのものです。

4. 電子署名：暗号化とは鍵の使い方が違う【A】

AさんがBさんに文書を送り、「本当にAさんが署名した文書か」を確認したい場合、Aさんの秘密鍵で署名を生成し、Aさんの公開鍵で検証します。

実際の電子署名では文書のハッシュ値を計算し、署名アルゴリズムで署名を生成・検証します。単純に「文書全体を秘密鍵で暗号化する」処理とは異なり、ECDSAなどは暗号化・復号の逆操作として説明できません。電子署名は署名者の確認と完全性の検証が目的であり、電子署名だけでは文書の内容は秘密になりません。

目的使用する鍵
Bさんだけが読めるよう暗号化Bさんの公開鍵
暗号文を復号Bさんの秘密鍵
Aさんが署名を生成Aさんの秘密鍵
Aさんの署名を検証Aさんの公開鍵

第33講の復習です。攻撃者がファイルと単なるハッシュ値を両方書き換えられる場合、ハッシュ照合だけでは配布元の正当性を確認できません。信頼できる公開鍵で電子署名を検証すれば、対応する秘密鍵を持たない攻撃者による改ざんを検知できます。ただし、秘密鍵の漏えいや検証用公開鍵自体のすり替えには別の対策が必要です。

5. RSA・DH・DSA・ECCの違い【A】

公開鍵暗号に関連するアルゴリズムは、すべて同じ用途ではありません。

技術主な役割
RSA公開鍵暗号化・電子署名
DH（Diffie-Hellman）鍵共有
DSA電子署名
ECC（楕円曲線暗号）公開鍵暗号技術の一群
ECDH楕円曲線を使った鍵共有
ECDHE一時的な鍵を使うECDH
ECDSA楕円曲線を使った電子署名

RSA

RSAは大きな整数の素因数分解の難しさを利用する方式です。受信者向けの暗号化では受信者の公開鍵で暗号化し、秘密鍵で復号します。電子署名にも利用できます。参考書p.265では鍵長2048ビット以上が推奨されることが説明されています。RSAの2048ビットとAESの256ビットは同じ安全性を意味する数字ではありません。

DH鍵共有

DHは事前に共通の秘密鍵を共有していない2者が、通信を通じて共通の秘密情報を確立する方式です。ただしDHそのものは相手を認証しません。認証のないDHは中間者攻撃を受ける可能性があります。

ECDHE

ECDHEは楕円曲線を利用し、一時的な鍵を使って鍵共有を行います。TLS 1.3の鍵共有でも利用される技術です。

6. Forward Secrecyとは何か【A】

攻撃者が企業のHTTPS通信を記録しておき、数年後にWebサーバの長期秘密鍵を盗み出した場合、過去に記録した通信まで解読できるのでしょうか。

Forward Secrecy（前方秘匿性）は、長期秘密鍵が後から漏えいしても、それだけでは過去の通信を解読できない性質です。

ECDHEなどを適切に使用し、一時的な秘密情報が消去されていれば、サーバの長期秘密鍵が後から漏えいしてもそれだけでは過去の通信を復号できません。ただし、通信中に端末が侵害された場合や、セッション鍵が別途漏えいした場合まで防げるわけではありません。

7. 公開鍵のすり替えと中間者攻撃【A】

公開鍵を入手しただけでは、その所有者が正しいか分かりません。AさんがBさんの公開鍵を取得する際、攻撃者Mが自分の公開鍵にすり替えたとします。

  1. AさんがBさんの公開鍵を取得しようとする。
  2. Mが自分の公開鍵をBさんの公開鍵と偽って渡す。
  3. AさんがMの公開鍵でメッセージを暗号化する。
  4. Mが自分の秘密鍵で復号し、内容を読む。
  5. Mが本来のBさんの公開鍵で再暗号化し、Bさんへ転送する。

AさんとBさんは正常に通信できていると思い込む可能性があります。

対策：電子証明書とPKI

PKI（Public Key Infrastructure：公開鍵基盤）は、公開鍵と所有者の対応関係を信頼できる形で確認するための仕組みです。HTTPSでは認証局（CA）が発行するサーバ証明書などを使って接続先サーバの公開鍵の正当性を検証します。署名の検証だけでなく、ホスト名、有効期間、信頼できる認証局につながるかなども確認します。公開鍵の数学的安全性と所有者の認証の両方が必要です。

8. TLSで公開鍵技術をどう使うのか【A】

HTTPSのTLS 1.3を例に、これまでの知識を組み合わせます。

  1. クライアントとサーバがECDHEなどの鍵共有情報を交換する。
  2. サーバ証明書と署名を検証し、通信相手を認証する。
  3. 鍵共有で得た秘密情報などから通信に使う共通鍵を導出する。
  4. AES-GCMなどの認証付き共通鍵暗号でアプリケーションデータを保護する。

TLS 1.3では「サーバのRSA公開鍵で共通鍵を暗号化して送る」という古い説明は当てはまりません。ECDHEなどで共有秘密を確立し、通信鍵を導出します。サーバ証明書に関連する公開鍵は主に認証のために利用されます。HTTPSはTLSが適用された通信区間を保護します。WebサーバとDBサーバの間が別の平文通信なら、そこは別途保護する必要があります。

9. 科目Bでの実務例【A】

次の設定を考えてください。

通信方式          : TLS 1.3
鍵共有方式        : ECDHE
サーバ証明書検証  : 無効
アプリケーション暗号 : AES-GCM

最も問題なのはサーバ証明書の検証が無効なことです。ECDHEで安全に鍵を共有できたとしても、その相手が本物のサーバとは限りません。攻撃者が通信経路に割り込める場合、攻撃者との間で鍵共有を成立させてしまう可能性があります。

サーバ証明書の検証が無効であるため、攻撃者が正規サーバになりすまし、中間者攻撃を行うおそれがある。信頼できる認証局による署名や接続先ホスト名などを検証する設定に変更する。

「TLS 1.3だから安全」「AES-GCMだから安全」と個別の暗号方式だけで判断しないことが大切です。
