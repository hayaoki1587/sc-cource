第22講｜DNS詳細

情報処理安全確保支援士（SC）合格講座｜第1〜23講・詳細再執筆

第21講では、DNSの階層構造、名前解決、DNSレコード、キャッシュ、権威DNSサーバを学びました。今回は、その仕組みを利用する攻撃と防御を詳しく学びます。中心となるのは、DNSキャッシュポイズニング、DNSSEC、DNS Rebinding、サブドメインテイクオーバーです。

これらはすべてDNSに関係する攻撃であっても、攻撃者が操作するものや有効な対策が異なります。例えば、DNSSECを導入していても、組織が正規のDNSゾーンに不要なCNAMEレコードを残していれば、サブドメインテイクオーバーの問題が解消するとは限りません。

1. 到達目標・学習範囲

1-1. 試験上の到達目標

  1. DNSキャッシュポイズニングの成立条件と影響を説明する。
  2. DNSトランザクションIDと送信元ポート番号の役割を説明する。
  3. DNSSECのDNSKEY・RRSIG・DSレコードを区別する。
  4. 親ゾーンから子ゾーンへつながるDNSSECの信頼の連鎖を説明する。
  5. DNS Rebindingの攻撃の流れと防御策を説明する。
  6. サブドメインテイクオーバーとDNSキャッシュポイズニングを区別する。
  7. DNSログや設定例から原因を特定し、科目Bで具体的な対策を記述する。

1-2. 参考資料

基本参考書：『徹底攻略 情報処理安全確保支援士教科書 令和7年度版』。

確認した関連箇所は、第3章「ネットワーク基礎技術」3-3-3「DNSのプロトコル」p.224〜229です。ここで扱われるDNSの階層構造、委任、資源レコード、TTL、権威DNSとキャッシュDNS、ゾーン転送が今回の前提になります。

DNSSECの詳細、DNS Rebinding、サブドメインテイクオーバーの技術的な説明は、今回の講師補足として区別します。これらの詳細について参考書の該当ページを確認できたとは扱いません。

また、令和7年度春期のIPA午後試験・問4の採点講評では、サービス利用終了後のCNAMEレコードの削除漏れがサブドメインテイクオーバーにつながる事例が取り上げられています。この論点は、確認済みのIPA資料に基づいて重点的に扱います。

2. DNSの仕組みをセキュリティの観点から復習する

2-1. 通常の名前解決

利用者が www.example.jp へアクセスするとき、一般的には次の流れになります。

クライアント
    |
    | www.example.jp のAレコードは？
    v
再帰リゾルバ
    |
    | キャッシュになければ問い合わせ
    v
ルートDNS
    |
    | jpの権威DNSを案内
    v
jpの権威DNS
    |
    | example.jpの権威DNSを案内
    v
example.jpの権威DNS
    |
    | www.example.jp = 203.0.113.10
    v
再帰リゾルバ
    |
    | 結果をクライアントへ返す
    v

この構造では、再帰リゾルバがさまざまなDNSサーバから情報を取得します。

2-2. どこを攻撃されると危険なのか

攻撃対象 起こり得る問題
クライアントのhostsファイル 不正なIPアドレスへの誘導
クライアントのDNS設定 攻撃者のDNSサーバを利用させられる
再帰リゾルバのキャッシュ 不正なDNS情報が利用者へ返される
権威DNSのゾーン情報 正式なDNS情報そのものが改ざんされる
DNS委任・CNAME設定 不適切な管理先や残存レコードが悪用される

名前解決結果が誤っているという症状だけでは、どこが攻撃されたか分からないことが重要です。

2-3. DNSSECが解決できる問題とできない問題

DNSSECは、DNSデータの真正性・完全性を検証する仕組みです。しかし、DNSSECはDNS設定の内容が業務上正しいか、参照先サービスが安全かまで判断する仕組みではありません。この違いを理解すると、サブドメインテイクオーバーの設問にも対応できます。

3. DNSキャッシュポイズニング

A：必須

3-1. 攻撃の目的

DNSキャッシュポイズニングは、再帰リゾルバなどのキャッシュに不正なDNS情報を取り込ませる攻撃です。

通常の情報が www.example.jp → 203.0.113.10 であるのに対し、攻撃者は www.example.jp → 203.0.113.200 に置き換えようとします。利用者が正しいドメイン名を入力しても、誤ったIPアドレスが返されることで、攻撃者が用意したサーバへ接続してしまう可能性があります。

3-2. 攻撃の流れ

  1. 正常な問い合わせ：再帰リゾルバが権威DNSへ www.example.jp のAレコードを問い合わせる。
  2. 攻撃者が偽の応答を送信：正規の権威DNSからの応答に見せかけて、不正なIPアドレスを含む応答を送り込む。
  3. 偽の応答が受理される：必要な照合条件を満たしていると誤認されれば、不正なレコードがキャッシュされる。
  4. 利用者に不正なIPアドレスが返る：同じ名前を問い合わせた利用者が、意図しないサーバへ誘導される。

3-3. なぜ偽の応答を受け入れてしまうのか

従来のDNS応答では、問い合わせと応答の対応付けにトランザクションID、送信元・宛先IPアドレス、ポート番号、質問内容などが使われます。これらは応答の整合性を確認するための情報ですが、暗号学的な署名とは異なります。

攻撃者が必要な条件を満たす偽の応答を正規の応答より先に受理させると、キャッシュポイズニングが成立する可能性があります。ただし、偽の応答を送るだけで必ず成功するわけではありません。DNS実装の検証処理や、攻撃者が通信を観測できるかなどによって成立条件は異なります。

3-4. トランザクションID

DNSトランザクションIDは、問い合わせと応答を対応付けるための16ビットの値です。例えば、再帰リゾルバが問い合わせにID 0x7A31 を使用した場合、応答にも対応するIDが含まれます。

攻撃者が正しいIDを知らなければ、偽の応答を受理させることは難しくなります。ただし、16ビットという値だけで十分な防御になるわけではありません。

3-5. 送信元ポート番号のランダム化

DNS問い合わせを行う再帰リゾルバは、問い合わせ元のUDPポート番号をランダムに選ぶことがあります。

再帰リゾルバ
192.0.2.10:53127
       |
       | UDP
       v
権威DNS
203.0.113.53:53

攻撃者が偽の応答を送り込むには、トランザクションIDに加えて、問い合わせ元ポート番号などの条件にも適合させる必要があります。そのため、送信元ポート番号のランダム化は、推測による応答偽装を困難にする対策になります。

3-6. 対策

  • DNSトランザクションIDを予測困難にする。
  • 問い合わせ元ポート番号をランダム化する。
  • 応答の送信元、問い合わせ内容などを適切に照合する。
  • DNSSECによって署名付きDNSデータを検証する。
  • DNSサーバのソフトウェアを更新し、既知の脆弱性に対処する。

トランザクションIDやポート番号のランダム化は偽応答を受け入れさせにくくする対策であり、DNSSECは署名を使ってDNSデータ自体の真正性を検証する対策です。

4. DNSキャッシュポイズニングとHTTPSの関係

4-1. DNSを偽装すればHTTPSも破られるのか

必ずしもそうではありません。利用者が https://www.example.jp にアクセスしたとします。DNSキャッシュポイズニングによって攻撃者のIPアドレスが返された場合、ブラウザはそのIPアドレスへ接続しようとする可能性があります。

しかし、HTTPSではサーバ証明書の検証が行われます。攻撃者が www.example.jp に対する正当な証明書を提示できなければ、通常は証明書エラーになります。

4-2. それでも危険な理由

DNSキャッシュポイズニングによる影響は、HTTPSで完全に消えるわけではありません。HTTPでアクセスするサービス、証明書警告を無視する利用者、証明書検証に問題のあるアプリケーションなどでは、攻撃の影響が生じる可能性があります。また、通信の妨害や、意図しない接続先への誘導そのものが問題となる場合もあります。

4-3. 科目Bでの説明

「DNSを偽装されたので暗号通信が復号された」と短絡的に書くのは不適切です。DNS偽装によって接続先IPアドレスが変化することと、TLSによって接続先の正当性を検証することを分けて説明します。

5. DNSSECの目的と基本構成

A：必須・重点復習

5-1. DNSSECとは

DNSSEC（Domain Name System Security Extensions）は、DNSの応答データにデジタル署名を利用し、そのデータが正当なゾーンから提供されたもので、改ざんされていないことを検証する仕組みです。

通常のDNSでは、例えば次のようなレコードが返されます。

www.example.jp. 300 IN A 203.0.113.10

DNSSECに対応したゾーンでは、これに関連する署名情報も管理されます。検証側は、署名と公開鍵などを利用してDNSデータを検証します。

5-2. DNSSECが保証すること

  • 真正性：信頼できるDNSゾーンから提供されたデータであることを確認する。
  • 完全性：DNSデータが不正に改ざんされていないことを確認する。

DNSSECはDNS通信を暗号化する仕組みではありません。従来の平文DNS問い合わせの内容が通信経路上で見えなくなるわけではありません。

5-3. DNSSECに登場する主要レコード

レコード 役割
DNSKEY DNSSECの署名検証に利用する公開鍵を公開する
RRSIG DNSレコード集合に対するデジタル署名を保持する
DS 親ゾーンに置かれ、子ゾーンのDNSKEYを信頼の連鎖につなぐ
NSEC/NSEC3 名前やレコードが存在しないことを検証可能な形で示す

今回の最優先は、DNSKEY・RRSIG・DSの三つです。

5-4. RRSIGは何に署名するのか

DNSSECでは、同じ名前・種類などの条件でまとめられたDNSレコード集合（RRset）に対して署名が付けられます。例えば www.example.jp. 300 IN A 203.0.113.10 というAレコード集合に対し、対応するRRSIGが存在します。検証側は、適切なDNSKEYを利用して、その署名を検証します。

5-5. DNSKEYは秘密鍵なのか

いいえ。DNSKEYレコードに登録されるのは公開鍵です。署名を作成するための秘密鍵は、適切に保護して管理します。

署名作成側：
秘密鍵 → DNSレコード集合に署名

検証側：
公開鍵（DNSKEY） → RRSIGを検証

秘密鍵が漏えいすれば、不正な署名付きデータを作成されるおそれがあるため、鍵管理は重要です。

6. DNSSECの信頼の連鎖

A：必須・既存の復習対象

6-1. 公開鍵を取得しただけでは信用できない

ここがDNSSECの理解で最も重要な点です。攻撃者が偽のAレコードを作り、自分の秘密鍵で署名し、自分の公開鍵も配布したとします。その公開鍵で署名を検証すれば、数学的には検証に成功する可能性があります。しかし、その公開鍵が本当に正規の example.jp の公開鍵なのかが分かりません。そのため、DNSSECには公開鍵自体を信頼できる仕組みが必要です。

6-2. 親ゾーンと子ゾーン

ルート（.）
   |
   v
jp
   |
   v
example.jp
   |
   v
www.example.jp

DNSSECでは、この階層構造を利用して信頼をつなぎます。

6-3. DSレコードの役割

DS（Delegation Signer）レコードは、親ゾーンに登録され、子ゾーンのDNSKEYに対応するダイジェストなどを保持します。例えば、example.jp のDNSSEC情報を検証する場合、親である jp ゾーンに example.jp のDSレコードが置かれます。このDSを利用して、子ゾーンから取得したDNSKEYが、親ゾーンによって示された鍵と対応しているか確認します。

6-4. 信頼の連鎖の全体図

① 信頼の起点：ルートゾーン
   検証側が信頼するルートの公開鍵情報（トラストアンカー）
             |
             | 署名とDSを検証
             v
② 親ゾーン：jp
   信頼できるjpのDNSKEYを確立し、example.jpのDSを検証
             |
             | DSと子DNSKEYを照合
             v
③ 子ゾーン：example.jp
   取得したDNSKEYが親のDSと対応することを確認
             |
             | DNSKEYでRRSIGを検証
             v
④ www.example.jp のAレコード
   RRSIGを検証し、レコード集合の真正性・完全性を確認

6-5. 検証手順を順番に理解する

第1段階：信頼の起点を確立する。検証側は、あらかじめ信頼しているルートの公開鍵情報を起点とします。

第2段階：親ゾーンの情報を検証する。ルートから jp へ、DNSKEYとDS、署名を利用して信頼をつなぎます。

第3段階：親ゾーンのDSを確認する。jp ゾーンに登録された example.jp のDSレコードを、信頼済みの jp の鍵によって検証します。

第4段階：子ゾーンのDNSKEYを確認する。example.jp から取得したDNSKEYが、親ゾーンのDSと対応していることを確認します。

第5段階：子ゾーンのRRSIGを検証する。信頼できると確認した example.jp のDNSKEYを利用して、Aレコード集合に付けられたRRSIGを検証します。このように、上位から下位へ信頼をつないでいきます。

6-6. 親のDSは子のAレコードを直接検証するのか

いいえ。DSは子ゾーンのDNSKEYを信頼するための情報です。Aレコード集合の署名を検証するのは、対応するDNSKEYとRRSIGを利用する処理です。

情報 検証での役割
親のDS 子のDNSKEYを信頼の連鎖に結び付ける
子のDNSKEY 子のRRsetに対するRRSIGを検証する
子のRRSIG 対象RRsetの署名を示す

6-7. DNSSECの検証が失敗すると

DNSSEC検証を行う再帰リゾルバが、不正な署名や鍵の不整合を検出した場合、名前解決に失敗することがあります。例えば、DNSSEC設定の誤りや鍵更新の失敗によって、正規のドメインでもSERVFAILになる場合があります。DNSSECは導入するだけでなく、鍵更新や親ゾーンのDS登録との整合性を管理する必要があります。

6-8. 科目Bでの答案例

設問：DNSSECで、親ゾーンのDSレコードが必要な理由を説明せよ。

答案例：「親ゾーンで検証したDSレコードと子ゾーンのDNSKEYを照合し、子ゾーンの公開鍵を信頼の連鎖につなぐため。」

設問：子ゾーンのAレコードの改ざんを検出する仕組みを説明せよ。

答案例：「親ゾーンのDSから信頼性を確認した子ゾーンのDNSKEYを用いて、Aレコード集合のRRSIGを検証する。」

この二つの答案を区別して書けることが、今回の重要な到達目標です。

7. DNSSECと暗号化DNSの違い

7-1. DNSSECは通信内容を隠さない

DNSSECはDNSデータの署名検証に関する技術です。DNS問い合わせの内容を第三者に見られないようにする仕組みではありません。

7-2. DoTとDoH

技術 主な役割 代表的な通信
DNSSEC DNSデータの真正性・完全性を検証 DNSの署名検証
DNS over TLS（DoT） DNS通信をTLSで保護 TCP 853
DNS over HTTPS（DoH） DNS通信をHTTPSで保護 HTTPS、一般に443番

DoTやDoHは、クライアントとDNSサービス間などの通信を保護します。しかし、暗号化された通信路の先にあるDNSサービスが誤った情報を返す可能性まで、通信路の暗号化だけで排除できるわけではありません。

7-3. 三つの違いを整理する

  • DNSSEC：返されたDNSデータは正当か。
  • DoT/DoH：DNSの問い合わせ・応答を通信経路上で保護できるか。
  • HTTPS：Webサーバとの通信を保護し、証明書などで接続先を検証できるか。

保護する対象が違います。

8. DNS Rebinding

A：必須

8-1. DNS Rebindingとは

DNS Rebinding（DNSリバインディング）は、攻撃者が管理するドメイン名のDNS応答を変化させ、ブラウザなどから内部ネットワークのサービスへアクセスさせようとする攻撃です。

攻撃者が正規のDNSキャッシュを偽装する必要がない場合があることがポイントです。攻撃者自身が管理するドメインについて、正当な権威DNSサーバから異なるIPアドレスを返すことができます。

8-2. 攻撃の前提

利用者PC：192.168.1.10
社内管理サーバ：192.168.1.100
攻撃者のWebサーバ：203.0.113.200

攻撃者は attacker.example というドメインを管理しているとします。

8-3. 攻撃の流れ

第1段階：攻撃者のWebサイトへアクセス。利用者が攻撃者のWebサイトへアクセスします。最初のDNS応答は、攻撃者の外部サーバのIPアドレスです。

attacker.example
      ↓
203.0.113.200

ブラウザは攻撃者のWebページを取得します。

第2段階：攻撃者のスクリプトが実行される。Webページには、後で同じドメインへアクセスするJavaScriptなどが含まれているとします。

第3段階：DNS応答が変更される。一定時間後、同じドメイン名の名前解決結果が内部IPアドレスへ変わるように、攻撃者がDNSを設定します。

attacker.example
      ↓
192.168.1.100

第4段階：ブラウザから内部サーバへのアクセスを試みる。ブラウザが再び attacker.example へ接続しようとしたとき、名前解決結果が内部サーバを指していれば、内部サーバへの接続を試みる可能性があります。

ただし、現代のブラウザやネットワーク環境では、Private Network Accessなどの制限、DNSキャッシュ、HTTPS証明書の検証、対象サーバのHostヘッダ処理などによって攻撃が阻止される場合があります。DNS応答を変更するだけで必ず成立するわけではありません。

8-4. 同一オリジンポリシーとの関係

ブラウザの同一オリジンポリシーは、基本的にスキーム、ホスト名、ポート番号などでオリジンを判断します。攻撃者は、同じホスト名を維持したまま、その名前が指すIPアドレスを変化させることで、内部サービスへのアクセスを試みます。このため、DNS Rebindingは、単純な「DNS応答を偽装する攻撃」とは異なる特徴を持ちます。

8-5. 対策

  1. 内部管理サービスに適切な認証・認可を実装する。
  2. HostヘッダやOriginなどを、サービスの設計に応じて検証する。
  3. 管理用サービスを不要に公開せず、アクセス元を制限する。
  4. DNSリゾルバで、外部ドメインが内部アドレスを返す不審な応答を制限する対策を検討する。
  5. ブラウザやサーバのセキュリティ更新を適用する。

DNSリゾルバによるプライベートIPアドレス応答の制限は、正当な内部用途にも影響する可能性があるため、環境に応じた設計が必要です。

8-6. キャッシュポイズニングとの違い

項目 キャッシュポイズニング DNS Rebinding
主な操作対象 キャッシュDNSに取り込まれる情報 攻撃者管理ドメインのDNS応答
主な狙い 偽のIPアドレスを返させる ブラウザなどから内部サービスへ接続させる
偽のDNS応答 攻撃方法によって必要 必ずしも必要ない
重要な防御 DNSSEC、応答検証、ランダム化 内部サービスの認証・アクセス制限、Host/Origin検証など

9. サブドメインテイクオーバー

A：必須・IPA採点講評で確認された論点

9-1. どのような攻撃か

サブドメインテイクオーバーは、組織が管理するサブドメインについて、外部サービスとの紐付けが不適切に残っている場合などに、第三者がそのサブドメインで提供されるコンテンツを制御できるようになる問題です。

例えば、企業が campaign.example.jp を利用し、外部のWebホスティングサービスやCDNを参照するCNAMEレコードを持っているとします。

campaign.example.jp. IN CNAME old-site.hosting.example.

9-2. サービス終了後の設定漏れ

キャンペーン終了により、企業が外部ホスティングサービス上のサイトを削除したとします。しかし、DNSのCNAMEレコードを削除し忘れました。

企業のDNS
campaign.example.jp
       |
       | CNAMEが残っている
       v
old-site.hosting.example

外部サービス側
該当リソースは削除済み

外部サービス側の仕様によっては、第三者が削除済みの名前やリソースを再取得できる場合があります。

9-3. 攻撃が成立する条件

CNAMEが残っているだけで必ずサブドメインテイクオーバーが成立するわけではありません。

  • 組織のDNSに外部サービスへの参照が残っている。
  • 外部サービス上で、元の組織が利用していたリソースが削除されている。
  • 第三者が参照先に対応するリソースや名前を取得できる。
  • 外部サービスが十分な所有権検証を行わず、当該サブドメインへのコンテンツ提供を許してしまう。

成立条件はサービスによって異なります。

9-4. 攻撃の影響

  • 正規組織のサブドメインで偽のWebページが表示される。
  • 利用者が正規組織のサイトだと誤認する。
  • 偽のログイン画面などを通じて情報を入力させられる。
  • 当該サブドメインに対する組織の信用が悪用される。

実際にHTTPS証明書を取得できるか、Cookieを悪用できるかなどは、サービス設定やブラウザの制約に依存します。

9-5. なぜDNSSECだけでは防げないのか

企業の権威DNSに次のCNAMEが正規の設定として残っているとします。

campaign.example.jp. IN CNAME old-site.hosting.example.

DNSSECは、このCNAMEが正規ゾーンから提供されたもので改ざんされていないことを検証できます。しかし、その参照先が既に廃止されたサービスなのか、第三者に取得され得るのかまでは判断しません。DNSSECの検証が成功していても、DNS設定の運用上の問題は残ります。

9-6. 対策

  • 利用終了したサービスに対応する不要なCNAMEを削除する。
  • DNSレコードを定期的に棚卸しする。
  • 外部サービスの利用開始・終了時にDNS設定を確認する。
  • 外部サービス側でドメイン所有権の検証を適切に実施する。
  • サブドメインの参照先が有効な管理対象か継続的に確認する。

9-7. IPAの設問から学ぶ答案の書き方

令和7年度春期のIPA午後試験の採点講評では、CDNやWebサーバの利用終了後にDNSのCNAMEレコードが残存する問題が扱われています。

「DNSの設定を見直す」という抽象的な回答ではなく、不要になったCNAMEレコードを削除するという具体的な設定変更を示すことが重要です。

答案例：「利用を終了した外部サービスを参照するCNAMEレコードをDNSゾーンから削除する。」

9-8. 三つのDNS攻撃を比較する

攻撃 攻撃者が利用する問題 代表的な対策
DNSキャッシュポイズニング 不正なDNS応答がキャッシュに取り込まれる DNSSEC検証、応答照合、ランダム化
DNS Rebinding 同じドメイン名の解決先を変更し、内部サービスへアクセスを試みる 内部サービスの認証・アクセス制限、Host/Origin検証
サブドメインテイクオーバー 外部サービスの利用終了後もDNS参照が残る 不要なCNAME削除、DNS棚卸し、所有権検証

この表は、科目Bの原因と対策を取り違えないために重要です。

10. DNSの不正利用とその他の脅威

10-1. DNSリフレクション攻撃

DNSは、送信元IPアドレスを偽装したUDP問い合わせによって、第三者への応答を発生させる攻撃に悪用されることがあります。例えば、攻撃者が被害者のIPアドレスを送信元としてDNSサーバへ問い合わせると、DNSサーバが被害者へ応答を送る場合があります。これをDNSリフレクション攻撃と呼びます。

10-2. DNS増幅攻撃

小さなDNS問い合わせに対して大きなDNS応答が返る場合、攻撃者が送信した通信量よりも大きな通信量を被害者へ発生させられることがあります。これがDNS増幅攻撃です。対策には、送信元IPアドレスの詐称防止、不要な再帰問い合わせの制限、応答レート制限などがあります。

10-3. オープンリゾルバ

不特定多数からの再帰問い合わせを受け付けるDNSサーバは、第三者に悪用される可能性があります。組織内向けの再帰リゾルバであれば、問い合わせを許可するクライアントを必要な範囲に限定します。

10-4. ゾーン転送の設定不備

権威DNSサーバが不特定多数へゾーン転送を許可していると、ゾーン内のホスト名などを第三者に取得されるおそれがあります。

db01.example.jp.  IN A 192.0.2.10
vpn.example.jp.   IN A 192.0.2.20
mail.example.jp.  IN A 192.0.2.30

攻撃者がネットワーク構成を推測する手掛かりになる場合があります。対策は、ゾーン転送を許可する相手を正当なセカンダリDNSサーバなどに限定し、必要に応じて認証を利用することです。

10-5. DNSトンネリング

DNS問い合わせの名前部分などにデータを埋め込み、DNS通信をデータ送受信の経路として悪用する手法があります。通常とは異なる長いサブドメイン名への問い合わせが大量に発生する場合、不審な通信の手掛かりになることがあります。ただし、長いDNS名や問い合わせ回数の多さだけで攻撃と断定することはできません。調査では、問い合わせ先ドメイン、文字列の特徴、頻度、端末の動作、他の通信ログなどを組み合わせます。

11. DNSSEC検証失敗の障害調査

A：必須・科目B重点

11-1. DNSSECを有効にすると障害が起きることもある

DNSSECはDNS情報の正当性を検証しますが、設定が誤っていると、正規のドメインであっても検証に失敗する場合があります。例えば、子ゾーンの鍵を更新したのに、親ゾーンのDSレコードが古いままだった場合です。

11-2. 鍵更新とDSの不整合

親ゾーン：
example.jp のDS → 古いDNSKEYに対応

子ゾーン：
example.jp のDNSKEY → 新しい鍵

検証側は、親ゾーンのDSと子ゾーンのDNSKEYを照合します。しかし、両者が対応していなければ、信頼の連鎖を正しく構築できません。その結果、DNSSEC検証に失敗する可能性があります。

11-3. SERVFAIL

DNSSEC検証に失敗した再帰リゾルバは、クライアントへSERVFAILを返す場合があります。

;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL

ただし、SERVFAILはDNSSEC検証失敗専用の応答ではありません。上流DNSへの問い合わせ失敗やサーバ内部の問題など、別の原因でも発生します。

11-4. 障害の切り分け

例えば、DNSSEC検証を行う再帰リゾルバではSERVFAILになり、権威DNSへ直接問い合わせるとAレコードが返る場合です。次の情報を確認します。

  1. 親ゾーンのDSレコード。
  2. 子ゾーンのDNSKEYレコード。
  3. 対象レコード集合のRRSIG。
  4. 署名の有効期間。
  5. 再帰リゾルバのDNSSEC検証ログ。
  6. DNSサーバの時刻設定。

11-5. 科目Bの答案例

設問：DNSSEC対応ドメインで鍵更新後に名前解決が失敗した。親ゾーンのDSと子ゾーンのDNSKEYが一致していない場合、失敗する理由を説明せよ。

答案例：「親ゾーンのDSから子ゾーンのDNSKEYの正当性を確認できず、DNSSECの信頼の連鎖を構築できないため。」

12. DNSログの読み取り演習

12-1. 正常なDNS応答

10:00:00 QUERY
Client: 192.168.1.10
Name: www.example.jp
Type: A
TXID: 0x7A31

10:00:00 RESPONSE
Status: NOERROR
Answer: 203.0.113.10

このログでは、Aレコード問い合わせに対してIPアドレスが返っています。ただし、DNS応答が正常でも、そのIPアドレスへのWeb接続まで成功したとは限りません。

12-2. 不審な応答

10:05:00 QUERY
Name: www.example.jp
Type: A

10:05:00 RESPONSE
Answer: 203.0.113.200

通常の登録内容が 203.0.113.10 である場合、調査が必要です。しかし、CDNによる応答の違いや正規の設定変更なども考えられるため、これだけで攻撃と断定しません。権威DNSの設定、キャッシュ、変更履歴、応答元などを照合します。

12-3. DNSSEC検証失敗

10:10:00 DNSSEC VALIDATION FAILED

Zone: example.jp
Reason: DS/DNSKEY mismatch

Result: SERVFAIL

親ゾーンのDSと子ゾーンのDNSKEYが対応していないことが示されています。DNSSECの信頼の連鎖が成立しないことが、名前解決失敗の原因です。

12-4. サブドメインテイクオーバーの疑い

campaign.example.jp. IN CNAME old-site.hosting.example.

運用台帳を確認すると、old-site.hosting.example に対応するサービスは既に廃止されていました。この場合、外部サービス側で第三者によるリソース再取得が可能かを確認する必要があります。対策として、不要なCNAMEを削除し、サービス廃止時のDNSレコード確認を運用手順に追加します。

12-5. DNS Rebindingが疑われる例

10:20:00
attacker.example → 203.0.113.200

10:20:10
attacker.example → 192.168.1.100

短時間で、同じドメインの解決先が外部IPアドレスから内部IPアドレスへ変化しています。このような変化はDNS Rebindingを疑う手掛かりになります。ただし、正当なDNS設定変更や特殊な運用の可能性もあるため、ブラウザの通信、アクセス先の内部サービス、DNSの管理主体などを合わせて確認します。

14. 科目Bの答案作成ポイント

14-1. 設問例①：キャッシュポイズニング

設問：DNSキャッシュポイズニングによって利用者が偽サイトへ誘導される理由を説明せよ。

答案例：「再帰リゾルバに不正なIPアドレスがキャッシュされ、利用者の名前解決時に偽サイトのIPアドレスが返されるため。」

14-2. 設問例②：ポートランダム化

設問：DNS問い合わせの送信元ポート番号をランダム化する目的を説明せよ。

答案例：「攻撃者がDNS応答の宛先ポート番号を推測しにくくし、偽のDNS応答が受理される可能性を低下させるため。」

14-3. 設問例③：DNSSEC

設問：DNSSECを利用する目的を説明せよ。

答案例：「DNSデータに対するデジタル署名を検証し、取得したDNS情報の真正性と完全性を確認するため。」

14-4. 設問例④：DSレコード

設問：DNSSECにおいて、親ゾーンのDSレコードが必要な理由を説明せよ。

答案例：「親ゾーンで検証したDSと子ゾーンのDNSKEYを照合し、子ゾーンの公開鍵を信頼の連鎖につなぐため。」

14-5. 設問例⑤：DNS Rebinding

設問：DNS Rebindingによって、ブラウザから内部サーバへのアクセスが試みられる仕組みを説明せよ。

答案例：「攻撃者管理ドメインの名前解決先を外部サーバから内部サーバのIPアドレスへ変更し、ブラウザから同じホスト名を使って内部サーバへの接続を試みるため。」

14-6. 設問例⑥：サブドメインテイクオーバー

設問：外部サービスを廃止した後もCNAMEレコードが残っている。サブドメインテイクオーバーを防ぐための具体的な対策を説明せよ。

答案例：「利用を終了した外部サービスを参照する不要なCNAMEレコードをDNSゾーンから削除する。」

14-7. 設問例⑦：DNSSECでは防げない理由

設問：DNSSECを導入していても、サブドメインテイクオーバーが成立する可能性がある理由を説明せよ。

答案例：「DNSSECはDNSデータの真正性を検証するが、正規ゾーンに残ったCNAMEの参照先が第三者に取得可能かどうかまでは検証しないため。」

14-8. 設問例⑧：DNSSEC障害

設問：親ゾーンのDSと子ゾーンのDNSKEYが対応しない場合、DNSSEC検証に失敗する理由を説明せよ。

答案例：「親ゾーンのDSを使って子ゾーンのDNSKEYを信頼できると確認できず、署名検証の信頼の連鎖を構築できないため。」

14-9. 答案作成の判断手順

  1. 攻撃対象を確認する。 キャッシュ、権威DNS、DNS委任、外部サービス、ブラウザのどれか。
  2. 攻撃者が操作できるものを確認する。 偽の応答、攻撃者管理ドメイン、外部サービスのリソースなど。
  3. 攻撃成立条件を確認する。 偽応答の受理、DNSの解決先変更、CNAMEの残存など。
  4. 影響を確認する。 偽サイトへの誘導、内部サービスへのアクセス、サブドメインの乗っ取りなど。
  5. 対策を対応付ける。 DNSSEC、ポートランダム化、アクセス制御、CNAME削除など。
  6. 設問にある具体的な設定・ログを答案へ反映する。

「DNSを安全にする」「設定を見直す」といった抽象的な回答ではなく、何をどう変更するかまで記述することが重要です。

15. 重要事項の整理

第一に、DNSキャッシュポイズニングは、不正なDNS情報を再帰リゾルバなどのキャッシュに取り込ませる攻撃です。 偽のIPアドレスが返されることで、利用者が意図しないサーバへ誘導される可能性があります。

第二に、DNSトランザクションIDや送信元ポート番号のランダム化は、偽応答の推測を困難にする対策です。 DNSデータ自体の暗号学的な真正性を検証する仕組みとは異なります。

第三に、DNSSECはDNSデータの真正性・完全性を検証します。 DNS通信の内容を暗号化して隠す技術ではありません。

第四に、DNSSECではDNSKEY・RRSIG・DSの役割を区別します。 DNSKEYは公開鍵、RRSIGはレコード集合の署名、DSは親ゾーンから子ゾーンへ信頼をつなぐ情報です。

第五に、DNSSECの信頼の連鎖は、信頼の起点から親ゾーンのDS、子ゾーンのDNSKEY、対象RRsetのRRSIGへと検証を進めます。 これは今回の最重要復習事項です。

第六に、DNS Rebindingは、攻撃者管理ドメインの解決先を変化させ、内部サービスへのアクセスを試みる攻撃です。 キャッシュポイズニングとは攻撃の仕組みが異なります。

第七に、サブドメインテイクオーバーは、外部サービスの利用終了後に残ったCNAMEなどが悪用される場合があります。 DNSSECを導入していても、正規ゾーンの不要なCNAMEは自動的に削除されません。

第八に、科目Bでは攻撃と対策を正確に対応付けます。 キャッシュポイズニングならDNS応答の検証、サブドメインテイクオーバーなら不要なCNAMEの削除、DNS Rebindingなら内部サービスの認証やアクセス制御などです。

  • KSK・ZSKの高度な鍵ロールオーバー設計
  • NSEC/NSEC3のビット単位の仕様
  • DNSキャッシュポイズニングの攻撃コード
