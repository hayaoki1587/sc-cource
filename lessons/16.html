第16講｜TCP

情報処理安全確保支援士（SC）合格講座｜第1〜23講・詳細再執筆

第15講では、IP通信のエラー通知や経路診断に使用するICMPを学びました。今回扱うTCP（Transmission Control Protocol）は、Web、メール、SSHなど、多くのアプリケーション通信を支えるトランスポート層のプロトコルです。

SC試験では、TCPの仕組みを理解するだけでなく、パケットのフラグやシーケンス番号から通信状態を判断し、SYN Floodなどの攻撃がなぜ成立するのかを説明できることが重要です。

第16講は、既存の進捗表で13／15点・要復習となっています。今回は特に、3ウェイハンドシェイク、ACK番号、再送制御、コネクション状態を重点的に解説します。

2. TCPは何をするプロトコルなのか

2-1. IPだけでは信頼性を保証できない

第12講で学んだIPは、宛先IPアドレスに基づいてパケットを転送します。しかし、IP自体は、送信したパケットが必ず相手に届くことや、送信順序どおりに届くことを保証しません。

例えば、送信元が三つのIPパケットを送ったとします。

送信順序
① → ② → ③

受信結果
② → ①
（③は途中で消失）

このような状況は、ネットワークの混雑や経路の違いなどによって起こり得ます。TCPは、このような不確実なIPネットワーク上で、アプリケーションに順序どおりの信頼性のあるバイトストリームを提供します。

2-2. TCPの主な機能

機能 目的
コネクション管理 通信開始・終了を管理する
シーケンス番号 データの位置・順序を識別する
確認応答（ACK） 受信済みのデータを知らせる
再送制御 消失したデータを再送する
フロー制御 受信側の処理能力を超えないようにする
輻輳制御 ネットワークの混雑を考慮して送信量を調整する
チェックサム 転送中のデータ破損などを検出する

TCPは信頼性を提供しますが、暗号化や通信相手の本人確認を自動的に提供するわけではありません。例えばHTTPSでは、TCPによる転送の上でTLSを使用し、暗号化やサーバ認証などを実現します。

2-3. TCPとUDPの違い

項目 TCP UDP
通信方式 コネクション型 コネクションレス型
コネクション確立 あり なし
順序制御 あり UDP自体にはなし
消失時の再送 TCPが実施 UDP自体にはなし
フロー制御 あり UDP自体にはなし
主な利用例 HTTPS、SSH、SMTPなど DNS、音声・映像通信など

UDPを使うアプリケーションが、独自に再送や順序制御を実装することは可能です。したがって、「UDPを使う通信は絶対に再送しない」という理解は不正確です。

3. TCPの通信を識別する情報

3-1. ポート番号の役割

IPアドレスは通信先のホストなどを識別するために使用します。一方、ポート番号は、そのホスト上のどのサービス・通信端点へデータを渡すかを識別するために使います。

クライアント
192.168.1.10:52000

Webサーバ
203.0.113.10:443

クライアントの送信元ポートは52000、サーバの宛先ポートは443です。

3-2. TCPコネクションの識別

TCPコネクションは、一般に次の四つの値の組合せで識別できます。

  • 送信元IPアドレス
  • 送信元ポート番号
  • 宛先IPアドレス
  • 宛先ポート番号

これを4タプルと呼びます。同じサーバの443番ポートに複数のクライアントが同時接続できます。

192.168.1.10:52000 → 203.0.113.10:443
192.168.1.11:53000 → 203.0.113.10:443
192.168.1.12:54000 → 203.0.113.10:443

それぞれ4タプルが異なるため、別々のTCPコネクションとして管理できます。

3-3. コネクションの相手は必ず最終的なサーバか

必ずしもそうではありません。明示的なHTTPプロキシを使用する場合、クライアントがTCPコネクションを確立する相手はプロキシサーバです。プロキシは必要に応じて、接続先のサーバとの間に別のTCPコネクションを確立します。

クライアント
    |
    | TCPコネクション①
    v
プロキシサーバ
    |
    | TCPコネクション②
    v
Webサーバ

この場合、クライアントからWebサーバまで一本のTCPコネクションがそのまま延びているわけではありません。ファイアウォールやプロキシのログを読むときに重要です。

4. TCPヘッダの主要フィールド

TCPセグメントには、TCPヘッダとデータが含まれます。

4-1. TCPヘッダの構造

┌────────────────┬────────────────┐
│ 送信元ポート番号 │ 宛先ポート番号   │
├────────────────┴────────────────┤
│ シーケンス番号                    │
├─────────────────────────────────┤
│ 確認応答番号                      │
├────────────────┬────────────────┤
│ ヘッダ長・Flags │ ウィンドウサイズ │
├────────────────┼────────────────┤
│ チェックサム    │ 緊急ポインタ     │
├────────────────┴────────────────┤
│ オプション（存在する場合）         │
├─────────────────────────────────┤
│ TCPデータ（ペイロード）            │
└─────────────────────────────────┘

模式図です。実際の各フィールドのビット幅や並びを厳密に縮尺表示したものではありません。オプションを含まないTCPヘッダの長さは20バイトです。

4-2. 試験で特に重要なフィールド

フィールド 意味 試験での確認ポイント
Source Port 送信元ポート 通信元の識別
Destination Port 宛先ポート サービスの識別
Sequence Number シーケンス番号 データの位置
Acknowledgment Number 確認応答番号 次に受信したい番号
Flags 制御フラグ 接続確立・終了・異常終了
Window 受信ウィンドウ 受信側が受け取れるデータ量

特に、Sequence Number、Acknowledgment Number、Flagsは重点的に理解してください。

5. TCPの制御フラグ

フラグ 主な意味
SYN コネクション確立時にシーケンス番号を同期する
ACK 確認応答番号が有効であることを示す
FIN 送信方向のデータ送信を終了する
RST コネクションのリセットを示す
PSH 受信データをアプリケーションへ速やかに渡すよう促す
URG 緊急ポインタが有効であることを示す

5-1. SYN

SYNは、TCPコネクションを確立するときに使用します。通常のクライアントからサーバへの接続開始では、最初にSYNを送信します。

5-2. ACK

ACKは、受信したデータなどに対する確認応答を示します。ただし、ACKフラグが立っているパケットが、必ずしもデータを含まないとは限りません。データと確認応答を同じTCPセグメントに含めることもあります。

5-3. FIN

FINは、その方向のデータ送信を終了するために使用します。TCPは双方向通信なので、一方がFINを送っても、相手方向のデータ送信が直ちに終了するとは限りません。

5-4. RST

RSTは、コネクションのリセットに使用します。接続先のTCPポートでサービスが待ち受けていない場合、RSTが返されることがあります。また、既存のコネクションを異常終了させる場合にも使用されます。FINは通常の送信終了、RSTはリセットという違いを押さえてください。

6. 3ウェイハンドシェイク

A：最重要

TCPはコネクション型のプロトコルです。通常、データ通信を開始する前に、3ウェイハンドシェイクでコネクションを確立します。

6-1. なぜ3回のやり取りが必要なのか

TCPでは、送信側と受信側がそれぞれシーケンス番号を使用します。そのため、通信を始める際には、互いの初期シーケンス番号を通知し、相手からの通知を受け取ったことを確認します。

クライアントの初期シーケンス番号を1000、サーバの初期シーケンス番号を5000とします。

クライアント                         サーバ

① SYN  ──────────────────────────→
   SEQ=1000

       ←────────────────────────── ② SYN+ACK
                           SEQ=5000, ACK=1001

③ ACK  ──────────────────────────→
   SEQ=1001, ACK=5001

          TCPコネクション確立

6-2. 第1段階：SYN

クライアントはサーバへSYNを送信します。

Client → Server
Flags : SYN
SEQ   : 1000

クライアントの初期シーケンス番号がサーバへ通知され、クライアントは通常 SYN-SENT 状態になります。

6-3. 第2段階：SYN+ACK

サーバは受信したSYNに対してSYN+ACKを返します。

Server → Client
Flags : SYN, ACK
SEQ   : 5000
ACK   : 1001

ACK番号が1001なのは、SYNがシーケンス番号を1つ消費するためです。サーバはクライアントの次の番号1001を期待します。またサーバは自分の初期シーケンス番号5000をSYNで通知し、通常 SYN-RECEIVED 状態になります。

6-4. 第3段階：ACK

クライアントはサーバのSYNに対してACKを返します。

Client → Server
Flags : ACK
SEQ   : 1001
ACK   : 5001

サーバのSYNも番号を1つ消費するため、ACK番号は5001です。このACKによって通常、サーバ側でもコネクションが確立します。

6-5. なぜSYNだけで接続確立としないのか

SYNを受信しただけでは、相手がサーバの応答を受信できるか分かりません。サーバはSYN+ACKを返し、クライアントから最終ACKを受け取ることで、クライアントがサーバの初期シーケンス番号を受け取ったことを確認できます。

この仕組みはTCPの接続管理に必要ですが、相手が正当な利用者であることを認証する仕組みではありません。SYN Floodなどの攻撃を考える上で重要です。

7. シーケンス番号と確認応答番号

A：最重要・計算問題

7-1. シーケンス番号はパケットの通し番号ではない

TCPはバイトストリーム型のプロトコルです。シーケンス番号は基本的にTCPデータのバイト位置を示します。

SEQ = 1001
データ長 = 500バイト

データの番号：1001〜1500
次に送るデータの先頭番号：1501

7-2. ACK番号は「次に期待する番号」

受信：SEQ=1001, LEN=500
返信：ACK=1501

1001〜1500までのデータを受信したので、次は1501から送ってほしいという意味です。ACK=1501は「1501番まで受信済み」という意味ではありません。

7-3. ACK番号の計算

送信SEQ データ長 正常受信後のACK
1001 100バイト 1101
1101 200バイト 1301
1301 500バイト 1801

一般に、連続したデータを正常に受信した場合、ACK = SEQ + データ長となります。ただしSYNやFINが含まれる場合は、それぞれ番号を1つ消費します。

7-4. SYN・FIN・ACKとシーケンス番号

要素 シーケンス番号の消費
データ100バイト 100
SYN 1
FIN 1
データを含まない通常のACK 0

7-5. データが途中で欠落した場合

① SEQ=1001, LEN=500    受信
② SEQ=1501, LEN=500    消失
③ SEQ=2001, LEN=500    受信

受信側は1001〜1500まで連続して受信していますが、1501〜2000が欠落しています。そのため③を受信しても通常の累積ACKは ACK=1501 のままです。後続の③が到着したからといってACKが2501へ進むわけではありません。

7-6. 累積ACK

TCPの基本的な確認応答は累積ACKです。例えば ACK=2501 は、通常2500番までのバイトを連続して受信したことを示します。途中に欠落がある場合、その欠落部分を越えて累積ACKを進めることはできません。これがTCPの欠落検出・再送の基盤です。

8. TCPの再送制御

8-1. なぜ再送が必要なのか

IPネットワークではパケットが消失する可能性があります。TCPは、送信したデータに対するACKが適切に返らない場合などにデータを再送します。代表的な仕組みは再送タイムアウトと重複ACKなどを利用した早期再送です。

8-2. 再送タイムアウト（RTO）

送信側                       受信側
データ① ──────────────────→ 受信
       ←────────────────── ACK①
データ② ──────X              消失
        （ACKを待つ）
        （タイムアウト）
データ② ──────────────────→ 受信
       ←────────────────── ACK②

一定時間が経過しても必要なACKが得られない場合、再送を行います。RTOは常に一定値ではなく、往復時間などに応じて調整されます。

8-3. 重複ACKとFast Retransmit

受信側が1501番からのデータを待っているのに、それより後のデータが届き続けた場合、同じACK番号が繰り返されることがあります。

ACK=1501
ACK=1501
ACK=1501

送信側は重複ACKを手掛かりに、タイムアウトを待たず欠落データを再送する場合があります。これをFast Retransmit（高速再送）と呼びます。一般的な説明では3個の重複ACKが契機となる方式が知られていますが、実際の再送判断は実装や機能によって異なります。

8-4. SACK

SACK（Selective Acknowledgment）は、受信側が累積ACKより先に受信済みのデータ範囲を送信側へ知らせる仕組みです。

1501〜2000：未受信
2001〜2500：受信済み

累積ACKだけでは「1501から必要」という情報が中心ですが、SACKを使えば2001〜2500が受信済みであることも知らせられ、不要な再送を避けやすくなります。

8-5. 再送は必ず攻撃の兆候なのか

いいえ。TCPの再送は、ネットワーク混雑、パケット損失、通信品質の問題などによって正常な通信でも発生します。ログに TCP Retransmission と表示されただけで攻撃と判断せず、再送の頻度、通信、負荷、他のログを組み合わせて調査します。

9. フロー制御と輻輳制御

A：区別／B：動作の詳細

9-1. フロー制御

フロー制御は、受信側が処理できる量を超えて送信しないようにする仕組みです。例えば受信側のバッファに空きが4000バイトしかない場合、受信側はその受信可能量をウィンドウサイズとして通知できます。

受信側の空きバッファ：4000バイト
Advertised Window = 4000

送信側は受信側が通知するウィンドウを考慮して、未確認データの送信量を制御します。

9-2. 輻輳制御

輻輳制御は、ネットワークが混雑しすぎないように送信量を調整する仕組みです。送信側と受信側の性能に問題がなくても、途中のネットワークが混雑していればパケットが消失することがあります。TCPはACKの受信状況や損失などを手掛かりに送信量を調整します。

9-3. 両者の違い

項目 フロー制御 輻輳制御
主な対象 受信側の処理能力・バッファ ネットワークの混雑
代表的な情報 受信ウィンドウ（rwnd） 輻輳ウィンドウ（cwnd）
目的 受信側を圧迫しない ネットワークを過負荷にしない

実際の送信量は、受信ウィンドウと輻輳ウィンドウの双方などによって制限されます。

9-4. Zero Window

受信側のバッファに空きがなくなると、受信ウィンドウが0になる場合があります。

Window = 0

この場合、送信側は通常のデータ送信を停止し、ウィンドウが再び利用可能になるのを待ちます。受信アプリケーションの処理遅延などでも発生し、必ずしも攻撃ではありません。

10. TCPコネクションの終了

10-1. FINによる正常終了

TCPは双方向通信です。一方がデータ送信を終了しても、もう一方はまだデータを送信できる場合があります。典型的な正常終了では次のような4つのセグメントを使用します。

クライアント                 サーバ
FIN ──────────────────────→
    ←───────────────────── ACK
    ←───────────────────── FIN
ACK ──────────────────────→

ただし実際にはACKとFINが同じセグメントにまとめられる場合もあるため、常に4パケットになるわけではありません。

10-2. FINとACKの番号

FIN
SEQ=3001

応答：ACK=3002

FINはシーケンス番号を1つ消費するため、サーバは通常ACK=3002を返します。SYNと同じくFINも1つ消費する点に注意してください。

10-3. Half-Close

一方がFINを送信しても逆方向のデータ送信が続く状態をHalf-Closeと呼びます。クライアントが「こちらから送るデータは終わった」と通知しても、サーバは処理結果を送信し続けることができます。FINを受信した瞬間に、両方向の通信が必ず終了するわけではありません。

10-4. RSTによるリセット

RSTは通常のFINによる終了とは異なり、TCPコネクションをリセットするために使用します。通信相手が想定しないセグメントを受信した場合や、サービスが存在しないポートへの接続要求を受けた場合などにRSTが使われることがあります。ログにRSTがあれば、どちらの機器が送信したのか、どの状態で発生したのかを確認します。

10-5. TIME_WAIT

通常のTCP終了では、最後のACKを送信した側がTIME_WAIT状態になる場合があります。遅れて到着する古いセグメントが新しいコネクションに悪影響を与えることを抑えたり、最後のACKが失われた場合の再送に対応したりする役割があります。TIME_WAITが存在すること自体は必ずしも異常ではありません。

11. TCPの主要な状態

A：接続状態の判断／B：終了時の詳細

状態 意味
LISTEN 接続要求を待っている
SYN-SENT SYNを送信し、応答を待っている
SYN-RECEIVED SYNを受信し、SYN+ACKを送って最終ACKを待っている
ESTABLISHED コネクションが確立している
FIN-WAIT-1 FINを送信し、その確認などを待っている
FIN-WAIT-2 自分のFINへのACKを受信し、相手のFINを待っている
CLOSE-WAIT 相手のFINを受信し、自分側の終了を待っている
LAST-ACK 自分のFINへのACKを待っている
TIME-WAIT 終了後、一定時間待機している

11-1. SYN-RECEIVEDが大量に存在する場合

サーバにSYN-RECEIVED状態の接続が大量にある場合、接続確立が途中で止まっている可能性があります。クライアントから最終ACKが返らない、ネットワーク障害でACKが失われる、送信元IPアドレスを偽装したSYN Floodなどが考えられます。SYN-RECEIVEDが多いだけでSYN Floodと断定することはできません。

11-2. CLOSE-WAITが大量に存在する場合

CLOSE-WAITは相手からFINを受信した後、自分側の終了を待っている状態です。大量に残り続ける場合、アプリケーションがソケットを適切にクローズしていない可能性があります。ネットワーク機器だけでなくアプリケーション側の処理を調査します。

12. SYN Flood攻撃

A：最重要・攻撃の仕組みと対策

12-1. SYN Floodとは

SYN FloodはTCPの3ウェイハンドシェイクを悪用するDoS攻撃です。攻撃者は大量のSYNを送信し、サーバに接続確立途中の状態を多数作らせようとします。

12-2. 攻撃の流れ

正常な接続：

クライアント                 サーバ
SYN ──────────────────────→
    ←───────────────────── SYN+ACK
ACK ──────────────────────→
コネクション確立

SYN Floodでは、最終ACKを返さない、または返せない状況を大量に作ります。

攻撃者                       サーバ
SYN ───────────────────────→
    ←────────────────────── SYN+ACK
      （最終ACKなし）
SYN ───────────────────────→
    ←────────────────────── SYN+ACK
      （最終ACKなし）
SYN ───────────────────────→
    ←────────────────────── SYN+ACK
      （最終ACKなし）

サーバ側には接続確立途中の情報が蓄積する可能性があります。

12-3. なぜサーバに負荷がかかるのか

一般的なTCPサーバでは、SYNを受信すると接続確立のために必要な情報を管理します。未完了接続が大量に発生すると、接続管理用の資源や処理能力が消費され、正規利用者からの新しい接続要求を処理しにくくなる可能性があります。

12-4. 送信元IPアドレスの偽装

攻撃者がSYNの送信元IPアドレスを偽装すると、サーバのSYN+ACKは偽装された送信元へ送られます。攻撃者自身が受信できなければ通常の最終ACKを返せず、接続確立途中の状態を作ることができます。ただし、SYN Floodは送信元IPアドレスの偽装を必須とする攻撃ではありません。

12-5. SYN Cookie

SYN Cookieは、サーバがSYNを受信した際、通常の接続管理情報を直ちに大量に保持する代わりに、必要な情報を符号化した初期シーケンス番号を利用する仕組みです。クライアントから最終ACKが返ってきたときにACK番号などを検証して接続を成立させます。

通常の処理：
SYN受信 → 接続確立途中の情報を管理 → 最終ACKを待つ

SYN Cookie：
SYN受信 → 検証用情報を初期SEQに符号化 → 最終ACKを検証

これにより未完了接続に関する状態情報の保持を抑え、SYN Floodへの耐性を高められます。ただしSYN CookieはすべてのDoS攻撃を防ぐ万能な対策ではなく、回線帯域自体が埋まる場合などには別の対策も必要です。

12-6. その他の対策

  • SYN Cookieの利用
  • SYN Proxyなどによる接続確立の代理処理
  • 不審なSYNのレート制限
  • DoS対策機器・サービスの利用
  • 送信元IPアドレスの偽装対策
  • サーバの接続管理資源や設定の適切な調整

攻撃によって何が消費されるのかを理解し、それに対応する防御策を選ぶことが重要です。

13. TCPのログとパケットを読む

13-1. 正常な3ウェイハンドシェイク

No.  Source          Destination     Flags     Seq   Ack
1    192.168.1.10    203.0.113.10    [SYN]     1000  -
2    203.0.113.10    192.168.1.10    [SYN,ACK]  5000  1001
3    192.168.1.10    203.0.113.10    [ACK]      1001  5001

正常な3ウェイハンドシェイクです。SYNにSYN+ACKが返され、SYN+ACKのACK番号がクライアントの初期SEQ+1、最終ACKのACK番号がサーバの初期SEQ+1であることを確認します。

13-2. SYNを送信したが応答がない

10:00:01 Client → Server [SYN]
10:00:02 Client → Server [SYN] Retransmission
10:00:04 Client → Server [SYN] Retransmission

SYNを送信しても期待する応答を受信できず再送しています。宛先へ届いていない、ファイアウォールがSYNを破棄している、サーバからのSYN+ACKが途中で失われている、サーバが接続要求を処理できない、といった原因が考えられます。このログだけでは断定できず、送信元と宛先の双方でパケットを確認して絞り込みます。

13-3. SYNに対してRSTが返る

Client → Server [SYN]  Dst Port: 443
Server → Client [RST,ACK]

サーバが接続を拒否した可能性があります。TCP 443番ポートでサービスが待ち受けていない場合などです。ただしファイアウォールなどがRSTを生成する構成もあるため、送信元を確認する必要があります。

13-4. SYN Floodを疑うログ

10:00:01  198.51.100.11 → 203.0.113.10 [SYN]
10:00:01  198.51.100.12 → 203.0.113.10 [SYN]
10:00:01  198.51.100.13 → 203.0.113.10 [SYN]
10:00:01  198.51.100.14 → 203.0.113.10 [SYN]

サーバ状態：
SYN-RECEIVED が短時間で急増

SYN Floodの可能性がありますが、正当な利用者の大量アクセスでもSYNは増えます。最終ACKの割合、接続確立率、送信元の分布、サーバ負荷などを確認します。

13-5. ACK番号から欠落を見つける

Client → Server  SEQ=1001 LEN=500
Server → Client  ACK=1501

Client → Server  SEQ=1501 LEN=500
                （途中で消失）

Client → Server  SEQ=2001 LEN=500
Server → Client  ACK=1501

最後のACKが1501のままなのは1501からのデータが欠落しているためです。2001からのデータが到着していても1501〜2000が欠落している限り累積ACKは先へ進めません。ACK番号が進まない理由をシーケンス番号とデータ長から説明することが重要です。

13-6. ファイアウォールのステートフル検査

ステートフルファイアウォールは通信状態を管理し、その状態に基づいてパケットを許可・拒否できます。

内部PC → 外部サーバ：SYN
外部サーバ → 内部PC：SYN+ACK
内部PC → 外部サーバ：ACK

内部から開始した正規通信の戻りパケットを許可し、状態に合わない不審なパケットを拒否できます。ただし実際の受理条件は機器の設定や実装によって異なります。

14. TCPを利用したその他の攻撃

14-1. TCPセッションハイジャック

TCPセッションハイジャックは既存のTCP通信に不正に介入する攻撃です。攻撃者が通信経路上にいる場合などには、TCPのシーケンス番号や通信内容を観測し、不正なデータを挿入しようとすることがあります。ただしTCPのシーケンス番号は通信相手の本人性を暗号学的に保証するものではなく、重要な通信ではTLSなどによる暗号化・認証が必要です。

14-2. RSTを利用した通信妨害

攻撃者が既存のTCPコネクションに対して有効なRSTを送信できると、通信を強制的に終了させられる場合があります。ただし任意のRSTを送信すれば必ず切断できるわけではありません。TCPはコネクションの識別情報やシーケンス番号などを検証します。

14-3. SYN Floodとセッションハイジャックの違い

攻撃 主な狙い 悪用する仕組み
SYN Flood 新規接続の妨害 3ウェイハンドシェイク途中の状態
セッションハイジャック 既存通信への不正介入 TCPコネクションの識別・シーケンス管理
RSTによる妨害 既存通信の切断 TCPのリセット機能

どの通信段階を狙っているかを区別してください。

16. 科目Bの答案作成ポイント

16-1. 設問例①：ACK番号の計算

設問：クライアントが SEQ=3001、データ長800バイトのTCPセグメントを送信した。サーバが欠落なく受信した場合、返すACK番号を求めよ。

答案例：3801

解説：3001から800バイトのデータを受信したため、次に期待する番号は3801です。

16-2. 設問例②：SYN Floodの仕組み

設問：SYN Flood攻撃によってサーバが正規利用者からの新規接続を受け付けにくくなる理由を説明せよ。

答案例：「大量のSYNによって接続確立途中の状態が多数作られ、接続管理用の資源や処理能力が消費されるため。」

解説：単に「大量のパケットが送られるため」では不十分です。TCPのどの処理が負荷を受けるのかを示してください。

16-3. 設問例③：SYN Cookie

設問：SYN CookieがSYN Floodへの対策になる理由を説明せよ。

答案例：「SYN受信時に未完了接続の状態情報を大量に保持せず、初期シーケンス番号に符号化した情報を最終ACKで検証することで、接続管理資源の消費を抑えられるため。」

16-4. 設問例④：SYN再送の原因

設問：クライアントがSYNを繰り返し送信しているが、SYN+ACKを受信できない。考えられる原因を二つ挙げよ。

答案例：「送信したSYNがファイアウォールで破棄されていること、またはサーバからのSYN+ACKが戻り経路で破棄されていること。」

解説：送信方向だけでなく戻り方向にも着目することが重要です。

16-5. 設問例⑤：フロー制御と輻輳制御

設問：TCPのフロー制御と輻輳制御の違いを説明せよ。

答案例：「フロー制御は受信側の処理能力を超えないように送信量を調整し、輻輳制御はネットワークの混雑を抑えるために送信量を調整する。」

16-6. 記述答案の組み立て方

TCP関連の科目B問題では、次の順序で考えると答案が安定します。

  1. 通信の段階を特定する。 接続確立中、データ転送中、終了処理中のどこか。
  2. パケットの根拠を示す。 SYN、ACK、SEQ、ACK番号、RSTなどの情報を確認する。
  3. 原因と影響を結び付ける。 何が失われ、何が待機し、何が消費されるのか。
  4. 対応する対策を述べる。 例えばSYN FloodならSYN Cookieやレート制限など。

「TCP通信に問題があるため」といった抽象的な説明ではなく、具体的な通信状態と根拠を示してください。

17. 重要事項の整理

第一に、TCPはコネクション型のトランスポート層プロトコルです。 順序制御、確認応答、再送などによって信頼性のあるバイトストリームを提供します。

第二に、3ウェイハンドシェイクはSYN → SYN+ACK → ACKです。 両方向の初期シーケンス番号を通知・確認します。

第三に、TCPのシーケンス番号はバイト単位です。 SYNとFINはそれぞれ番号を1つ消費しますが、データを含まない通常のACKは番号を消費しません。

第四に、ACK番号は次に期待する番号です。 データの欠落がある場合、後続データが到着しても累積ACKが進まないことがあります。

第五に、フロー制御と輻輳制御は目的が異なります。 前者は受信側の能力、後者はネットワークの混雑を考慮します。

第六に、FINとRSTを区別します。 FINは送信方向の通常終了、RSTはコネクションのリセットに使用します。

第七に、SYN Floodは接続確立途中の状態を悪用するDoS攻撃です。 SYN Cookieなどが対策になります。

発展学習として分離した内容

  • TCPの全状態遷移とタイマの厳密な実装
  • Reno、CUBIC、BBRなどの輻輳制御アルゴリズムの詳細
  • TCP Timestamp、Window Scaleなどのオプションのビット単位の解析
  • OS固有のTCPパラメータ調整
  • TCP Fast Openなどの追加機能

まずは、3ウェイハンドシェイク、SEQ・ACK計算、再送、SYN Floodの原因と対策を確実に理解してください。
