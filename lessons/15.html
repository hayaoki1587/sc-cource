情報処理安全確保支援士（SC）合格講座｜第1〜23講・詳細再執筆

第14講では、IPv6のNDP、NS・NA、RS・RAを学びました。今回は、これらの基盤にもなっているICMP（Internet Control Message Protocol）を体系的に理解します。

ICMPは、IP通信で発生した問題を通知したり、通信経路を調査したりするためのプロトコルです。

SC試験では、単に「pingに使うプロトコル」と覚えるだけでは不十分です。ICMPのメッセージがなぜ発生するのか、どこから返されるのか、ログから何が分かるのか、どの通信を制限すべきかまで判断できるようにします。

1. 到達目標と参考書

到達目標

この講義では、次の七つを目指します。

  1. ICMPの役割と、IP・TCP・UDPとの関係を説明できる。
  2. Echo RequestとEcho Replyによるpingの仕組みを理解する。
  3. Destination Unreachable、Time Exceeded、Fragmentation Neededの意味を区別する。
  4. tracerouteが経路上のルータを調査する仕組みを説明できる。
  5. ICMPを悪用する攻撃と、その影響を説明できる。
  6. ICMPを一律遮断することの問題点を理解する。
  7. パケット情報やログを読み、科目Bで原因・根拠・対策を記述できる。

2. ICMPは何をするプロトコルなのか

2-1. IPだけでは通信の状態を十分に伝えられない

第12講で、IPはパケットを宛先まで届けるためのプロトコルだと学びました。

しかし、IPの基本的な転送機能だけでは、例えば次のような状況を送信元へ詳しく伝えられません。

  • 宛先ネットワークに到達できない。
  • パケットがルータ間を回り続けている。
  • パケットが大きすぎて次のリンクへ転送できない。
  • 宛先端末が応答可能な状態か調べたい。

そこで、IP通信に関する制御情報やエラー情報を通知するICMPを使用します。

2-2. ICMPとTCP・UDPの違い

プロトコル 主な役割
IP 宛先IPアドレスに基づくパケット転送
ICMP IP通信に関するエラー通知・状態確認など
TCP コネクション管理、信頼性のあるバイトストリーム転送
UDP コネクションレスのデータグラム転送

ICMPは、TCPのようにアプリケーション間で信頼性のあるデータ転送を提供するプロトコルではありません。

また、ICMPはTCPやUDPのポート番号を使用しません。

例えば、

TCP 443番ポート
UDP 53番ポート

という表現はありますが、通常、

ICMP 443番ポート

という表現はしません。

ICMPでは、Type（タイプ）とCode（コード）でメッセージの種類や詳細を区別します。

2-3. IPv4パケット内での位置付け

ICMPv4メッセージは、IPv4パケットのペイロードに格納されます。

ICMPv4を含むEthernetフレーム

┌────────────────────────────────────┐
│ Ethernetヘッダ                     │
│ 送信元MAC、宛先MAC、EtherTypeなど  │
├────────────────────────────────────┤
│ IPv4ヘッダ                         │
│ 送信元IP、宛先IP、TTL、Protocol=1  │
├────────────────────────────────────┤
│ ICMPメッセージ                     │
│ Type、Code、Checksumなど           │
└────────────────────────────────────┘

IPv4ヘッダのProtocol番号は、ICMPv4の場合 1 です。

比較すると、

Protocol 1  → ICMP
Protocol 6  → TCP
Protocol 17 → UDP

となります。

IPv6ではICMPv6のプロトコル番号は 58 です。

ICMPv4とICMPv6は密接に関連しますが、メッセージの種類や役割が完全に同一ではありません。

3. ICMPのTypeとCode

3-1. Typeはメッセージの大分類

ICMPメッセージには、Typeというフィールドがあります。

これは、メッセージの種類を識別します。

例えば、ICMPv4では次のようなTypeがあります。

Type メッセージ 意味
0 Echo Reply Echo Requestへの応答
3 Destination Unreachable 宛先へ届けられない
8 Echo Request 応答を要求する
11 Time Exceeded TTLなどの制限に達した
12 Parameter Problem IPヘッダなどの問題

すべてのType番号を丸暗記する必要はありません。

ただし、Echo Requestが8、Echo Replyが0、Destination Unreachableが3、Time Exceededが11という組合せは、パケットやログの読み取りに役立ちます。

3-2. Codeは詳細な理由

同じTypeでも、理由が異なる場合があります。

例えば、ICMPv4のDestination UnreachableはType 3です。

その中には、次のようなCodeがあります。

Type Code 意味
3 0 Network Unreachable
3 1 Host Unreachable
3 3 Port Unreachable
3 4 Fragmentation Needed and DF Set

ここで注意が必要です。

「Destination Unreachable」という名前だけを見て、すべて同じ原因だと判断してはいけません。

Typeで大分類を判断し、Codeで具体的な理由を判断します。

4. pingの仕組み

4-1. pingは何を確認するのか

pingは、対象ホストなどへICMP Echo Requestを送信し、Echo Replyが返ってくるか確認する診断手段です。

例えば、PC-AからサーバBへpingを実行します。

PC-A：192.168.1.10
サーバB：192.168.1.20

PC-Aは、サーバBへEcho Requestを送ります。

サーバBがそれを受信し、応答可能であればEcho Replyを返します。

PC-A（192.168.1.10）         サーバB（192.168.1.20）
        │                              │
        │ ① Echo Request（Type 8）    │
        ├─────────────────────────────>│
        │                              │
        │ ② Echo Reply（Type 0）      │
        │<─────────────────────────────┤
        │                              │

4-2. pingの結果例

$ ping 192.168.1.20

64 bytes from 192.168.1.20:
icmp_seq=1 ttl=64 time=1.2 ms

64 bytes from 192.168.1.20:
icmp_seq=2 ttl=64 time=1.0 ms

64 bytes from 192.168.1.20:
icmp_seq=3 ttl=64 time=1.1 ms

この出力から、少なくとも次のことが分かります。

  • Echo Replyを受信できた。
  • 各応答に対応するシーケンス番号を確認できる。
  • 往復時間の目安を確認できる。
  • 受信したIPv4パケットのTTLを確認できる。

time=1.2 ms は、通常、Echo Requestを送ってからEcho Replyを受け取るまでの往復時間です。

4-3. pingが成功してもアプリケーションが動くとは限らない

ここは非常に重要です。

pingが成功しても、例えばWebサーバのTCP 443番ポートが開いているとは限りません。

ICMP Echo Reply：成功
TCP 443接続　　：失敗

という状態は十分にあり得ます。

原因として、次のようなものがあります。

  • Webサーバのプロセスが停止している。
  • TCP 443番ポートがファイアウォールで遮断されている。
  • サービスが別のポートで待ち受けている。
  • アプリケーション側に障害がある。

したがって、pingの成功は、目的のアプリケーション通信の成功を保証しません。

4-4. pingが失敗してもホストが停止しているとは限らない

逆も重要です。

pingが失敗した場合、対象ホストが停止しているとは限りません。

例えば、サーバがEcho Requestに応答しない設定であっても、HTTPS通信は正常にできる場合があります。

ICMP Echo Reply：なし
HTTPS通信　　 ：成功

このような構成は矛盾ではありません。

ファイアウォールやOSの設定によって、ICMP Echo Requestへの応答を制限できるからです。

4-5. pingで判断できること・できないこと

判断対象 pingだけで判断できるか
Echo Replyを受信できたか できる
ICMPの往復時間 目安を確認できる
途中経路に障害がないか 限定的
Webサービスが正常か できない
TCPポートが開いているか できない
相手の本人性が保証されるか できない

科目Bでは、「pingが成功したから通信に問題はない」と結論付けないようにしてください。

5. Destination Unreachable

5-1. 宛先へ届けられないことを通知する

Destination Unreachableは、パケットを宛先へ届けられない場合などに送信されるICMPエラーメッセージです。

例えば、次の構成を考えます。

PC-A
192.168.1.10
    |
    v
ルータR
192.168.1.1
    |
    X  宛先ネットワークへの経路がない
    |
203.0.113.10

PC-Aは 203.0.113.10 へパケットを送信します。

ルータRが宛先への転送経路を持たず、パケットを転送できない場合、Destination Unreachableを返すことがあります。

ここで重要なのは、エラーを通知する機器が必ず最終宛先とは限らないことです。

途中のルータが通知する場合もあります。

5-2. Port Unreachable

UDPを使用する場合、宛先ホストに該当するUDPポートの受信先が存在しないと、ICMP Port Unreachableが返されることがあります。

例えば、

送信元：192.168.1.10
宛先　：192.168.1.20
UDP宛先ポート：9999

というUDPデータグラムを送信したとします。

宛先ホストにUDP 9999番ポートで受信するアプリケーションが存在しなければ、Port Unreachableが返される場合があります。

ただし、ファイアウォールがパケットを破棄したり、応答を制限したりする場合には、エラーメッセージが返らないこともあります。

5-3. TCPの接続拒否とは異なる

TCPで待受けのないポートへ接続しようとした場合、通常はTCP RSTが返されることがあります。

これはICMP Port Unreachableとは異なります。

状況 代表的な応答
UDPの未使用ポート ICMP Port Unreachable
TCPの未使用ポート TCP RST
FWが通信を破棄 応答なしの場合もある
FWが明示的に拒否 TCP RSTやICMPエラーなど、設定による

試験では、TCPとUDPの動作を混同しないことが重要です。

6. TTLとTime Exceeded

6-1. TTLは何のためにあるのか

IPv4ヘッダにはTTL（Time To Live）があります。

TTLは、パケットがルータを通過するたびに減少する値です。

例えば、送信元がTTLを4に設定したとします。

送信元 → R1 → R2 → R3 → R4 → 宛先
 TTL=4   3    2    1    0

ルータがTTLを減らした結果、0になる場合、パケットは破棄されます。

これにより、ルーティングループが発生しても、パケットが無限に転送され続けることを防ぎます。

6-2. Time Exceeded

ルータがTTLの期限切れでパケットを破棄した場合、通常、送信元へICMP Time Exceededを返します。

ICMPv4では、

Type：11
Code：0

がTTL超過によるTime Exceededを示します。

ただし、ネットワーク機器の設定やレート制限などによって、必ず通知が返るとは限りません。

6-3. ルーティングループの例

次のような誤設定があったとします。

ルータA：
10.10.20.0/24 はルータBへ転送

ルータB：
10.10.20.0/24 はルータAへ転送

宛先 10.10.20.10 のパケットが、

ルータA → ルータB → ルータA → ルータB → …

と転送される可能性があります。

しかしTTLは減少し続けるため、最終的には破棄されます。

ここで、ICMP Time Exceededが送信元に返されることがあります。

Time Exceededはルーティングループの調査材料になりますが、Time Exceededを受信しただけでループの存在が確定するわけではありません。

後述するtracerouteでも、意図的にTTLを小さくしたパケットによってTime Exceededを発生させるからです。

7. tracerouteの仕組み

7-1. tracerouteは何を調べるのか

tracerouteは、宛先までの経路上にあるルータを調査するためのツールです。

IPv4では、TTLを小さな値から順番に増やしてパケットを送信し、途中のルータから返るICMP Time Exceededなどを利用する方式があります。

例えば、送信元PCからサーバまで、三つのルータを通過するとします。

PC → R1 → R2 → R3 → サーバ

7-2. TTLを1にして送信

最初にTTLを1にして送信します。

PC → R1
     TTLが0になり破棄

R1がICMP Time Exceededを返せば、PCは最初のホップにあるルータを知ることができます。

7-3. TTLを2にして送信

次にTTLを2にして送信します。

PC → R1 → R2
          TTLが0になり破棄

R2がICMP Time Exceededを返せば、二番目のホップを知ることができます。

7-4. TTLを3、4と増やす

同じ方法でTTLを増やします。

TTLを増やして経路を調べる

PC ─── R1 ─── R2 ─── R3 ─── サーバ
       1      2      3       4 ホップ目
送信TTL 期限切れ・到達地点 観測する応答
TTL=1 R1で期限切れ R1から応答
TTL=2 R2で期限切れ R2から応答
TTL=3 R3で期限切れ R3から応答
TTL=4 サーバへ到達 方式に応じた応答

7-5. tracerouteは必ずICMP Echo Requestを送るのか

いいえ。

tracerouteの送信パケットは、OSやツール、指定オプションによって異なります。

例えば、UDPデータグラム、ICMP Echo Request、TCP SYNなどを利用する実装があります。

ただし、途中のルータからICMP Time Exceededを受け取るという基本的な考え方は共通します。

UDP方式では、最終宛先の未使用UDPポートに到達すると、ICMP Port Unreachableが返され、それを到達の判断に利用する場合があります。

7-6. tracerouteの出力例

traceroute to 203.0.113.10

1  192.168.1.1      1.0 ms
2  10.0.0.1         4.5 ms
3  * * *
4  203.0.113.10    15.2 ms

3ホップ目が * * * になっています。

これは、3ホップ目のルータから期待する応答が得られなかったことを示します。

しかし、4ホップ目の宛先から応答が得られています。

したがって、3ホップ目の * * * だけを根拠に、その地点で通信が途絶えていると断定することはできません。

考えられる理由には、ICMPの応答制限、フィルタリング、レート制限などがあります。

7-7. 経路調査の限界

tracerouteの結果は、実際の通信経路を調べる重要な材料ですが、すべてのルータが必ず応答するわけではありません。

また、負荷分散や経路変更によって、複数回の調査で結果が変わる場合もあります。

そのため、障害調査ではtracerouteの結果だけでなく、ルーティングテーブル、ファイアウォールログ、通信の送受信記録などと照合します。

8. MTUとPath MTU Discovery

8-1. MTUとは

MTU（Maximum Transmission Unit）は、あるリンクで転送できるネットワーク層パケットの最大サイズを表します。

例えば、一般的なEthernetでは、IPパケットのMTUとして1500バイトが使われます。

ただし、VPNやトンネルなどを経由する場合、途中の経路で利用できるMTUが小さくなることがあります。

8-2. Path MTU Discoveryとは

Path MTU Discovery（PMTUD）は、送信元から宛先までの経路で利用可能なMTUを調べ、適切なパケットサイズで通信するための仕組みです。

例えば、

送信元PC
   |
   | MTU 1500
   v
ルータA
   |
   | MTU 1400
   v
ルータB
   |
   v
宛先サーバ

という経路を考えます。

送信元PCが1500バイトのIPv4パケットを送り、DF（Don't Fragment）フラグが設定されているとします。

ルータAが、そのパケットをMTU 1400のリンクへ転送しようとすると、パケットを分割できません。

そこで、パケットを破棄し、送信元へICMPのFragmentation Neededを返すことがあります。

8-3. Fragmentation Needed

IPv4では、

ICMP Type：3
Code     ：4

が、DFフラグによってフラグメント化できないことを示すメッセージです。

この通知によって、送信元はより小さなパケットサイズを使う必要があると判断できます。

IPv6では途中のルータがフラグメント化を行わず、ICMPv6 Packet Too Bigによって通知します。

8-4. ICMPを遮断した場合

ここでファイアウォールが、必要なICMPエラーメッセージを遮断していたとします。

送信元は、途中の経路でパケットが大きすぎることを把握できない場合があります。

その結果、

  • 小さいデータは送受信できる。
  • 大きいデータの送信で通信が停止する。
  • 特定のWebサイトやVPNだけ通信が不安定になる。

といった症状が発生する可能性があります。

これを、Path MTU Discoveryの失敗によるブラックホール現象などと呼ぶことがあります。

8-5. 科目Bでの説明方法

設問例

VPN経由の通信で、小さなパケットは正常に送信できるが、大きなパケットは送信できない。ファイアウォールでICMP Fragmentation Neededを遮断していた。原因を説明せよ。

答案例

「経路上のMTUを超えるパケットを分割できない際のICMP通知が遮断され、送信元が適切なパケットサイズへ調整できないため。」

このように、MTU超過 → 通知の遮断 → サイズ調整失敗 → 通信障害という因果関係で説明します。

9. ICMPを悪用する攻撃

ICMPは診断やエラー通知に必要ですが、攻撃に悪用されることもあります。

9-1. ICMP Flood

ICMP Floodは、大量のICMPメッセージを送り、ネットワーク帯域や機器の処理能力を消費させるDoS攻撃の一種です。

例えば、大量のEcho Requestを送信し、対象サーバに処理や応答を発生させることが考えられます。

ただし、実際の負荷や影響は、機器の実装、パケット量、通信経路、制限設定などに依存します。

9-2. Smurf攻撃

Smurf攻撃は、送信元IPアドレスを被害者のアドレスに偽装し、ブロードキャスト宛てのICMP Echo Requestを利用して、多数の応答を被害者へ集中させる攻撃です。

概念的には次の流れです。

攻撃者
  |
  | 送信元IPを被害者に偽装
  | Echo Requestをブロードキャスト宛てに送信
  v
複数の端末
  |
  | Echo Replyを送信
  v
被害者

一つの要求によって多数の応答が発生すると、通信量が増幅されます。

ただし、現在の一般的なネットワークでは、ディレクテッドブロードキャストの転送禁止や、ブロードキャスト宛てEcho Requestへの応答抑制などによって対策されていることが多く、古典的な攻撃例として理解するのが適切です。

攻撃成立のポイントは、送信元IPアドレスの偽装と、複数端末からの応答による増幅です。

9-3. ICMPを使った情報収集

攻撃者はpingなどを利用して、応答する端末や到達可能なネットワークを調査する場合があります。

ただし、ICMPに応答しない機器も存在するため、応答がないことは端末が存在しない証拠にはなりません。

9-4. ICMPトンネリング

ICMPメッセージにデータを格納し、通常とは異なる用途で情報をやり取りする手法があります。

例えば、攻撃者がICMPを利用して不正な通信路を作ろうとする場合があります。

これはICMPトンネリングと呼ばれることがあります。

ただし、ICMPを利用した通信がすべて不正なわけではありません。パケットの内容、通信量、頻度、送信先などを総合的に確認する必要があります。

9-5. 攻撃と対策の整理

攻撃・悪用 主な問題 対策の考え方
ICMP Flood 帯域や処理能力の消費 レート制限、DoS対策
Smurf攻撃 応答の増幅による負荷 ブロードキャスト転送の制限、送信元偽装対策
ICMPによる探索 ネットワーク情報の収集 必要に応じた応答制限、監視
ICMPトンネリング 不正な通信路の形成 通信内容・振る舞いの監視、適切な制御

10. ICMPに対するセキュリティ対策

10-1. ICMPをすべて遮断すれば安全か

必ずしもそうではありません。

ICMPには、正常な通信や障害調査に必要なメッセージがあります。

特に、Destination Unreachableの一部やPath MTU Discoveryに関係するメッセージを無条件に遮断すると、通信障害の原因になる場合があります。

一方、不要なEcho Requestへの応答や、大量のICMP通信を制限することには意味があります。

したがって、重要なのは用途に応じた選択的な許可・拒否です。

10-2. Echo Requestの制限

例えば、インターネットから社内の管理サーバへのEcho Requestを拒否する構成が考えられます。

これにより、外部からの単純なICMP探索を制限できます。

ただし、これだけで管理サーバへの不正アクセスを防げるわけではありません。

SSHやHTTPSなどの管理サービスについても、送信元や認証方式を適切に制御する必要があります。

10-3. レート制限

ICMPの送受信量を制限することで、大量のメッセージによる負荷を抑えることができます。

例えば、ルータがICMPエラーを大量に生成すると、転送処理に影響する場合があります。

そのため、ICMPエラーの生成や応答をレート制限する機能が使われることがあります。

ただし、必要な通知まで過度に制限すると、障害調査が難しくなったり、通信に影響したりする可能性があります。

10-4. 送信元IPアドレスの偽装対策

Smurf攻撃のような送信元IPアドレスの偽装を悪用する攻撃に対しては、ネットワーク境界で不正な送信元アドレスを持つパケットを遮断することが重要です。

例えば、内部ネットワークから外部へ送信するパケットの送信元が、組織に割り当てられていないアドレスであれば、異常な通信として制限する方法があります。

これは、送信元アドレスの妥当性を確認するフィルタリングの考え方です。

10-5. IPv4とIPv6でポリシーを分けて考える

第14講で学んだとおり、IPv6ではICMPv6が近隣探索やルータ発見にも使われます。

したがって、IPv4で設定しているICMPの遮断ルールを、そのままIPv6に適用することは適切でない場合があります。

ICMPv4とICMPv6は、必要なメッセージをそれぞれ確認して制御する必要があります。

11. ファイアウォールとICMPログの読み取り

11-1. Echo Requestのログ

次のログを考えます。

2026-10-12 10:00:01
Action      : DENY
Source IP   : 198.51.100.10
Destination : 203.0.113.20
Protocol    : ICMP
Type        : 8
Code        : 0

ICMPv4のType 8はEcho Requestです。

このログから、送信元 198.51.100.10 が宛先 203.0.113.20 へ送ったEcho Requestが拒否されたと分かります。

ただし、このログだけで送信元が攻撃者だと断定することはできません。

正当な監視や疎通確認の可能性もあります。

11-2. Time Exceededのログ

2026-10-12 10:05:30
Source IP   : 10.0.0.2
Destination : 192.168.1.10
Protocol    : ICMP
Type        : 11
Code        : 0

Type 11、Code 0は、TTLの期限切れに関するTime Exceededです。

このログから、ルータなどがTTLの期限切れを通知していると判断できます。

ただし、原因がルーティングループなのか、tracerouteのような診断通信なのかは、追加の情報が必要です。

11-3. Fragmentation Neededのログ

2026-10-12 10:10:20
Action      : DENY
Protocol    : ICMP
Type        : 3
Code        : 4

このログは、IPv4のFragmentation Neededが拒否されたことを示します。

もし同時期に、VPN経由で大きなデータだけ通信できない障害が発生していた場合、Path MTU Discoveryに必要な通知の遮断が原因の一つとして疑われます。

ただし、ログの存在と通信障害の因果関係は、パケットキャプチャやMTU設定などによって確認する必要があります。

13. 科目Bの答案作成ポイント

13-1. 設問例①：pingの失敗

設問

あるサーバに対してpingが失敗した。管理者は「サーバが停止している」と判断した。この判断が適切でない理由を説明せよ。

答案例

「ファイアウォールやサーバの設定によってICMP Echo RequestまたはEcho Replyが制限されている可能性があり、pingの失敗だけではサーバ停止を断定できないため。」

ポイント

「ping失敗＝サーバ停止」と決め付けないことが重要です。

13-2. 設問例②：tracerouteの途中で応答がない

設問

tracerouteの結果で3ホップ目が * * * となったが、4ホップ目の宛先から応答があった。3ホップ目で通信が停止したと判断できない理由を説明せよ。

答案例

「3ホップ目のルータがICMP Time Exceededを返さない設定や制限を行っている可能性があり、後続の宛先から応答が得られているため。」

ポイント

途中ルータからのICMP応答と、実際のパケット転送は区別します。

13-3. 設問例③：PMTUDの障害

設問

大きなパケットを送る通信だけが失敗しており、ICMP Fragmentation Neededが遮断されていた。原因を説明せよ。

答案例

「経路のMTUを超えるパケットを分割できない際の通知が遮断され、送信元が適切なパケットサイズに調整できないため。」

ポイント

単に「ICMPを遮断したから」ではなく、通知の役割とサイズ調整の失敗を結び付けます。

13-4. 設問例④：ICMP Flood

設問

大量のICMP Echo Requestがサーバに送信されている。想定される影響と対策を説明せよ。

答案例

「大量のICMP通信によってサーバやネットワークの処理能力が消費される可能性があるため、通信量の監視や適切なレート制限を行う。」

ポイント

攻撃による影響と、対応する防御策を具体的に示します。

13-5. 設問例⑤：ICMPの一律遮断

設問

セキュリティ強化のため、すべてのICMP通信を遮断することが提案された。問題点を説明せよ。

答案例

「経路MTUの通知など、正常なIP通信に必要なICMPメッセージまで遮断し、通信障害を引き起こす可能性があるため。」

ポイント

必要なメッセージまで遮断してしまうことが問題です。

14. 重要事項の整理

今回の講義で特に重要な事項を整理します。

第一に、ICMPはIP通信に関するエラー通知や状態確認などを行うプロトコルです。 TCPやUDPのようにアプリケーションデータの転送を担うものではありません。

第二に、pingはICMP Echo RequestとEcho Replyなどを利用します。 ただし、pingの成功はアプリケーションの正常動作を保証せず、失敗もホスト停止を意味するとは限りません。

第三に、Destination Unreachableは、パケットを宛先へ届けられない状況などを通知します。 TypeとCodeを組み合わせて理由を判断します。

第四に、Time ExceededはTTLの期限切れなどを通知します。 tracerouteでは、TTLを変化させて途中のルータを調査します。

第五に、ICMPはPath MTU Discoveryにも関係します。 必要なエラーメッセージを遮断すると、大きなパケットを送る通信で障害が発生する場合があります。

第六に、ICMPは攻撃にも悪用されます。 ICMP Flood、Smurf攻撃、情報収集、不正なトンネリングなどが例です。

第七に、ICMPを一律遮断するのではなく、必要なメッセージを適切に許可し、不正な通信や過剰な通信を制限します。
