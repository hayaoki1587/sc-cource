第17講｜UDP

情報処理安全確保支援士（SC）合格講座｜第1〜23講・詳細再執筆シリーズ

第16講ではTCPの3ウェイハンドシェイク、シーケンス番号、ACK、再送制御、SYN Floodを学びました。今回のテーマはもう一つの代表的なトランスポート層プロトコルであるUDP（User Datagram Protocol）です。

UDPはTCPと違い、コネクションを確立せず、データの到達確認や再送を標準機能として行いません。しかし「UDPはTCPより簡単で高速」という理解だけではSC試験の科目Bには対応できません。UDPがなぜDNSなどで利用されるのか、なぜ送信元IPアドレスの偽装を利用した攻撃に悪用されやすいのか、通信ログから攻撃と正常通信をどう区別するのかを重視します。

第17講は既修了講義の再執筆です。既存の採点・弱点履歴は保持し、確認問題は再学習用として扱います（本HTMLには理解度チェックを収録しません）。

2. UDPは何をするプロトコルなのか

2-1. トランスポート層の役割

トランスポート層には、主に受信したデータを適切なアプリケーションへ渡す役割があります。一台のサーバでDNSとWebサービスが稼働している例を考えます。

サーバ：192.0.2.10
DNSサーバ       UDP 53番ポート
Webサーバ       TCP 443番ポート

IPアドレスが同じでも、トランスポート層のプロトコルとポート番号によって、通信を適切に振り分けられます。

2-2. UDPはコネクションレス型

UDPはTCPのような3ウェイハンドシェイクを行いません。送信側は宛先IPアドレスと宛先ポート番号などを指定してデータグラムを送信します。

送信元：192.0.2.100:53000
宛先　：192.0.2.10:53

事前にSYN、SYN+ACK、ACKを交換する必要はありません。ただし、コネクションレスとは、通信相手を一切識別しないという意味ではありません。IPアドレスやポート番号で通信を識別でき、アプリケーション側でセッションを管理することもできます。

2-3. UDPはデータグラム型

TCPは順序のあるバイトストリームを提供します。一方、UDPは個々のメッセージの境界を保つデータグラム型です。

送信①：「ABC」
送信②：「DEFG」
送信③：「HI」

UDPはそれぞれを別のデータグラムとして扱います。TCPの場合は、送信時のデータの区切りがそのまま受信側に保証されるわけではありません。

2-4. UDPが保証しないこと

  • データが相手に到達したことの確認
  • 消失したデータの自動再送
  • 送信順序どおりの受信
  • 重複データの排除
  • TCPのようなフロー制御・輻輳制御
送信側                    受信側
① ────────────────────→ ①
② ─────────── X          消失
③ ────────────────────→ ③

UDP自体は②の消失を検出して自動再送しません。ただし、アプリケーションが独自に確認応答や再送を行うことは可能です。「UDPには再送機能がない」と「UDPを利用する通信では再送できない」は別の意味です。

3. TCPとUDPの違いを整理する

3-1. 基本的な比較

項目 TCP UDP
通信方式 コネクション型 コネクションレス型
データ形式 バイトストリーム データグラム
接続確立 通常3ウェイハンドシェイク 不要
順序制御 あり UDP自体にはなし
再送制御 あり UDP自体にはなし
フロー制御 あり UDP自体にはなし
輻輳制御 あり UDP自体にはなし
基本ヘッダ長 20バイト 8バイト
主な用途 HTTPS、SSH、メールなど DNS、音声・映像通信、QUICなど

3-2. UDPは必ずTCPより速いのか

UDPはTCPよりヘッダが小さく、接続確立や確認応答などの処理を標準では行いません。低遅延が求められる用途に適していますが、UDPを使用すれば必ずTCPより高速になるわけではありません。UDP上のアプリケーションが厳密な再送・順序制御を実装すれば処理が必要です。性能はネットワーク品質、アプリケーションの実装、輻輳制御の方式などにも左右されます。

3-3. UDPを使う理由

① 接続確立の往復を省きたい。 小さな要求と応答をやり取りするDNSなどでは、事前のTCP接続確立を省けることが利点になります。

② 古いデータより新しいデータを優先したい。 リアルタイム音声では遅れて届いた古いデータより、現在の音声を再生することが重要な場合があります。

③ アプリケーションに合わせた制御を実装したい。 QUICのようにUDP上で暗号化、信頼性制御、輻輳制御などを実装するプロトコルもあります。UDPは「信頼性が不要な通信専用」ではありません。

4. UDPヘッダの構造

B：理解補助。ただしポート番号はA：必須

4-1. UDPヘッダは8バイト

UDPの基本ヘッダは四つのフィールドで構成されます。

先頭16ビット 次の16ビット
送信元ポート番号（16bit） 宛先ポート番号（16bit）
Length（16bit） Checksum（16bit） 
┌────────────────────────┬────────────────────────┐
│ 送信元ポート（16bit）  │ 宛先ポート（16bit）    │
├────────────────────────┼────────────────────────┤
│ Length（16bit）        │ Checksum（16bit）      │
└────────────────────────┴────────────────────────┘
│ データ（可変長）                                │
└─────────────────────────────────────────────────┘

16ビット×4フィールド＝64ビット＝8バイトです。TCPに存在するシーケンス番号、確認応答番号、SYN・FINなどの制御フラグ、ウィンドウサイズはUDPヘッダにはありません。

4-2. 送信元・宛先ポート番号

送信元IP：192.0.2.100
送信元UDPポート：53000
宛先IP：192.0.2.53
宛先UDPポート：53

宛先ポート53はDNSサービスへの問い合わせを示します。送信元ポート53000は、応答をクライアント側の適切な通信へ対応付けるために使用されます。UDPポート番号は16ビットで0〜65535ですが、利用可能なポートや割当てには用途・OS上の制約があります。

4-3. Length

LengthフィールドはUDPヘッダとUDPデータを合わせた長さです。

UDPヘッダ：8バイト
UDPデータ：100バイト
UDP Length = 108バイト

IPパケット全体の長さと混同しないようにします。

4-4. Checksum

UDPチェックサムは、UDPヘッダやデータなどの破損を検出します。送信元・宛先IPアドレスなどを含む疑似ヘッダも計算に使われます。ただし、暗号学的な認証ではありません。攻撃者はチェックサムを正しく計算できます。チェックサムが正しくても送信元IPアドレスが本物であることは保証されません。 IPv4のUDPではチェックサムを使用しないことも規格上可能ですが、IPv6のUDPでは原則必須です（特定用途の例外あり）。

5. UDP通信の具体的な流れ

5-1. DNSの名前解決を例にする

クライアントPC 192.0.2.100 がDNSサーバ 192.0.2.53 に www.example.com のIPアドレスを問い合わせます。

クライアントPC                        DNSサーバ
192.0.2.100:53000                    192.0.2.53:53
       │                                     │
       │ ① DNS Query（UDP 53000 → 53）     │
       ├────────────────────────────────────→│
       │                                     │
       │ ② DNS Response（UDP 53 → 53000）   │
       │←────────────────────────────────────┤
       │                                     │

5-2. 第1段階：DNS Query

Source IP   : 192.0.2.100
Source Port : 53000
Destination IP   : 192.0.2.53
Destination Port : 53
Protocol : UDP

この段階ではTCPの3ウェイハンドシェイクは発生しません。

5-3. 第2段階：DNS Response

Source IP   : 192.0.2.53
Source Port : 53
Destination IP   : 192.0.2.100
Destination Port : 53000
Protocol : UDP

要求と応答では送信元・宛先のIPアドレスとポート番号が入れ替わります。

5-4. UDPに接続確立がなくても応答を対応付けられる理由

DNSなどのアプリケーションはUDPのIPアドレスとポート番号に加え、アプリケーションプロトコル自身の識別情報を使用します。DNSにはトランザクションIDがあります。正当な応答か判断する際には送信元IP、ポート、問い合わせ内容なども重要です。UDPにTCPのコネクション管理がないことと、アプリケーションが要求・応答を対応付けられないことは別です。

6. UDPの信頼性とアプリケーション側の制御

6-1. 応答がないとき何が起こるか

PC                         DNSサーバ
DNS Query ───────────────→ 受信
          ←───── X          DNS Response消失

UDP自体にDNS Queryを再送する機能はありません。しかしDNSクライアントの処理として、一定時間待って再問い合わせしたり別のDNSサーバへ問い合わせたりできます。UDP上で再送が観測されてもUDPプロトコル自身が再送したとは限りません。

6-2. 順序が逆転した場合

送信：① → ② → ③
受信：② → ① → ③

UDP自体は元の順序に並べ替えません。必要ならアプリケーション側でシーケンス番号などを用意します。

6-3. リアルタイム音声の例

20ミリ秒ごとの音声データを送る場合を考えます。

音声① → 音声② → 音声③ → 音声④

音声②が消失して再送しても、到着が遅すぎれば再生に間に合いません。欠落を補間したり次の音声へ進んだりする方が適切なことがあります。重視されるのは完全な再送より再生時刻に間に合うことです。ただし、すべての音声・映像通信がUDPを使うわけではありません。

7. UDPとICMP Port Unreachable

B：第15講との接続

7-1. 宛先ポートで受信するサービスがない場合

UDPの宛先ホストに該当ポートの受信先が存在しない場合、ICMP Port Unreachableが返ることがあります。

PC：192.0.2.100
サーバ：192.0.2.10
UDP宛先ポート：9999

ICMPv4
Type = 3
Code = 3

7-2. UDPではTCP RSTを返さない

UDPにはRSTフラグがありません。

状況 代表的な応答
TCPの未使用ポートへSYN TCP RSTなど
UDPの未使用ポートへデータ送信 ICMP Port Unreachableなど
FWが黙って破棄 応答なしの場合もある

7-3. 応答がないことの意味

  • 宛先ポートにサービスが存在しない。
  • ファイアウォールがUDPを破棄している。
  • サービスは存在するがアプリケーションが応答しない。
  • 応答パケットが途中で失われた。
  • ICMPエラーの生成・送信が制限されている。

UDPで応答がないことだけを根拠に、ポートが閉じていると断定できません。

8. UDPが攻撃に悪用されやすい理由

A：必須

8-1. 3ウェイハンドシェイクがない

TCPでは通常SYN、SYN+ACK、ACKを交換しますがUDPにはありません。UDPサービスは受信したデータグラムを処理し、送信元IPアドレスとポート番号に応答することがあります。送信元IPが偽装されていても、アプリケーションが見抜けるとは限りません。

8-2. IPスプーフィング

IPスプーフィングは送信元IPアドレスを偽装することです。

実際の送信者：攻撃者
IPヘッダの送信元：203.0.113.100（被害者）
IPヘッダの宛先：192.0.2.53（DNSサーバ）

DNSサーバが送信元と記載された 203.0.113.100 へ応答すると、問い合わせを送っていない被害者へDNS応答が届きます。

8-3. TCPでは送信元偽装が不可能なのか

TCPでも送信元IPアドレスを偽装したパケットを送れます。ただし通常のTCP接続を確立するにはSYN+ACKに対応するACKが必要です。偽装した攻撃者が戻り通信を受信できなければ難しくなります。一方UDPサービスには、接続確立の確認なしに応答を返すものがあります。

8-4. 重要な区別

用語 意味
IPスプーフィング 送信元IPアドレスを偽装する
リフレクション攻撃 第三者のサーバに被害者宛ての応答を送らせる
増幅攻撃 小さな要求から大きな応答などを発生させ通信量を増やす

リフレクションと増幅は組み合わされることが多いものの、意味は異なります。

9. UDP Flood攻撃

9-1. UDP Floodとは

大量のUDPデータグラムを対象へ送信し、ネットワーク帯域やサーバ・ネットワーク機器の処理能力を消費させるDoS攻撃です。

  • 受信回線の帯域が消費される。
  • サーバが大量のパケットを処理する。
  • ファイアウォールやルータの処理能力が消費される。
  • 宛先ポートが閉じている場合、ICMPエラーの生成負荷が生じることがある。

9-2. UDP Floodの流れ

攻撃者・複数の攻撃端末
      |
      | 大量のUDPデータグラム
      v
インターネット
      |
      v
被害サーバ
      |
      ├─ 回線帯域の消費
      ├─ パケット処理負荷
      └─ 正規通信の遅延・失敗

9-3. SYN Floodとの違い

項目 SYN Flood UDP Flood
主な対象 TCP接続確立処理 UDP受信・転送処理や帯域
利用する通信 TCP SYN UDPデータグラム
典型的な負荷 未完了接続の状態管理 帯域・パケット処理
代表的な対策 SYN Cookie、SYN Proxyなど レート制限、フィルタリング、DDoS対策

SYN CookieはTCPの接続確立処理に対する対策であり、UDP Floodの直接的な対策ではありません。

9-4. 対策

サーバが処理しきれない場合は手前で不要なUDPを制限します。しかし回線自体が大量通信で埋まっている場合、サーバ側FWで遮断しても回線の混雑は解消できません。ISPやDDoS対策サービスなど、被害組織の回線へ到達する前の段階で通信を処理する対策が必要です。

10. DNSリフレクション攻撃

A：必須・科目B重点

10-1. 攻撃の全体像

DNSリフレクション攻撃はDNSサーバを第三者への応答の中継役として悪用します。攻撃者はDNS Queryの送信元IPアドレスを被害者のIPアドレスに偽装し、DNSサーバはそのIPへDNS Responseを送信します。被害者へDNS応答が集中します。

10-2. 具体例

攻撃者    ：198.51.100.10
DNSサーバ ：192.0.2.53
被害者    ：203.0.113.100

① 攻撃者 → DNSサーバ
   DNS Query送信（IP送信元は被害者に偽装）
   Source: 203.0.113.100 → Destination: 192.0.2.53

② DNSサーバ → 被害者
   DNS Response送信
   Source: 192.0.2.53 → Destination: 203.0.113.100

③ 被害者へ多数の応答が集中
   被害者は問い合わせていないのに応答を受信する

10-3. 攻撃者が直接被害者へ送らない理由

DNSサーバが応答パケットの送信元になるため、被害者から見ると通信元はDNSサーバです。攻撃者は第三者のDNSサーバを利用して通信を集中させます。これが「反射（reflection）」と呼ばれる理由です。

10-4. オープンリゾルバの問題

不特定多数から再帰問い合わせを受け付けるDNSキャッシュサーバはオープンリゾルバと呼ばれます。攻撃者が利用できると偽装した送信元IPへDNS応答を発生させられる可能性があります。再帰問い合わせを許可する送信元を正当な利用者に限定することが重要です。ただし権威DNSサーバは外部からの問い合わせに応答する必要がある場合があり、すべてのDNSサーバの外部問い合わせを禁止すればよいわけではありません。

11. DNS増幅攻撃

11-1. リフレクションと増幅の違い

リフレクションでは第三者DNSサーバから被害者へ応答を送らせます。小さな問い合わせに対して大きな応答を返させることで通信量を増やすのがDNS増幅攻撃です。

11-2. 増幅率の例

DNS Query   ：100バイト
DNS Response：2,000バイト
増幅率 = 2,000 ÷ 100 = 20倍

説明用の例であり、すべてのDNS通信が20倍になるわけではありません。応答サイズは問い合わせ内容、DNS設定、EDNS、応答データなどによって変わります。

11-3. なぜDNSで大きな応答が発生するのか

問い合わせ内容によって複数のリソースレコードが含まれる場合があります。DNSSECの署名情報などで応答が大きくなることもあります。DNSSECは真正性検証の重要な仕組みであり、DNSSEC自体が攻撃を目的としているのではなく、大きな応答が生じ得る性質が悪用されます。

11-4. DNS増幅攻撃の成立条件

  1. 攻撃者が送信元IPアドレスを偽装できる。
  2. DNSサーバが偽装された送信元に応答する。
  3. 問い合わせに対して大きな応答が発生する。
  4. 多数の問い合わせ・DNSサーバを利用して被害者へ応答を集中させる。

送信元IPアドレスの偽装を防ぐことは重要な防御策です。

11-5. DNS増幅攻撃への対策

対策 防ぐ対象・効果
送信元IPアドレスの検証 偽装した送信元からのパケット送出を抑える
オープンリゾルバの解消 不特定多数による再帰問い合わせの悪用を抑える
DNS応答のレート制限 過剰な応答を抑える
DDoS対策サービス 被害者へ集中する大量通信を上流で処理する
DNSサーバの役割分離・適切な設定 必要な問い合わせだけを処理する構成にする

12. NTPリフレクション攻撃

A：攻撃の構造と対策／B：NTP固有の背景

12-1. NTPとは

NTP（Network Time Protocol）はコンピュータやネットワーク機器の時刻同期のためのプロトコルで、通常UDP 123番ポートを使用します。機器のログ時刻が大きくずれると、インシデント調査で順序を判断できなくなります。

12-2. NTPリフレクション

攻撃者が送信元IPを被害者に偽装してNTPサーバへ要求を送り、NTPサーバから被害者へ応答を送らせます。基本構造はDNSリフレクションと同じです。

12-3. monlistの悪用

参考書では古いNTP管理・状態確認機能 monlist を悪用した増幅攻撃が紹介されています。小さな要求に対して多数の情報を含む応答が返る場合がありました。ただし、monlistはすべての現行NTPサーバに存在する機能ではありません。旧式実装における代表例として理解します。

12-4. 対策

不要な monlist 機能を無効化します。加えてNTPソフトウェアを更新し、不要な管理用機能を外部公開せず、問い合わせ元を適切に制限します。

12-5. DNSとNTPの共通点

項目 DNSリフレクション NTPリフレクション
主な通信 UDP 53 UDP 123
攻撃の基本 偽装した送信元への応答 偽装した送信元への応答
増幅の要因 要求より大きなDNS応答 特定の管理要求などへの大きな応答
代表的な対策 再帰問い合わせ制限、応答制御 不要な管理機能の無効化、アクセス制限
共通対策 送信元IP偽装対策、DDoS対策 送信元IP偽装対策、DDoS対策

サービス名よりも、IPスプーフィングと応答の反射・増幅という共通構造を理解します。

13. UDPに対するセキュリティ対策

13-1. 送信元IPアドレスの偽装を防ぐ

リフレクション攻撃では攻撃者が被害者のIPを送信元に指定します。ネットワーク境界で送信元IPの妥当性を検証することが重要です。

社内ネットワーク：192.0.2.0/24

このネットワークから外へ出るパケットの送信元がまったく別のアドレスなら遮断する構成が考えられます。送信元アドレス検証、イングレス・エグレスフィルタリングの考え方です。

13-2. 外部から内部アドレスを名乗るパケット

インターネット
       |
       | 送信元IP：社内アドレス
       v
社内境界FW
       |
       X  不正な送信元として遮断
       |
社内ネットワーク

外部インターフェースから自組織内部のアドレスを名乗るパケットが来たら偽装を疑います。ただしVPN、トンネル、特殊なルーティングなど正当な構成を考慮します。

13-3. uRPF

uRPF（Unicast Reverse Path Forwarding）は送信元IPへの戻り経路などを利用し送信元の妥当性を検証します。厳格な方式では非対称ルーティングによって正当な通信を拒否する可能性があるため、構成に合う方式を選択します。

13-4. 不要なUDPサービスを公開しない

社内向けDNSキャッシュサーバは不特定多数の再帰問い合わせを受け付ける必要がありません。再帰問い合わせ元を社内に限定し、不要なUDPサービスは停止するかFWで制限します。

13-5. レート制限

DNSやNTPの異常な頻度の要求・応答を制限します。過度なレート制限は正当な通信にも影響するため、正常時の通信量を把握して設定します。

13-6. DDoS対策は上流での対応も必要

大量のUDP応答が回線へ流入すると、組織内FWで破棄してもそこまでの回線帯域は消費済みです。ISPやDDoS対策サービスと連携し上流側で処理する必要があります。

14. ステートフルファイアウォールとUDP

A：ログ・通信制御／B：状態管理の仕組み

14-1. UDPにはコネクションがないのに状態管理できるのか

できます。ステートフルFWはUDPの通信情報を一定時間保持し、要求に対応する戻り通信を識別できます。

社内PC：192.0.2.100:53000
DNSサーバ：198.51.100.53:53

FWは通信元・先のIPとポートなどをもとに状態を記録し、戻りUDP Responseをポリシーに従い許可します。

14-2. UDPの疑似的なセッション管理

① 内部PC → 外部DNS
   UDP 53000 → 53
          ↓
② FWが通信情報を記録
   IP・ポート・プロトコル・タイムアウトなど
          ↓
③ 外部DNS → 内部PC
   UDP 53 → 53000
          ↓
④ 記録した通信に対応すればポリシーに従って許可

これはTCPの3ウェイハンドシェイクの監視ではなく、FW独自のUDP通信状態管理です。

14-3. UDPのタイムアウト

UDPにはTCPのFINのような終了通知がないため、FWは一定時間通信がないと状態を削除することがあります。

10:00:00 PC → DNS：Query
10:00:00 FW：UDP通信状態を記録
（一定時間経過）
FW：UDP通信状態を削除
10:01:30 DNS → PC：Response
FW：対応する状態がなく拒否

タイムアウト値や状態管理方法は製品・設定によって異なります。

14-4. UDPなら外部から自由に通信できるのか

いいえ。UDPがコネクションレスであることとFWが無条件に許可することは別です。FWはIP、ポート、方向、状態、通信量などで制御できます。

15. UDP通信のログ分析

15-1. 正常なDNS通信

10:00:01.100
192.0.2.100:53000 → 192.0.2.53:53
UDP DNS Query

10:00:01.120
192.0.2.53:53 → 192.0.2.100:53000
UDP DNS Response

要求と応答で送信元・宛先のIP・ポートが入れ替わります。応答の正当性はDNSトランザクションIDや問い合わせ内容なども確認します。

15-2. UDPの応答がない場合

10:05:01.100
192.0.2.100:53000 → 192.0.2.53:53
UDP DNS Query

10:05:03.100
192.0.2.100:53000 → 192.0.2.53:53
UDP DNS Query

DNSサーバの無応答、応答の途中破棄、アプリケーションが応答を受け付けないことなどが考えられます。再送のように見える通信はDNSクライアント側の処理かもしれません。

15-3. DNSリフレクション攻撃を疑うログ

10:10:01 192.0.2.53:53 → 203.0.113.100:53000 UDP DNS Response
10:10:01 192.0.2.54:53 → 203.0.113.100:53000 UDP DNS Response
10:10:01 192.0.2.55:53 → 203.0.113.100:53000 UDP DNS Response

複数DNSサーバから被害者に短時間で大量応答が届いている場合、リフレクションの可能性があります。調査点は次のとおりです。

  1. 被害者が実際にDNS Queryを送信したか。
  2. 応答の件数・サイズが通常より大きいか。
  3. 複数のDNSサーバから応答が集中しているか。
  4. トランザクションIDや問い合わせ内容が正当な通信と一致するか。
  5. 通信量増加が回線やサービスへ影響しているか。

大量のDNS応答だけで攻撃と断定しません。

15-4. IPスプーフィングを疑うログ

Interface : WAN
Direction : IN
Source IP : 192.0.2.100
Destination IP : 192.0.2.10
Protocol : UDP
Action : DENY

社内ネットワークが 192.0.2.0/24 なら、WAN側から社内アドレスを送信元とするパケットが来たことになります。通常構成では偽装が疑われます。どのインターフェースから受信したかが重要な根拠です。

15-5. DNSの応答を遮断したログ

10:20:01 ALLOW
192.0.2.100:53000 → 198.51.100.53:53 UDP

10:20:05 DENY
198.51.100.53:53 → 192.0.2.100:53000 UDP
Reason: No matching session

要求は許可され応答は拒否されています。No matching session は製品依存のログ表現例です。UDP状態のタイムアウト、戻り経路の相違などが考えられますが、このログだけで確定せず設定や経路を調査します。

16. 科目Aで押さえる典型論点

論点 覚えるべきこと

UDPヘッダ 基本ヘッダは8バイト

17. 科目Bの答案作成ポイント

17-1. 設問例①：UDPとTCPの違い

設問：UDPがTCPと異なり、コネクションレス型と呼ばれる理由を説明せよ。

答案例：「UDPはTCPの3ウェイハンドシェイクのような事前のコネクション確立を行わず、データグラムを送信するため。」

解説：単に「UDPは速いから」ではなく、通信開始時の処理の違いを示します。

17-2. 設問例②：UDPとIPスプーフィング

設問：UDPを使用するDNSサーバが、送信元IPアドレスを偽装した要求に対して被害者へ応答を送ってしまう理由を説明せよ。

答案例：「UDPにはTCPのような接続確立時の応答確認がなく、DNSサーバが要求パケットに記載された送信元IPアドレスへ応答するため。」

解説：コネクションレス性と応答先に送信元IPアドレスを利用することを結び付けます。

17-3. 設問例③：DNSリフレクション攻撃

設問：DNSリフレクション攻撃の仕組みを説明せよ。

答案例：「攻撃者が送信元IPアドレスを被害者に偽装してDNSサーバへ問い合わせ、DNSサーバからの応答を被害者へ集中させる攻撃。」

解説：「誰が偽装するか」「誰が応答するか」「誰に届くか」を明確にします。

17-4. 設問例④：DNS増幅攻撃

設問：DNS増幅攻撃で攻撃者の送信量より大きな通信量が被害者へ届く理由を説明せよ。

答案例：「小さなDNS問い合わせに対して大きなDNS応答を返す性質を利用し、送信元を偽装した問い合わせによって、その応答を被害者へ送らせるため。」

17-5. 設問例⑤：IPスプーフィング対策

設問：外部インターフェースから、送信元IPアドレスが自組織の内部ネットワークに属するパケットを受信した。どのような対策を行うべきか。

答案例：「外部から受信したパケットの送信元IPアドレスを検証し、自組織の内部アドレスを不正に名乗るパケットを境界機器で遮断する。」

17-6. 設問例⑥：UDP Floodと対策場所

設問：UDP Floodによってインターネット接続回線が飽和している。社内ファイアウォールだけで遮断する対策が不十分な理由を説明せよ。

答案例：「社内ファイアウォールへ到達する前に大量のUDP通信が接続回線の帯域を消費するため、ISPなどの上流側で通信を遮断・処理する必要がある。」

17-7. 記述問題で意識する因果関係

① UDPにはTCPの接続確立手順がない
          ↓
② 送信元IPを偽装した要求に応答するサービスがある
          ↓
③ 第三者のサーバが被害者へ応答を送る
          ↓
④ 大きな応答が多数集中すると通信量が増幅される
          ↓
⑤ 送信元偽装対策・サービスのアクセス制御・上流DDoS対策で防ぐ

この流れを理解すれば、DNS、NTPなどサービスが変わっても同じ考え方で設問に対応できます。

18. 重要事項の整理

第一に、UDPはコネクションレス型のトランスポート層プロトコルです。 TCPのような3ウェイハンドシェイクを行わず、データグラムを送信します。

第二に、UDP自体は再送、順序制御、フロー制御を提供しません。 ただし必要な制御をアプリケーション側で実装できます。

第三に、UDPヘッダは8バイトです。 送信元ポート、宛先ポート、Length、Checksumの四つのフィールドがあります。

第四に、UDPはDNS、NTP、リアルタイム通信などで利用されます。 接続確立を省けることやアプリケーション独自の制御を行えることが利点です。

第五に、IPスプーフィングは送信元IPアドレスの偽装です。 UDPの接続確立手順がない性質と組み合わさりリフレクション攻撃に悪用されます。

第六に、リフレクションと増幅は異なる概念です。 リフレクションは第三者に応答を送らせること、増幅は要求より大きな通信量を発生させることです。

第七に、UDP Floodは大量のUDP通信によって帯域や処理能力を消費させる攻撃です。 回線飽和の場合は上流側での対策が必要です。

第八に、UDPはコネクションレスでも、ファイアウォールは通信状態を管理できます。 要求・応答の対応付けやタイムアウトを理解すると通信障害ログを分析できます。

C：発展学習として切り分ける内容

  • QUICの暗号化ハンドシェイクとストリーム管理の詳細
  • RTP・RTCPの詳細なパケット構造
  • STUN、TURN、ICEなどのNAT越え技術
  • UDP-Liteなどの特殊なトランスポートプロトコル
  • 製品固有のDDoS防御アルゴリズム
